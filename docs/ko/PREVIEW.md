# 3D 뷰의 질감

3D 뷰(독립 실행형 Rust 구현의 자체 렌더링. wgpu)는 그린 채널을 그대로 모델에 입혀 보여줍니다.
이 페이지에서 비교하는 대상은 Unity 안에서 그릴 수 있었던 0.4.x까지의 Unity 브리지 미리 보기입니다(0.5.0 이후의 Unity 브리지에는 그리기 기능과 3D 미리 보기가 없습니다).

외형 수식은 0.4.x까지의 Unity 브리지 미리 보기 셰이더
(`PreviewSurfaceLit`·`PreviewSurface`·`PreviewEnvironment`·`PreviewToneMap`)와 그 바탕이 된 Unity Standard의 BRDF(`UnityStandardBRDF.cginc`의
`BRDF1_Unity_PBS`, 선형 색 공간)를 WGSL(wgpu의 셰이더 언어)로 옮긴 것입니다. 같은 수식을 CPU에도 작성했으며(`crates/yolu-app/src/view3d/brdf.rs`), 테스트에서 알려진 값과
GPU 이미지를 대조합니다. 외형 종류를 lilToon으로 설정한 텍스처 세트는 lilToon 수식으로 그립니다([lilToon 외형](#liltoon-の見た目)).

## 표시 전환

3D 뷰 왼쪽 위 모서리의 드롭다운(툴팁 「3D 표시」)을 눌러 여는 메뉴에서 선택합니다(순서는 0.4.x까지의 Unity 브리지와 같음). 3D 뷰를 늘리면 뷰마다 선택할 수 있습니다.

| 표시 | 보이는 내용 |
|---|---|
| 머티리얼(PBR) | 금속성 방식의 PBR. Color·Roughness·Metallic·Normal·Emission이 적용됩니다. 환경·조명·톤 매핑을 사용합니다. 외형이 lilToon인 세트는 lilToon 수식으로 그립니다 |
| 중립 | 0.4.x까지의 Unity 브리지의 단순한 명암(`0.35 + 0.65 × saturate(n·L)`, 감마 공간). 노멀 맵이 적용됩니다. 환경을 사용할 때는 환경 확산과 약한 반사가 적용됩니다 |
| 채널만 | Color·Roughness·Metallic·Normal·Emission·Height 또는 현재 텍스처 세트의 사용자 채널 중 하나를 조명·환경·톤 매핑 없이 값 그대로 표시합니다. 사용자 채널은 이름으로 찾으며, 같은 이름의 채널이 없는 세트의 면은 체크무늬로 표시합니다 |
| 메시 맵만 | 베이크한 메시 맵(AO·곡률·노멀 등) 하나를 조명·환경·톤 매핑 없이 값 그대로 표시합니다. 각 세트의 면에 해당 세트에서 베이크한 맵을 표시합니다(베이크하지 않은 세트의 면은 체크무늬). 어느 세트에도 베이크되지 않은 종류는 선택할 수 없으며, 보고 있는 맵이 모든 세트에서 없어지면 머티리얼로 돌아갑니다 |

오른쪽 위 모서리의 「조명·환경·톤 매핑」 아이콘으로 작은 패널을 엽니다. 표시(조명·환경·톤 매핑. 그림자 활성화와 부드러움도 여기)·화질(안티앨리어싱과 블룸)·시점의 세 페이지가 있습니다.
시점 페이지에는 회전 중심(화면 중심·면 위치(자동 깊이)·모델 중심·텍스처 세트 중심. 기본값은 화면 중심), 확대·축소 중심(화면 중심으로·포인터 위치로. 기본값은 화면 중심),
현재 텍스처 세트의 면을 화면에 맞추는 「선택한 부분에 맞추기」가 있습니다. 오른쪽 위 모서리에는 모델 전체가 보이는 위치로 돌아가는 아이콘과 3D 이미지가 원본보다 축소되었을 때의 경고 표시도 나타납니다. 그 아이콘 아래에는 축 표시(X·Y·Z의 양·음 방향 원)가 있으며, 원을 누르면 해당 방향에서 보는 시점이 되고,
가운데 원으로 원근 투영과 직교 투영을 전환하며, 표시를 드래그하면 시점이 회전합니다. 축 방향 시점으로 바꾸거나 스냅 회전(Alt를 누른 채 오른쪽 드래그)으로 축 시점으로 전환하면 직교 투영이 되고, 회전하여 축에서 벗어나면 원근 투영으로 돌아갑니다.
(설정의 「축 방향에서 직교 투영」. 기본값은 켬. 직접 바꾼 투영 방식은 축에서 벗어나도 되돌리지 않습니다.)

- 환경: 없음(균일한 환경광)·하늘(0.4.x까지의 Unity 브리지의 기본 그라데이션)·스튜디오(어두운 회색 배경에 면광원. 금속 반사와 회전을 확인할 수 있음). 밝기·회전·배경에 표시할지(및 흐림)를 설정합니다.
  하늘은 위쪽 축을 중심으로 대칭이므로 회전해도 외형이 변하지 않습니다.
- 조명: 강도·방위·높이(0.4.x까지의 Unity 브리지의 `PreviewSceneSettings`와 같은 항목). 강도 1(기본값)은 Unity 장면의 흰색·강도 1 방향광과 같은 밝기입니다. 기본 입사 방향은 (−0.3, 0.65, +0.7), 즉 모델 앞(+Z)의 비스듬한 위쪽입니다.
  (0.4.x까지의 Unity 브리지 기본값 (−0.3, 0.65, −0.7)을 Z축에서 뒤집은 방향이며, 높이와 가로 오프셋은 같습니다.) Unity는 +Z를 앞쪽으로 삼으므로 정면에서 볼 때 역광이 되지 않습니다(기본 카메라도 모델 앞에서 보므로 처음 열자마자 밝은 쪽이 보입니다).
- 그림자: 주 조명으로 모델 자체에 드리우는 그림자(기본값은 끔)와 부드러움(그림자 가장자리 흐림 폭. 0%는 그림자 맵 1픽셀, 100%는 모델 크기의 약 2.5%).
  머티리얼과 중립 표시에 적용되며, 조명 없는 표시(채널만·메시 맵만)에서는 사용하지 않습니다.
- 톤 매핑: 없음·뉴트럴·ACES와 노출(EV). 3D 뷰의 이미지에만 적용합니다(텍스처 값·내보내기·2D에는 적용하지 않음).

### 화질(안티앨리어싱과 블룸)

둘 다 3D 뷰의 이미지에만 적용합니다(텍스처 값·내보내기·2D·칠할 때의 적중 판정에는 영향을 주지 않음). 설정 파일(`view3d_antialias`·`view3d_bloom`·
`view3d_bloom_strength`·`view3d_bloom_threshold`)에 저장합니다.

- 안티앨리어싱: 끔·2×·4×·8×(기본값 4×). 면을 다중 샘플로 그려 가장자리를 부드럽게 합니다(MSAA). 사용할 수 있는 수는 GPU에 따라 정해지며 지원하지 않는 수는 선택할 수 없습니다.
  렌더 타깃 메모리가 상한을 넘는 크기(큰 창에서 높은 샘플 수·HDR·블룸 조합)에서는 상한 안에 들어가는 수로 자동으로 낮춥니다(선택한 수는 유지).
  상한은 설정의 「GPU 메모리」가 3D 이미지에 배정하는 양과 같으며, 설정의 합계(3D 이미지·캔버스·에셋 썸네일에 배정한 양) 안이 아닌 바깥에 추가됩니다. 렌더 타깃을
  상한까지 올리면 합계에 더해 해당 양까지 사용합니다(표준값 512 MiB. 아래 표에서 4K HDR＋블룸의 4×는 약 496 MiB). 3D 이미지 몫에서 빼지 않는 이유는
  창 크기나 샘플 수를 바꿀 때마다 이미지가 다시 축소되기 때문입니다. 블룸과 톤 매핑은 다중 샘플을 하나로 리졸브한 뒤의 이미지에 적용합니다.
  확인한 것은 소프트웨어 렌더링(llvmpipe의 Vulkan)이 지원하는 1×와 4×입니다. 2×·8×와 Windows의 D3D12·Vulkan 실제 장치에서는 확인하지 않았습니다.
- 블룸: 켬·끔(기본값은 끔), 강도, 임곗값. 노출을 적용한 뒤의 밝기(선형. 1이 흰색)가 임곗값을 넘는 부분을 추출하고, 축소하면서 흐리게 한 뒤 다시 더합니다.
  (톤 매핑 전.) 발광(Emission)이 강한 곳의 주변이 빛나 보입니다. 조명 없는 표시(채널만·메시 맵만)에는 더하지 않습니다. 끔(켜져 있어도 강도 0인 경우 포함)일 때는
  블룸 처리를 거치지 않으며, 같은 샘플 수에서 블룸 도입 전에 그린 이미지와 바이트까지 같습니다(테스트는 켬과 끔을 왕복하여 확인합니다). 안티앨리어싱 기본값이 4×가 되었으므로
  다중 샘플이 없던 이전 버전의 이미지와는 가장자리가 다릅니다.

렌더 타깃 메모리의 대략적인 양(리졸브한 이미지·깊이·다중 샘플 색·HDR·블룸 단계):

## 채널의 의미

내보내기(`export::build`)와 같은 값의 의미를 사용하므로, 보고 있는 것과 내보낸 텍스처의 값은 다음 차이를 제외하면 같습니다(불투명 픽셀의 텍셀 일치는 테스트에서 대조).

- Color: 3D 뷰는 표시를 위해 **미리 곱한 알파**로 변환하여 업로드합니다(투명한 가장자리가 검게 되지 않음). 내보내기는 straight RGBA(투명 픽셀의 RGB를 유지)이므로 반투명·투명 픽셀에서는 값이 다릅니다.
  불투명 픽셀은 같습니다. Color의 투명한 곳은 회색 체크무늬 위에 보입니다.
- Color·Emission은 sRGB 텍스처로 보관하고, GPU에서 읽을 때 텍셀을 선형으로 바꾼 뒤 보간합니다(밉도 선형으로 평균). Unity가 선형
  색 공간에서 sRGB 텍스처를 읽는 것과 같으므로 색 경계의 중간색·멀리서 축소된 이미지의 밝기가 Unity와 맞습니다. Color의 미리 곱하기도 선형에서 수행합니다.
  (sRGB(선형(색) × α).) 체크무늬 위에 겹쳐 보이는 모양(중립·채널만 표시 및 머티리얼 표시의 투명한 곳)은 기존처럼 감마 값으로 합성합니다.
- Emission: RGB는 내보내기와 같습니다(값 × 알파). 3D 뷰는 알파도 보관하지만 읽지는 않습니다(내보내기는 알파를 불투명으로 설정).
- Roughness·Metallic·Height: 값 × 알파(칠하지 않은 곳은 0)로, 모든 텍셀이 내보내기와 같습니다. Roughness는 매끄러움 = 1 − Roughness로 읽습니다.
- Normal: Normal 출력(칠한 노멀을 평평한 노멀 위에 얹고, Height → Normal이 활성화되어 있으면 Height에서 만든 노멀을 바탕으로 겹친 것. OpenGL Y+)이며, 모든 텍셀이 내보내기와 같습니다.
- 어떤 레이어에서도 활성화하지 않은 채널은 내보내기의 기본값(Roughness 0.5·Metallic 0·Normal은 평평함·Emission은 검정·Color는 투명)을 보여줍니다.

노멀 맵의 접선은 Unity의 `Mesh.RecalculateTangents`와 같은 MikkTSpace(`bevy_mikktspace`)로 삼각형의 각 꼭짓점마다 만듭니다(FBX와 Live Link 모델 모두).
수만 개의 삼각형이 있는 모델은 수백 밀리초가 걸리므로 별도 스레드에서 만들며, 완성되기 전까지는 이전 모델의 접선으로 그립니다(포즈마다 모델이 바뀔 때도 그리기를 멈추지 않습니다).

## 속도

카메라·크기·모델·칠한 이미지·표시 설정 중 하나가 바뀌었을 때만 그립니다. 칠한 이미지는 core가 「변경됨」이라고 알린 타일만 합성하여 업로드합니다.
(인접 타일은 한 번의 쓰기로 묶고, 전체 면을 만들 때는 1024행씩 띠로 처리.) 전체 면을 만들 때는 레이어에 면이 있는 타일만 합성합니다. 다만 채우기·조정 레이어나 해당 채널에 적용되는 필터·Generator(레이어 마스크에 있는 것 포함)가 있으면 면이 없는 타일에도 효과가 나타나므로 모든 타일을 합성합니다. 변하지 않은 채널은 건드리지 않고 사용하지 않는 채널은 텍스처를 갖지 않습니다.
밉맵은 변한 범위만 다시 만듭니다(단계마다 변한 범위를 1픽셀 넓혀 그리므로 홀수 크기에서도 전체를 다시 만든 결과와 모든 단계에서 일치합니다. 테스트에서 대조).
3D 뷰에 업로드하는 이미지는 UV 아일랜드 바깥으로 16텍셀 넓혀 칠합니다(내보내기 패딩과 같은 수식. 문서·내보내기는 바꾸지 않고 표시용 복사본만 변경). 멀리서 볼 때
밉 단계가 아일랜드 바깥의 투명·0(또는 그라데이션 데칼처럼 UV 바깥에 값을 만들지 않는 효과 아래의 채우기 색)을 섞어 이음새에 선이 생기는 것을 방지합니다.
밉맵(단계 1 이후)은 박스 평균 대신 UV 위의 픽셀(아일랜드와 넓혀 칠한 16텍셀)만으로 만듭니다. UV 위인지 나타내는 가중치 이미지(텍셀당 1바이트, 밉 포함)를
세트마다 하나씩 가지고 채널끼리 공유합니다. 가중치 이미지는 메모리 예산에 포함됩니다(다음 「메모리」). 현재 세트는 UV 덮임과 확장 단계 맵을 모델의 UV 형태·문서 크기마다 한 번만 만들고, 그린 타일은 주변에서
확장이 닿는 곳만 다시 넓혀 칠한 뒤 업로드합니다(전체를 넓혀 칠한 것과 같은 값. 테스트에서 대조). 다른 세트는 문서 크기의 메모리가 세트 수에 비례해
남지 않도록 문서가 변해 동기화할 때마다 덮임과 단계 맵을 다시 만듭니다(4096² 세트에서 약 0.1초).
Height → Normal 설정은 레이어 합성을 바꾸지 않으므로 설정이 변하면 Normal을 다시 만듭니다.
기즈모나 슬라이더를 드래그하여 문서가 변경을 묶는 동안에는 효과 출력이 아직 평가되지 않은 타일을 1/4 크기로 거칠게 합성하여 업로드하고, 놓으면 정확하게 다시 업로드합니다.
(Height에서 만드는 Normal은 이웃 픽셀을 읽으므로 거칠게 만들지 않습니다.) 거칠게 업로드한 타일은 넓혀 칠하지 않고 가중치를 사용하지 않는 박스 평균으로 밉을 만들기 때문에 그동안만 아일랜드 가장자리가 조금 번집니다.
놓으면 정확하게 다시 업로드하며 번짐은 사라집니다.

메모리: 사용 중인 모든 채널 텍스처(밉 포함)의 예산은 512 MiB입니다. 가중치 이미지(넓혀 칠할 때. 기본값)는 텍셀당 1바이트로 계산하여 이 예산에 포함합니다.
4096²의 6개 채널 전체(약 341 MiB)는 들어가며, 8192²의 6개 채널(약 1.33 GiB)은 한 단계 줄여 4096²로 만듭니다. 예산을 넘는 문서는 할당 전에 2의 거듭제곱으로 축소해 보관하고(박스 평균), 3D 뷰 오른쪽 위 모서리에 경고 표시를 띄우며 툴팁에 「축소 표시 1/2」처럼 표시합니다(이미지와 내보내기는 원래 크기 유지).
새 채널을 사용하기 시작해 예산을 넘으면 축소 단계를 높여 전체를 다시 만듭니다. 축소 단계는 높이기만 하며 문서가 바뀌면 다시 정합니다. GPU 텍스처 변 길이의 상한을 넘는 문서도 같은 경로로 축소합니다.
메시 맵 한 장도 변 길이의 상한과 예산(채널 예산의 절반)을 넘으면 축소합니다.

### 모든 텍스처 세트의 이미지

3D 뷰는 모든 텍스처 세트의 이미지를 보여줍니다(현재 세트를 바꿔도 이전 세트의 면에서 이미지가 사라지지 않습니다). 그리기 대상은 현재 세트 그대로이며,
다른 세트의 면에는 그릴 수 없습니다.

- 현재 세트는 문서 크기 그대로입니다(위의 예산과 축소 적용). 다른 세트는 변 길이를 최대 1024로 축소해(2의 거듭제곱으로, 박스 평균) GPU에 보관하고, 해당 세트의 문서가 바뀔 때
  (리비전·변경 기록)만 변한 타일을 동기화합니다. 사용 채널은 현재 세트와 같고 Normal·Roughness 등도 적용됩니다.
- 메모리 예산(위의 512 MiB)에는 현재 세트의 이미지를 먼저 넣고 나머지에 다른 세트를 넣습니다. 들어가지 않으면 현재 세트에서 배열상 멀리 떨어진 세트부터 보관하지 않으며,
  해당 세트의 면은 이미지 없는 방식(체크무늬)으로 그려집니다. 텍스처 세트 목록의 해당 행에 경고 표시가 붙고 툴팁에 이유가 나옵니다. Unity에 전달할 대상이 없다는 경고나
  「Unity에 표시 중」과도 별개의 상태이므로 표시는 하나를 유지하고 툴팁에 나란히 표시합니다. 3D를 그리지 않는 동안(캔버스 탭이 앞에 있는 동안) 모델이나 현재 세트가
  바뀌면 이전 표시를 지웁니다(3D가 앞에 나오면 다시 계산).
- 눈을 감은 세트와 모델에 면이 없는(포즈의 「면 숨기기」로 모든 면을 숨긴) 머티리얼 세트는 보관하지 않습니다(눈을 열거나 면이 돌아오면 문서에서 만듦).
- 현재 세트가 바뀌면 이전 세트 이미지는 밉 단계를 복사하여 1024 크기로 축소해 보관합니다(GPU 안에서만 수행. 문서를 다시 합성하지 않음). 변 길이가 홀수인 경우 등 단계의 크기가
  문서에서 축소한 크기와 맞지 않을 때만 그 자리에서 문서로부터 다시 만듭니다(다른 세트의 재생성과 마찬가지로 해당 프레임의 첫 번째 항목이므로 40 ms를 넘어도 실행).
  전환한 대상 세트는 문서 크기로 다시 만듭니다(이는 기존부터 필요).
- 전환 프레임의 순서는 GPU 메모리가 예산을 넘어 겹치지 않도록 정했습니다. 새 현재 세트 이미지가 차지할 양을 예산에서 빼고 다른 세트의 보관 여부를 정한 다음,
  보관하지 않을 것을 버리고, 이전 이미지를 축소한 뒤 새 현재 세트 이미지를 만듭니다. 이전 이미지(전체 크기)와 새 이미지(전체 크기)가 동시에 올라가지 않습니다. 보장 범위는 직전 프레임
  종료 시 보관하던 이미지가 예산 안에 들어가 있던 경우입니다(예산을 낮춘 직후 프레임은 낮추기 전에 보관하던 분량이 먼저 올라가 있습니다). 측정한 최댓값은 아래 표와 같습니다.
- 다른 세트의 합성 작업 버퍼(CPU. 1024행 띠 분량, Height에서 만드는 Wrap Normal은 문서 전체. 4096²의 Wrap Normal이면 세트 하나당 약 128 MiB로 추정)는
  생성이 끝나면 해제합니다. 해제하지 않으면 세트 수에 비례해 CPU 메모리가 남습니다(이 분량은 GPU 예산에 포함되지 않음). 현재 세트의 버퍼는 그리기 갱신에 사용하므로 보관합니다.

  (창은 다음 프레임을 요청합니다.) 큰 세트가 많은 프로젝트에서도 한 프레임에 작업이 겹쳐 멈추지 않고 이미지가 순차적으로 나타납니다. 작은 문서는 한 프레임에 모두 나옵니다.
- 그리기는 머티리얼별 드로 호출 방식입니다. 정점을 머티리얼 순서로 정렬하고(모델을 바꿀 때만 다시 업로드. 세트를 바꿔도 다시 업로드하지 않음), 머티리얼마다
  이미지(6개 채널) 바인딩을 바꿔 그립니다. 이미지가 없는 머티리얼은 인접한 것끼리 한 번에 묶습니다. 텍스처 배열로 한 번에 그리는 안은 문서 크기가 세트마다 다르므로
  (현재 세트만 다른 해상도) 크기를 맞춰 다시 만드는 수고와 레이어 수 상한이 필요하며, 얻는 이점은 아래 호출 수만큼뿐이어서 채택하지 않았습니다.
- 메시 맵만 표시는 현재 세트의 면에만 붙입니다(다른 세트의 면은 이미지 없는 방식으로 그립니다).

  카메라 회전 시 1.18·1.19, Color·Roughness 칠하기 시 1.08·1.17, 모든 채널 칠하기 시 1.04·1.07이며, 소프트웨어 렌더링에서는 그림자 읽기(16점의 비교 샘플링) 비용이 1.04~1.19배로 나타납니다.
- 실제 GPU에서는 그림자 있음·없음의 차이가 회차별 편차 안에 들어갑니다(모든 채널 1.12·0.98, Color·Roughness 0.95·1.00, 카메라 회전 0.90·0.98).
- 실제 GPU 열은 WSL2의 `/dev/dxg`를 Mesa의 d3d12 드라이버로 OpenGL에 통과시킨 것으로, Windows D3D12 자체가 아닙니다. 이 경로에서는
  `write_texture` 한 번당 약 1.1 ms의 고정 부담이 생기며 그리는 중 CPU 시간의 대부분을 차지합니다. 이 경로에서는 측정 끝에 프로세스가 SIGSEGV로 종료됩니다.
  (수치가 나온 뒤이며 일반 테스트에서도 같음.) Windows D3D12에서의 값은 확인하지 않았습니다.

## 0.4.x까지의 Unity 브리지 외형과 비교하는 방법

Unity 브리지 0.5.0 이후에는 3D 미리 보기가 없으므로 비교하려면 0.4.x까지의 Unity 브리지 패키지를 사용합니다.

1. 0.4.x까지의 Unity 브리지 프로젝트의 색 공간을 Linear로 설정합니다. 머티리얼은 내장 Standard로 설정합니다(0.4.x까지의 Unity 브리지 미리 보기는 lilToon을 그리지 않습니다. lilToon 외형 비교 방법은 아래
   [lilToon 외형](#liltoon-の見た目) 참조).
2. 같은 모델을 양쪽에 넣습니다(Live Link로 같은 모델을 보내거나 같은 FBX 열기). 양쪽에서 「모델 전체가 보이는 위치로 돌아가기」를 누릅니다. 0.4.x까지의 Unity 브리지는 비스듬한 뒤쪽(yaw 25°·pitch 10°), Rust 구현은 같은 비스듬한 각도로 모델 앞(+Z 쪽. yaw 205°·pitch 10°)에서 시작하므로(모델을 연 직후도 같음), 같은 방향에서 비교하려면 0.4.x까지의 Unity 브리지 카메라를 수평으로 180° 돌려 정면에서 봅니다.
3. 0.4.x까지의 Unity 브리지 3D 뷰를 「머티리얼」 표시로 바꾸고 장면 설정을 기본값(환경 없음·그림자 없음·톤 매핑 없음·노출 0·조명 기본값)으로 되돌립니다.
   Rust 구현은 조명 패널의 「기본값으로 되돌리기」 후 환경을 「없음」으로 바꾸고 조명 방위를 −157°·높이를 40.5°로 설정합니다(0.4.x까지의 Unity 브리지 기본 입사 방향 (−0.3, 0.65, −0.7).
   Rust 구현 기본값은 앞(+Z)에서 오는 방향이므로 그대로는 맞지 않습니다). 조명 강도를 0.769로 설정합니다(0.4.x까지의 Unity 브리지 3D 뷰의 조명은 에디터 미리 보기
   창의 조명 색 0.769 × 강도. Rust 구현의 강도는 Unity 장면 방향광의 강도와 같은 의미이며 강도 1은 흰색·강도 1의 조명입니다).
   화질 페이지에서 안티앨리어싱을 「끔」으로 설정합니다(0.4.x까지의 Unity 브리지는 가장자리를 부드럽게 하지 않음). 이로써 조명(입사 방향·밝기)과 환경광(회색 0.5의 0.4배)이 같아집니다.
4. 환경이 있는 비교에서는 0.4.x까지의 Unity 브리지를 「하늘」(기본 천정·수평선·지면 색), Rust 구현도 「하늘」로 설정합니다. 「스튜디오」는 Rust 구현에만 있습니다.
5. 수치로 비교하려면 판(Unity Quad와 같은 방향)을 정면에서 보고 조명을 정면(방위 180°·높이 0°)으로 비추며, Color (200, 120, 60) 채우기와
   Metallic·Roughness 채우기를 넣습니다. 중심 픽셀은 CPU 수식(`brdf::standard_brdf`, 조명 강도 0.769)으로 계산한 값과 ±3 범위에서 일치합니다(Rust 구현의 테스트
   `the_material_view_matches_the_cpu_brdf_head_on`은 같은 수식을 기본 강도 1에서 대조):

   | Metallic | Roughness | 중심 픽셀(sRGB) |
   |---:|---:|---|
   | 0 | 255 | 156, 94, 50 |
   | 0 | 128 | 172, 122, 95 |
   | 0 | 0 | 195, 155, 136 |
   | 255 | 128 | 255, 172, 89 |
   | 255 | 20 | 255, 255, 255 |
   | 128 | 200 | 145, 88, 48 |

   0.4.x까지의 Unity 브리지에 같은 판·같은 값(Standard의 `_MainTex`·`_MetallicGlossMap`(R = Metallic, A = 1 − Roughness))을 넣고 같은 지점을 보며 비교합니다.

<a id="04x-までの-unity-ブリッジとの違い保証の射程"></a>

### 0.4.x까지의 Unity 브리지와의 차이(보장 범위)

- 3D 뷰의 초기 카메라: 0.4.x까지의 Unity 브리지는 모델의 비스듬한 뒤쪽(−Z 쪽), Rust 구현은 같은 비스듬한 각도로 모델 앞(+Z 쪽)에서 봅니다. 「모델 전체가 보이는 위치로 돌아가기」도 같은 방향입니다.
- 환경 「없음」의 반사: Rust 구현은 균일한 환경광(회색 0.5의 0.4배)을 반사합니다. 0.4.x까지의 Unity 브리지는 미리 보기 장면의 기본 프로브를 사용하며 같은지는 확인하지 않았습니다.
- 접선: Rust 구현은 MikkTSpace의 꼭짓점별 값을 사용하고, Unity의 `RecalculateTangents`는 정점마다 하나로 묶습니다. UV 이음새·미러 경계에서 노멀 맵의 명암이 조금 다를 수 있습니다.
- 텍스처 밉맵: Rust 구현은 UV 위의 픽셀만 밀고 당기는 방식(위의 「속도」), Unity는 엔진의 밉을 사용합니다. Rust 구현은 칠한 이미지를 읽는 샘플러에 16배 비등방성 필터링을 사용하므로 비스듬히 본 면의 이미지가 흐려지지 않습니다.
  (GPU가 지원하지 않을 때와 CPU로 그리는 어댑터〔lavapipe 등〕에서는 1배.) 0.4.x까지의 Unity 브리지 비등방성 설정과 일치하는지는 확인하지 않았습니다.
- 그림자: 0.4.x까지의 Unity 브리지는 Standard 셰이더를 수정할 수 없으므로 최종 색 전체(반사·발광 포함)에 「환경광 ÷ (환경광 + 직접광 × n·L)」을 곱해 어둡게 하는
  덧그리기로 근사합니다. Rust 구현은 자체 셰이더이므로 그림자 부분의 직접광(확산과 정반사 모두)만 없애고 환경광·반사·발광은 남깁니다. 램버트 면이라면
  확산은 0.4.x까지의 Unity 브리지와 같은 밝기가 되며, 정반사·반사·발광이 있는 면은 외형이 다릅니다. 바이어스도 다릅니다. 0.4.x까지의 Unity 브리지는 흐림 반지름에 비례하는 상수이고, Rust 구현은 면의 기울기에서
  깊이 기울기를 구해 읽는 지점마다 면 위의 깊이로 보정합니다(흐림을 넓혀도 조명에 대해 누운 면이 스스로에 그림자를 드리우지 않음). 그림자는 주 조명 하나에서 모델 내부로 드리우는 것만 지원합니다.
- Unity의 텍스처 HDRI·시차(Height 시차 맵)는 Rust 구현에 아직 없습니다. 다른 텍스처 세트의 동시 표시는 다른 세트의 변 길이를 최대 1024로 축소해 보여주므로
  (현재 세트는 문서 크기) 다른 세트의 세밀한 그림은 현재 세트로 선택하기 전까지 거칠게 보입니다.
- 색 공간: 질감 수식은 선형에서 풀고 출력은 「화면에 그대로 내보내는 값」(감마)입니다. 0.4.x까지의 Unity 브리지 Gamma 색 공간의 외형과는 맞지 않습니다.
- Windows D3D12·macOS Metal에서의 외형과 속도는 이 컨테이너에서 확인하지 않았습니다(스냅샷은 llvmpipe로 촬영했으며 실제 장치에서는 가장자리와 보간이 조금 다름).

## lilToon 외형

텍스처 세트마다 「머티리얼」 패널의 「외형」에서 종류를 「표준(PBR)」 또는 「lilToon」으로 설정합니다. lilToon 세트는 3D 뷰의
「머티리얼(PBR)」 표시에서 lilToon 2.3.4 수식으로 그립니다(중립·채널만·메시 맵만 표시는 종류와 관계없이 같음). 수식은 lilToon(MIT)의
셰이더에서 WGSL(`crates/yolu-app/src/view3d/shaders/liltoon/` 구성 요소)로 옮긴 것으로, 출처와 라이선스는 [제3자 라이선스](../../THIRD_PARTY.ko.md#liltoon-の再現式の移植)에 있습니다.
외형 설정은 세트의 .ylp에 있는 `look.json`에 들어갑니다(형식은 [YLP_FORMAT.md](YLP_FORMAT.md)의 「look.json」).

### 기본 외형

새 프로젝트·새 텍스처 세트·모델(FBX)이나 Live Link 머티리얼에서 만드는 세트는 lilToon으로 시작합니다(lilToon 셰이더의
기본값. 그림자는 끔. 메인 컬러·노멀 맵·발광은 같은 이름의 채널에 할당). 기본값을 넣는 것은 Undo에 포함되지 않으며 「저장하지 않은 변경」으로도
처리하지 않습니다. `look.json`이 없는 기존 `.ylp`는 열어도 표준을 유지하며(외형을 바꾸지 않음), 표준 설정은 `look.json`을 기록하지 않습니다.

- Live Link로 Unity에서 받은 텍스처가 있는 슬롯은 할당이 「어느 레이어에서도 사용하지 않는 표준 채널」(새 세트의 기본 할당)이면
  받은 텍스처로 그립니다. 내보내기에서도 사용하지 않는 채널의 이미지를 기록하지 않으므로 Unity의 원래 텍스처로 그리는 것이 Unity의 표시와 같습니다.
  해당 채널을 사용하기 시작하면(레이어에서 활성화) 해당 채널로 그립니다.

| 거리 페이드 | 색·시작 거리·종료 거리·강도·뒷면·모드(정점·좌표)·림 라이트 |

재현하지 않는 항목(값은 보관하고 저장하지만 그리지 않습니다. 항목에도 표시하지 않음): 그라데이션 맵, 디졸브, 디더, 시차 맵, AudioLink, ID Mask,
UV Tile Discard, 스텐실, 렌더링 설정(ZWrite·블렌드), 퍼·보석·굴절·테셀레이션·Lite 변형(비슷한 방식으로 그림), 시간에 따라 움직이는 값
(스크롤·회전·깜박임·그라데이션·데칼 애니메이션·글리터 깜박임은 시각 0의 값), 그림자 색 LUT, UV1~UV3(모델은 UV0만 지원. UV0으로 읽음.
선택한 항목에 「그리지 않음」 표시), 정점 색, 글리터 형태 텍스처, 환경광 반사 큐브맵 교체, MatCap UV1 합성, VR 값,
추가 조명(정점 조명·ForwardAdd), 라이트맵, 안개.

- 값의 규칙: 색 프로퍼티는 Unity와 같이 감마 값으로 보관하며, 선형 색 공간의 Unity와 같은 수식으로 선형으로 바꿔 사용합니다(Unity의
  `Mathf.GammaToLinearSpace`. 1 미만은 sRGB 수식, 1 이상은 pow(값, 2.2). lilToon 항목에서 1을 넘어 선택할 수 있는 색(`_BacklightColor`·`_MatCapColor`
  등. Unity의 `[HDR]`이 아님)은 16.948 → 505.9, 2.119 → 5.218이 됩니다). `[HDR]` 색(`_EmissionColor`·`_Emission2ndColor`)은
  Unity가 그대로 전달하므로 선형 값 그대로 사용합니다. 3D 뷰의 조명 색(색 × 강도. 흰색·강도 1이면 1)도 Unity의 `_LightColor0`과 같은 수식이며, 강도 1은 Unity 장면의 흰색·강도 1
  방향광과 같은 밝기입니다(Unity 2022.3의 선형 색 공간·lilToon 2.3.4에서 흰색 텍스처 구의 lilToon(기본값·그림자 있음)과
  Standard를 같은 조명과 환경광으로 촬영하여 픽셀 차이 평균 0.04 이하. 테스트 `light_of_strength_one_matches_a_unity_directional_light`).
  모두 Unity 2022.3의 선형 색 공간에서 색 프로퍼티·`[HDR]` 색·`[Gamma]` 수·조명 색을 부동소수점 렌더 타깃에 기록하여 측정한 값과 같습니다.
- 텍스처 읽기: 칠한 이미지(Color·Emission)와 MatCap의 sRGB 이미지는 Unity와 같이 텍셀을 선형으로 바꾼 뒤 보간합니다.
  사용자 채널의 sRGB 레이어와 Unity에서 받은 sRGB 이미지는 감마 값 그대로 보간한 뒤 선형으로 바꿉니다(한 배열 안에 sRGB와 선형 레이어가
  섞이기 때문. 색 경계의 중간색이 Unity보다 조금 어두움).
- 텍스처 슬롯: 슬롯마다 채널(표준 채널과 사용자 채널), 성분별 패킹(R·G·B·A 각각을 0·1·채널 성분 중에서),
  프로젝트 이미지(MatCap 이미지) 중 하나를 할당합니다. 사용자 채널은 아무것도 그리지 않은 곳을 채널 기본값 위에 겹쳐 읽습니다(내보내기의
  「lilToon 패킹」과 같은 값). 「lilToon 템플릿」은 켜져 있는 기능의 마스크 사용자 채널을 한 번의 조작으로 만들고 할당합니다.
- 슬롯 그리기: 슬롯 행 오른쪽의 브러시 버튼으로 해당 슬롯의 채널을 그리기 채널로 설정합니다. 할당이 없으면 템플릿과 같은 구성의
  사용자 채널(마스크는 스칼라 흰색, 색 레이어는 투명한 sRGB, 노멀은 평평함)을 만들어 할당합니다(한 번의 Undo). 현재 그리는 슬롯은 버튼이
  눌린 모양이 되며, 채널 항목 행에는 해당 채널을 읽는 lilToon 슬롯 표시(툴팁에 슬롯 이름)가 나타납니다.
  MatCap 이미지 슬롯(프로젝트 이미지)에는 브러시 버튼이 없습니다.
- 새 채널: 슬롯 선택지(채널 목록 끝)의 「새 채널」은 할당이 있어도 그리기 버튼과 같은 구성의 새 사용자 채널을
  만들어 할당하고 그리기 채널로 설정합니다(한 번의 Undo. 이전 채널은 삭제하지 않으며 다른 슬롯이 읽고 있으면 그대로 유지). 성분별 패킹의
  각 성분 선택지에도 있으며, 해당 성분만 새 스칼라 채널(이름은 「슬롯 채널명 R/G/B/A」. 아무것도 그리지 않은 곳은 교체하는 성분이
  0·1이면 그 값, 채널이면 슬롯의 기본값)로 바꿉니다. 3D 뷰가 보관하는 사용자 채널 상한(16)을 넘어도 만들 수 있으며 초과분은 슬롯 행에
  「그리지 않음」으로 표시합니다. MatCap 이미지 슬롯에는 나타나지 않습니다.
- 값의 규칙(추가 항목): `[Gamma]` 수(`_Metallic`·`_Reflectance`)는 Unity와 같이 sRGB → 선형(색과 같은 수식)으로 변환해 사용합니다. 할당하지 않은 노멀 맵
  슬롯은 Unity 기본 텍스처(`Texture2D.normalTexture` = (127, 127, 255, 255))로 읽습니다(거의 평평하며, 비등방성 반사의 접선 맵을
  할당하지 않으면 lilToon과 같이 접선이 비스듬해짐).
- 조명: 3D 뷰의 주 조명을 Unity 방향광(색은 조명 강도의 회색), 환경을 Unity 환경광의 SH(구면 조화 함수. 환경 「없음」은 균일한 회색, 하늘·스튜디오는 베이크한 SH를 회전에 맞춤)로 취급하여,
  lilToon이 빌트인 렌더 파이프라인에서 사용하는 OpenLit 수식(`ComputeLights`)과 lilToon 보정(밝기 하한·상한·흑백화)으로 조명의 색과 방향을 정합니다.
- 반투명: Unity와 같이 선형 공간에서 미리 곱한 색을 합성합니다(렌더 타깃의 sRGB 뷰에 두 번째 패스로 그림). 톤 매핑을 사용하거나 렌더 타깃의 sRGB 뷰를
  만들 수 없는 GPU(wgpu GL. `DownlevelFlags::VIEW_FORMATS` 없음)에서는 감마 값 그대로 합성하므로 반투명한 곳이 Unity보다 밝게 보입니다. 면을 재정렬하지 않습니다(모델 배열 순서).
- GPU 메모리: lilToon 슬롯이 읽는 사용자 채널은 세트마다 2D 텍스처 배열(채널당 레이어 1개, 최대 16레이어, GL을 위해 최소 2레이어)에 보관합니다.
  배열도 3D 뷰 전체 예산에 포함됩니다. 현재 세트의 배열은 표준 채널 이미지의 나머지에서(다른 세트보다 우선), 다른 세트는 표준 채널 이미지와 배열을
  합쳐 보관 여부를 정합니다. 둘 다 세트당 최대 256 MiB(밉 포함)이며 들어가지 않으면 2의 거듭제곱으로 축소합니다(마스크는 표준 채널보다 거칠게
  보일 수 있음). 17번째 이후 사용자 채널은 보관하지 않으며 해당 슬롯은 할당 없는 기본값으로 그립니다(슬롯 행에 「그리지 않음」 표시).

### Live Link로 Unity 머티리얼 값 사용

Live Link로 연 상대 머티리얼이 lilToon이면 독립 실행형 앱은 Unity가 요청에 기록한 해당 머티리얼 값으로
그 머티리얼의 텍스처 세트를 lilToon 외형으로 그립니다(전달 형식은 [LIVELINK.md](LIVELINK.md)). Unity는 읽기만 하며 머티리얼·텍스처·
임포트 설정을 변경하지 않습니다. lilToon 여부는 셰이더 이름만으로 정하지 않습니다(비슷한 이름의 셰이더를 lilToon으로 그리지 않음). 값에 lilToon 버전 값
`_lilToonVersion`이 있거나 셰이더가 lilToon 패키지(`jp.lilxyzw.liltoon`) 소속일 때만 해당합니다.

- 받는 항목: 셰이더 이름·버전·에셋 GUID·렌더링 순서, 모든 프로퍼티(색·수·벡터·정수. 텍스처의 타일링과 오프셋은
  `<名前>_ST`)와 키워드, 텍스처 프로퍼티별 이미지 파일 경로. 그리지 않은 슬롯(YoluPainter에서 그린 이미지로 표시하는 메인 컬러가 아닌,
  위 표의 슬롯)의 이미지는 독립 실행형 앱이 파일에서 읽습니다(변 길이를 최대 2048로 축소). Unity 안에만 있는 이미지(파일이 없는 생성물 등)는
  읽을 수 없으므로 슬롯 행에 이유를 표시합니다. Unity에서 값을 바꾸면 Live Link 창의 버튼으로 다시 보냅니다.
- 어떤 값으로 그리는가: Unity에서 온 값은 「Unity 값」으로 사용자 설정과 별도로 보관합니다(Undo 단계는 늘지 않음). 그릴 때는 Unity 값 위에
  항목에서 변경한 값을 겹칩니다. 항목에서 변경한 값은 이름에 「•」가 붙고 툴팁에 Unity 값이 나타납니다(렌더링 모드·윤곽선 활성화도 포함).
  구분의 「기본값으로 되돌리기」는 해당 구분을 Unity 값으로 되돌리고(기본 설정 구분은 렌더링 모드와 윤곽선 활성화도 포함),
  「Unity 값」 행의 「Unity에 맞추기」는 항목에서 변경한 값·렌더링 모드·윤곽선·종류 선택을 해제합니다(슬롯 할당은 남음).
  받은 세트의 종류는 항목에서 선택하지 않는 한 lilToon입니다. Unity 머티리얼이 lilToon이 아니게 되면 Unity 값을 해제합니다.
- 그린 이미지: 메인 컬러(`_MainTex`)는 Color 채널로 그립니다(내보내면 Unity의 이 슬롯으로 돌아가는 이미지). 그리지 않은 슬롯은
  항목에서 할당하지 않았으면 Unity 텍스처 파일로 그립니다. 새 세트의 기본 할당(노멀 맵 → Normal·발광 → Emission)은
  레이어가 해당 채널을 사용하기 전까지 할당하지 않은 것과 같으며, Unity 텍스처를 받았으면 그 텍스처로, Unity에서 빈 슬롯(이미지가 오지 않음·
  읽을 수 없음)이면 해당 슬롯의 기본 텍스처(흰색·검정·평평함)로 그립니다. 사용하지 않는 채널의 값(발광이면 검정)으로 읽지는 않습니다.
  (Unity는 빈 텍스처를 기본값으로 읽으므로 발광이 흰색으로 빛납니다.)
  - 세트마다 슬롯 순서(위 표의 순서)로 앞의 16장까지입니다. 17번째부터는 해당 슬롯의 기본 텍스처로 그리며 슬롯 행에
    「그리지 않음」으로 표시합니다(항목에서 앞쪽 슬롯을 할당하면 그만큼 뒤쪽 슬롯이 들어옴).
  - 2D 텍스처 배열이며 변 길이 1024·세트 하나당 최대 96 MiB(밉 포함)입니다. 3D 뷰의 메모리 예산 안에서 보관합니다. 현재 세트는 표준
    채널 이미지와 사용자 채널 배열을 제외한 나머지에 들어갈 때까지 2의 거듭제곱으로 축소하고, 다른 세트는 표준 채널 이미지·사용자 채널
    배열·받은 텍스처를 합쳐 들어갈 때만 보관합니다.
  - 값은 Unity가 읽은 그대로 보관합니다(미리 곱하지 않음). A를 불투명도가 아닌 다른 값으로 쓰는 텍스처(X를 A에 보관하는 노멀 맵의
    DXT5nm 등)도 A가 0인 곳의 색도 변하지 않습니다. 노멀 맵의 X는 lilToon과 같이 A × R로 읽습니다.
  - 모든 세트에서 받은 텍스처(픽셀)는 최대 256 MiB까지 보관합니다(초과한 텍스처는 보관하지 않고 알리며 해당 슬롯은 기본 텍스처로 그림).
- 저장: 설정의 「Unity에서 받은 머티리얼 값 저장」(기본값 켬)을 사용하여 `.ylp`의 `look.json`에 Unity 값을 넣습니다. 텍스처 픽셀은
  넣지 않습니다. 다시 열면 Unity 값으로 그리며, 텍스처는 Live Link 상대 기록(`livelink.json`)의 이미지 파일에서 다시 읽습니다.
  끄면 다음 저장에서 제외합니다. 수신은 편집이 아니므로 받기만 해서는 「저장하지 않은 변경」이 되지 않습니다.

Unity 값만으로 그린 비교(2026-10-05. 아래 「Unity lilToon과 비교」와 같은 장면·같은 Unity 이미지·같은 집계 방식): `tools/liltoon-reference.cs`는
장면마다 Unity 패키지의 Live Link가 보내는 항목(`LiveLinkMaterialValues`가 읽는 값과 그리지 않은 슬롯의 이미지)을 `link_<名前>.txt`에도 기록하며,
`compare_through_live_link`(수동 실행 테스트)는 사용자 설정을 기본값(표준)으로 둔 채 그 값만으로 독립 실행형 앱에서 수신했을 때와 같은 수신 외형을 만들어
그린 뒤 Unity 이미지와 비교합니다. 요청 파일에서 수신 외형까지의 경로는 `crates/yolu-app/tests/headless/livelink_files.rs` 테스트에서 통과시킵니다.

### Live Link로 Unity의 원래 텍스처를 맨 아래 레이어에 넣기

Unity 모델을 열면 독립 실행형 앱은 머티리얼마다 텍스처 세트를 만듭니다. 요청에 기록된 Color 전달 대상(독립 실행형 앱에서 그린 이미지를 보여주는 프로퍼티.
메인 컬러 등)의 이미지 파일을 읽고, 새로 만든 세트 맨 아래에 「원본 이미지」 레이어로 넣으므로 원래 텍스처 외형을 유지한 채 그 위에 그릴 수 있습니다.
내보내기(PNG·PSD)와 `.ylp`에는 일반 픽셀 레이어로 들어갑니다. 요청 형식과 상한은 [LIVELINK.md](LIVELINK.md)에 있습니다.

- 넣을 세트: Live Link 모델을 받을 때 새로 만든 세트와 아무것도 건드리지 않은 최초 세트(열거나 저장한 파일이 없고 그리지 않은
  최초 프로젝트의 첫 번째 세트)뿐입니다. 그린 세트·편집한 세트·사용자가 연 프로젝트의 세트에는 넣지 않습니다(그린 것을 알림 없이 바꾸지 않음).
- 최초 세트의 크기: 아무것도 건드리지 않은 최초 세트는 원본 이미지 크기로 다시 만든 문서에 넣습니다(4096 이미지를 기본 2048로 축소하지 않음). 크기는 새로 만드는
  세트와 같은 방식으로 정하며 이미지의 긴 변을 256~4096 범위의 2의 거듭제곱으로 맞춥니다(600 이미지는 1024, 8192 이미지는 4096). 같은 세트(이름·머티리얼 연결)를 유지하고 문서만 바꿉니다.
  다시 만든 문서에 원본 이미지가 들어가지 않으면(레이어 픽셀·한 번의 작업 예산) 현재 문서에 축소해 넣고 레이어 항목에 크기 조절 표시를 붙입니다.
  새 프로젝트 창에서 해상도를 선택해 만든 프로젝트는 선택한 크기를 유지하며 원본 이미지를 확대·축소해 넣습니다.
- 이미지가 없는 머티리얼·읽을 수 없는 이미지: 불투명 흰색(255, 255, 255, 255)의 「원본 이미지」를 넣습니다. Unity는 이미지 없는 슬롯을 기본 흰색으로 그리므로(머티리얼 색 × 흰색)
  연결한 순간 검게 되지 않습니다. Unity 안에만 있는 이미지(파일이 없는 생성물)도 흰색이며 읽을 수 없는 이미지는 이유를 알립니다.
- 이미지 크기가 세트와 다를 때: 세트 크기로 확대·축소합니다(축소는 박스 평균, 확대는 쌍선형. 알파로 가중치를 주므로 투명 픽셀의 RGB는 섞이지 않음).
  크기가 같으면 픽셀을 그대로 넣습니다(투명 픽셀의 RGB도 포함). 선형 텍스처(요청의 `srgb`가 거짓)는 Color 채널이 sRGB 픽셀을 보관하므로
  sRGB 픽셀로 변환해 넣습니다(외형은 바꾸지 않음).
- PSD 원본 이미지: Color 전달 대상의 이미지가 PSD(sRGB)이면 평탄화한 「원본 이미지」가 아닌 PSD 레이어 그대로 세트에 넣습니다([LIVELINK.md](LIVELINK.md)).
- 다시 보내기: 원본 이미지 파일(경로·수정 시각·크기·`srgb`)이 바뀌었으면 원본 이미지를 넣은 직후 그대로인(그리지 않음·아무것도 바꾸지 않음) 세트에는 새 원본 이미지를 다시 넣으며,
  건드린 세트는 바꾸지 않고 알립니다.
- Undo: 생성 직후의 초기화로 넣으므로 Undo 기록에 들어가지 않습니다(기록은 비어 있는 상태 유지. 레이어 삭제는 일반 작업으로 Undo로 되돌릴 수 있음). 변경 표시도 붙이지 않으므로
  받기만 해서는 「저장하지 않은 변경」이 되지 않습니다.
- 레이어 항목 표시: 선형에서 변환한 이미지와 확대·축소한 이미지는 레이어 오른쪽에 작은 표시가 붙고 툴팁에 이유가 나옵니다(원본 파일의 값 그대로이면 표시하지 않음).
  표시는 해당 세션 동안만 유지하며 저장하지 않습니다(다시 열면 일반 레이어).
- 상한: 이미지 변 길이 최대 8192·파일 최대 512 MiB(초과하면 축소하지 않고 거부하며 이유를 알림). 한 요청에서 읽는 원본 이미지 픽셀은 합계 최대 512 MiB입니다.
  문서의 레이어 픽셀·한 번의 작업 예산을 넘으면 넣지 않고 이유(예산)를 알립니다.
- 저장과 복원: 형식을 바꾸지 않습니다(원본 이미지와 흰색 모두 일반 픽셀 레이어이며 `.ylp` 버전을 올리지 않음). Unity 브리지(0.2.0)도 일반 레이어로 열 수 있습니다.

### Unity lilToon과 비교

`crates/yolu-app/tests/gui_view3d/liltoon_reference.rs`의 수동 실행 테스트는 합성 소재(구·판·시험용 인형)의 장면마다 3D 뷰 이미지와 Unity에서 같은 장면을 만드는 설명
(카메라·조명·환경광 SH·메시·텍스처·프로퍼티)을 기록합니다. `tools/liltoon-reference.cs`를 Unity(2022.3.22f1·lilToon 2.3.4)에서 실행해
같은 장면을 lilToon으로 그린 뒤 양쪽 차이를 셉니다. `tools/liltoon-reference.cs`는 실행하는 동안만 프로젝트의 색 공간을 Linear로 설정하고(VRChat과 같은 선형 색 공간. Unity는 즉시
선형으로 바뀌며(`QualitySettings.activeColorSpace`), 2026-10-05에 다시 촬영한 34장면의 이미지는 이전 이미지와 모든 픽셀이 같음. 같은 도구로 감마 상태에서 촬영하면
모든 장면에서 95% 이상의 픽셀이 다름), 장면이 사용하는 텍스처를 읽는
lilToon 기능만 켭니다(에디터의 OpenGL은 셰이더 텍스처 수에 상한이 있어 모두 켜면 셰이더가 깨짐. 장면을 `LILTOON_REF_ONLY`로 나눠 실행).
끝나면 둘 다 원래대로 되돌립니다. lilToon 설정 파일(`ProjectSettings/lilToonSetting.json`)이 없는 프로젝트에서는 복원할 수 없으므로 아무것도 바꾸지 않고 거부합니다.
촬영한 Unity 이미지(합성 소재만)는 `crates/yolu-app/tests/liltoon_unity/`에 두며 일반 테스트(`the_view_stays_within_the_measured_difference_from_unity_liltoon`)가
장면별 차이를 상한과 대조합니다. 상한은 아래 표의 값에 여유를 더한 것으로, 평균만 소프트웨어 렌더링(llvmpipe)과 GPU를 구분합니다(llvmpipe는
sRGB 텍스처를 읽을 때 선형 변환이 근사이므로 균일한 색에서도 1만큼 어긋나 llvmpipe에만 큰 상한을 허용. GPU 상한은
아래 표의 「실제 GPU GL」 값에 여유를 더한 것). GL 반투명은 감마에서 합성하므로 별도 상한입니다.

```sh
LILTOON_REF_DIR=<フォルダ> [LILTOON_REF_ONLY=<場面,…>] cargo test -p yolu-app --test gui_view3d liltoon_reference::export_and_render -- --ignored --nocapture
# Unity で tools/liltoon-reference.cs を回す（`__DIR__` をそのフォルダにする）
LILTOON_REF_DIR=<フォルダ> cargo test -p yolu-app --test gui_view3d liltoon_reference::compare -- --ignored --nocapture
# Live Link の値だけで描いて比べる（上の Live Link の節の表）
```

  21 → 4, emission_rim이 59 → 25, cutout·transparent의 「한쪽만」이 2,695·3,183 → 2,207)과 1을 넘는 색(bright_backlight_side의 95%가 24 → 1,
  matcap_hdr의 최대가 8 → 1)입니다.
- llvmpipe에서 평균이 1 가까이 오른 장면(rim·backface·anisotropy·emission 등)은 llvmpipe가 sRGB 텍스처를 읽을 때의 선형
  변환이 근사이므로 균일한 색에서도 1만큼 어긋나기 때문입니다(95%는 1 그대로). 실제 GPU GL에서는 같은 장면의 평균이 backface 0.00·rim 0.06·anisotropy 0.03·
  emission 0.31입니다. 실제 GPU에서 평균이 0.5를 넘는 것은 감마에서 합성하는 transparent 외에 cutout(0.60)·uv(0.74)·emission_rim(3.69)뿐입니다(가장자리 픽셀과 밉 단계 선택 방식).
- emission_rim과 uv 이외의 장면은 95%의 픽셀이 차이 1 이내입니다. 큰 차이는 줄무늬·체크무늬 이미지의 가장자리(양쪽 모두 삼선형이지만 밉 단계 생성 방식과 기울기에서
  단계를 선택하는 계산이 GPU마다 조금 다름), 마스크 경계, 윤곽선 껍질 가장자리 픽셀에서 나타납니다.
- emission_rim은 가는 줄무늬 이미지를 가장자리 방향 UV(림)로 읽는 장면으로, 가장자리에 가까울수록 기울기가 커져 밉 단계 선택 방식의 차이가 그대로 나타납니다(Unity의 줄무늬가 더 흐리고 옅음).
  읽는 UV와 기울기 수식은 lilToon과 같습니다.
- uv는 두 색의 체크무늬 이미지를 회전해 배열한 장면으로, 남은 차이는 색 경계 픽셀(밉 단계 선택 방식)입니다. UV 수식(Tiling·Offset·각도)은 같습니다.
- 머리카락 값 장면(bright_backlight_*)은 1을 넘는 역광 라이트 색(16.948. 선형으로 505.9)과 지향성 10의 값으로, 조명이 옆·뒤에서 오면 Unity에서도 가장자리가 흰색으로 날아갑니다.
  (3D 뷰와 같은 위치.) 역광 라이트는 조명과 시선이 마주 볼수록 강하며(지향성은 그 날카로움), 16.948 색에서는 강도가 1%에 못 미치는 곳도 흰색으로 날아갑니다(해당 장면의 색과 조명에서).
  이전 3D 뷰는 1을 넘는 색을 sRGB 수식 그대로 확장했기 때문에(16.948 → 약 790, Unity의 1.56배) 흰색 부분이 Unity보다 넓게 나타났습니다.
  (bright_backlight_side의 95%가 24.) 0.4.x까지의 Unity 브리지 기본 조명 방향 (−0.3, 0.65, −0.7)은 −Z 쪽에서 오므로 Unity에서 앞(+Z)을 향한 아바타를 얼굴 쪽에서
  보면 뒤쪽 조명(역광)이 됩니다(Rust 구현 기본값은 앞에서 오는 방향이므로 얼굴 쪽에서 보아도 역광이 되지 않음). 비교 장면과 3D 뷰 기본값은 그림자를 드리우지 않습니다. 그림자를 드리우는 조명에서의 역광 라이트는 측정하지 않았습니다. lilToon
  코드(`lil_common_frag.hlsl`의 `lilBacklight`)를 읽은 범위에서는 그림자를 드리우는 조명일 때 `_BacklightReceiveShadow`가 1이면 역광 강도에
  그림자를 받는 정도(`fd.attenuation`. 그림자 맵에서 빛이 가려진 곳은 0)를 곱해 그림자 속 역광을 없앱니다(3D 뷰도 같은 수식이며 그림자를 켰을 때의 그림자 맵을 사용).
- glitter·specular_toon의 최대 차이는 글리터 입자·툰 광택 가장자리의 몇 픽셀입니다. 글리터 난수(lilToon의 lilHashRGB4)와 입자 배열은 같습니다.
- wgpu GL(llvmpipe와 실제 GPU)로 그린 Rust 구현은 렌더 타깃을 sRGB 뷰로 만들 수 없어 반투명을 감마 값 그대로 합성하므로 transparent의 차이가 평균 28.19
  (실제 GPU 28.16)·95% 42가 됩니다(llvmpipe GL의 다른 장면은 평균이 위 표와 0.1 이내이며 95%는 uv가 3, 나머지는 같음). 「한쪽만」도
  5,623이며, 버튼 외에는 알파가 0에 가까운 옅은 가장자리 7열(3,416픽셀)입니다. 감마에서 합성하면 옅은 가장자리가 선형에서 합성하는 Unity보다 어두워져
  배경으로 간주하는 차이(3 이내)에 들어갑니다. 이전에는 6열(5,135)이었습니다. 감마 값으로 미리 곱한 8 bit 텍셀은 알파가 작은 곳에서 색 반올림이 크므로
  (알파 5/255 이하에서 곱하기를 되돌린 B는 230이 아닌 255) 옅은 가장자리가 약 1만큼 밝게 나타났습니다.
- 새로 그리도록 한 기능의 장면(rim_shade 이후)은 사용자 설정(항목 값)으로 그린 비교입니다. Live Link로 받은 값만으로 한 비교는 위 절에 있습니다.
- reflection_env는 환경광 반사를 끈 3D 뷰 이미지일 경우 Unity와의 차이가 평균 14.69·95% 31이 되는 장면입니다(반사 항목이 이미지에 영향을 줌).
  비교한 것은 균일한 환경의 수식(프레넬·매끄러움·금속성·반사율·색)이며 하늘·스튜디오 환경의 반사(반사 프로브 이미지와 흐림)는 비교하지 않았습니다.
- Unity와 비교하지 않은 항목(수식은 lilToon에서 옮겼지만 비교 장면이 없음): 메인 컬러 2nd·3rd의 MSDF·투명 모드·Cull·거리 페이드, 데칼 왼쪽만
  (오른쪽만과 좌우가 바뀐 같은 수식), 비등방성 반사의 MatCap 적용, 뒷면 UV 이동, 조명 방향 오버라이드, 글리터 색 텍스처,
  역광 라이트 색 텍스처, 그림자를 드리우는 조명에서 역광 라이트의 그림자 받기(`_BacklightReceiveShadow`).
- 비교한 것은 Linux Unity(OpenGL)입니다. Windows Unity(D3D11)와는 비교하지 않았습니다.
