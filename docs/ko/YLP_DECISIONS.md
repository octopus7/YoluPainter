# .ylp 형식을 정한 이유

.ylp 형식([YLP_FORMAT.md](YLP_FORMAT.md))의 구조를 선택한 이유, 채택하지 않은 대안, 보장 범위입니다.
0.4.x까지의 Unity 브리지 읽기 구현에 실제로 읽힌 기록은 `crates/yolu-io/tests/fixtures/*.unity.txt`에 있습니다.

## 버전 번호 부여 방식

정본 버전·내용 형식·종류 번호를 어떻게 배정했는지 설명합니다.
규칙 자체는 [YLP_FORMAT.md](YLP_FORMAT.md)의 「정본 버전 규칙」에 있습니다.

- **정본 버전 22~25와 27~30·32~35는 0.4.x까지의 Unity 브리지에 없는 기능을 사용하는 문서만 새 버전이 되도록 하기 위한 버전입니다.**
  0.4.x까지의 Unity 브리지 읽기 구현은 버전 번호만으로 파일을 건드리지 않고 거부합니다.
  정본 버전 22·23·24는 0.4.x까지의 Unity 브리지 `Runtime/Core` 읽기 구현에 실제로 읽힌 기록이 있습니다(`crates/yolu-io/tests/fixtures/*.unity.txt`).
- **내용 형식(7)은 올리지 않습니다.** 올리면 해당 기능을 쓰지 않는 세트까지 포함하여 파일 전체를 0.4.x까지의 Unity 브리지에서 열 수 없게 됩니다.
- **Unity 브리지가 0.5.0부터 .ylp를 처리하지 않더라도 버전 번호의 의미는 바꾸지 않습니다.**
  같은 버전 번호의 의미가 달라지면 이전 읽기 구현과 새 읽기 구현 모두 상대 문서를 잘못 읽습니다.
- **종류 번호 8~63(Generator)·3~63(조정)·7~63(필터)은 0.4.x까지의 Unity 브리지 번호 체계를 위해 비워 둡니다.**
  이 앱 전용 종류는 64부터 부여합니다.
- **정본 버전 31은 결번으로 두며 앞으로도 배정하지 않습니다.**
  - 읽기 구현은 버전 1~25·26·27~30·32~35만 읽고, 사이의 31은 의미를 정하지 않았으므로 범위에 넣지 않고 버전 번호로 거부합니다.
    정본 버전 25의 구조로 읽으면 의미 없는 버전의 문서를 아무 말 없이 읽게 됩니다.
  - 버전은 누적됩니다(상위 버전은 하위 버전의 모든 기능을 포함할 수 있음). 따라서 정본 버전 32·33의 읽기 구현은 나중에 31에 부여할 내용을 알 수 없습니다.
    31을 사용하면 이전 읽기 구현이 정본 버전 32·33 문서를 잘못 읽게 됩니다.
  - 새 기능의 버전은 이미 배포한 최상위 버전보다 높은 번호로 정합니다.

## Live Link 대상을 별도 항목으로 저장

- **상태 항목(채택).** 대상 기록은 픽셀의 의미를 바꾸지 않으므로 내용 형식을 올리면 Live Link를 사용했다는 이유만으로 이전 읽기 구현에서 파일 전체를 열 수 없게 됩니다.
  별도 항목이면 0.4.x는 알 수 없는 항목으로 바이트열을 보존하며(`Note::UnknownEntryKept`), 텍스처 세트는 키(Unity 머티리얼 GUID와 localFileId)를 그대로 사용하여 열 수 있습니다.
  잃는 것은 0.4.x에서 열려 있는 동안의 모델 표시뿐입니다.
- **포즈를 `pose.json`에 쓰는 대안(미채택).** `pose.json`은 프로젝트 모델 파일(`view.json`의 `standaloneModel`)의 포즈이며
  0.4.x는 모델 파일이 없는 문서를 저장할 때 `pose.json`을 제거합니다. 대상 포즈를 `livelink.json` 내부에 두면 0.4.x에서 다시 저장해도 잃지 않습니다.
- **값(lilToon 머티리얼 값)은 기록하지 않습니다.** 값은 `look.json`의 `received`에 있으며 저장 여부는 사용자 설정에 따릅니다. 같은 값을 2곳에 두면 설정에서 제외해도 남거나 서로 달라집니다.

## 외관 설정을 별도 항목으로 저장

선택한 이유와 채택하지 않은 대안:

- **별도 항목(채택).** 외관 설정은 픽셀 의미를 바꾸지 않으므로 정본 버전을 올리면 lilToon 외관을 사용했다는 이유만으로 Unity 0.2.0에서 파일 전체를 열 수 없게 됩니다.
  별도 항목이면 Unity 0.2.0에서 열 수 있으며 잃는 것은 외관 설정뿐입니다.
- **정본 버전을 올리고 정본 내부에 저장.** 위와 같은 호환성 손실이 큽니다.
- **view.json에 포함.** 0.4.x까지의 Unity 브리지 0.2.0은 view.json을 자체 항목(모델·선택한 채널·가시성)만으로 다시 쓰므로(`JsonUtility`), 0.4.x까지의 Unity 브리지에서 저장하면 사라지는 것은 마찬가지입니다.
  화면 상태와 저장할 문서의 외관 값을 같은 장소에 섞지 않습니다.

## 정본 버전 22 사용자 채널

Unity 0.2.0은 정본 버전 22를 「Unsupported archive version; source retained unchanged.」로 거부합니다.
C#의 `DocumentBinary.Read` / `ReadId` / `YlpFormat.Open`(`Runtime/Core`를 그대로 컴파일)에
Rust가 작성한 정본 버전 22를 읽힌 기록은
[`user-channels-v22.unity.txt`](https://github.com/YozoraKurage/YoluPainter/blob/main/crates/yolu-io/tests/fixtures/user-channels-v22.unity.txt)입니다.
외부 .ylp와 `project.json`은 읽을 수 있지만 열기 과정에서 세트의 정본을 읽을 때 거부합니다(모든 세트를 읽은 뒤에만 교체하므로 Unity 상태와 파일 모두 바뀌지 않음).
기록의 마지막 줄은 창(`TexturePaintWindow`)이 정본 읽기 실패에 붙이는 메시지를 읽기 구현의 예외에서 같은 형식으로 만든 것입니다.

선택한 이유와 채택하지 않은 대안:

- **버전 올리기(채택).** 0.4.x까지의 Unity 브리지가 새 기능을 추가할 때마다 사용한 규칙이며, 이전 읽기 구현은 버전 번호만으로 파일을 건드리지 않고 거부합니다.
  사용자 채널이 없는 문서는 정본 버전 21을 유지하므로 기존 문서와 Rust 구현에서 저장한 대부분의 문서를 Unity 0.2.0에서 열 수 있습니다.
- **모든 문서를 정본 버전 22(항목 0개 목록)로 저장.** Unity 0.2.0에서 Rust 구현으로 저장한 문서를 하나도 열 수 없게 됩니다. 사용자 채널을 쓰지 않는 사람까지 영향을 받으므로 채택하지 않습니다.
  잃는 점: 채널을 추가하면 정본 버전이 22로, 모두 삭제하면 21로 바뀝니다(저장할 때마다 현재 내용으로 결정).
- **내용 형식을 8로 변경.** Unity 0.2.0은 `ylp.json` 단계에서 파일 전체를 거부합니다. 사용자 채널이 없는 세트도 함께 영향을 받습니다. 내용 형식을 올리는 규칙(항목 추가·의미 변경)에 해당하지 않습니다.
- **사용자 채널 픽셀을 별도 항목에 두고 `document.utpaint`는 정본 버전 21 유지.** Unity 0.2.0은 알 수 없는 항목으로 목록에 표시만 하고 그대로 열며
  저장하면 해당 항목을 버립니다. 사용자 채널을 조용히 잃는 저장이 가능해지므로 「지원하지 않는 정보를 알림 없이 버리지 않기」에 어긋납니다.
- **정본 버전 21을 유지하며 번호 6~63 허용.** Unity 0.2.0은 `Invalid or duplicate channel`이라는 일반 메시지로 거부하여 새 버전이 필요함을 알리지 못하고 손상과 구별할 수 없습니다.
  이름·종류·색 공간·기본값을 저장할 곳도 없습니다.
- **`ylp.json`에 기능 플래그 추가.** Unity 0.2.0은 알 수 없는 키를 건너뛰므로 효과가 없습니다.

이행: 정본 버전 1~21은 그대로 읽을 수 있으며(사용자 채널 목록은 비어 있음), core를 통해 저장하면 정본 버전 21이 됩니다(사용자 채널이 있으면 정본 버전 22).
정본 버전 22를 읽는 Rust 구현은 버전 21까지의 읽기 규칙을 바꾸지 않습니다. 정본 버전 22에서 21로 되돌리려면 사용자 채널을 삭제하고 다시 저장합니다.

보장 범위와 잃는 점:

- 세트 하나라도 정본 버전 22이면 Unity 0.2.0에서는 해당 .ylp 전체를 열 수 없습니다(세트별 열기 불가). Unity에서 열어야 한다면 사용자 채널을 삭제한 파일을 저장합니다.
  정본 버전 22를 21로 바꾸는 이행 기능은 Unity 측에 없습니다.
- 정본 버전 22의 의미는 [YLP_FORMAT.md](YLP_FORMAT.md)의 「헤더」 절(`user_channels`)에 고정합니다.
  0.4.x까지의 Unity 브리지가 정본 버전 22 이후를 다른 의미로 사용하려면 같은 형식을 사양으로 정해 맞춰야 합니다(버전 번호가 어긋나면 양쪽 구현 모두 상대 문서를 잘못 읽음).
- 사용자 채널에는 C# 쓰기 구현이 없습니다. 합성은 표준 채널까지 포함하여 core의 f32 합성 공식을 기준으로 하며 Unity 0.2.0의 C# 합성과 픽셀 일치를 보장하지 않습니다(보장은 읽기 결과와 왕복 바이트 일치 범위).
  합성 PNG(`composite/<チャンネル>.png`)는 표준 채널만 기록하며 사용자 채널분은 기록하지 않습니다.
- 보장 범위는 `Runtime/Core`의 읽기 구현(`DocumentBinary`·`YlpFormat`) 결과까지입니다. Unity 창(EditorWindow) 조작 결과는 포함하지 않습니다.

## 정본 버전 23 노이즈와 그런지

평가 규칙: 위치(Position) 맵을 사용할 수 있는 동안에는 위치를 기준으로 3D 평가합니다(UV 아일랜드 이음새에서 무늬가 어긋나지 않음).
2D 무늬 프리셋(긁힌 자국·지문·직물)은 위치 공간에서 자동으로 트라이플래너를 사용합니다(방향 맵 필요, 채우기 투영과 같은 가중치).
위치 맵을 사용할 수 없으면(없음·오래됨·크기 불일치·핀 불일치·바운딩 박스 0) 입력을 그대로 통과시키지 않고 UV 공간으로 대체하며 이유를 `BoundGenerator::fallback`과
`Document::fallback_effect_list`로 반환합니다(값은 생성됨. UV에서는 x·y 격자를 주기로 감아 가장자리 이음새가 없으며 회전은 적용되지 않음).
공식은 + − × ÷ sqrt floor와 정수만 사용하며(sin·cos·pow·exp 미사용), 같은 설정·시드·맵이라면 스레드 수·영역·블록 크기와 무관하게 같은 바이트를 만듭니다.

Unity 0.2.0은 정본 버전 23을 버전 22와 마찬가지로 「Unsupported archive version; source retained unchanged.」로 거부합니다.
C#의 `DocumentBinary.Read` / `ReadId` / `YlpFormat.Open`(`Runtime/Core`를 그대로 컴파일)에
Rust가 작성한 정본 버전 23을 읽힌 기록은
[`procedural-v23.unity.txt`](https://github.com/YozoraKurage/YoluPainter/blob/main/crates/yolu-io/tests/fixtures/procedural-v23.unity.txt)입니다(정본은
[`procedural-v23.utpaint`](https://github.com/YozoraKurage/YoluPainter/blob/main/crates/yolu-io/tests/fixtures/procedural-v23.utpaint)).

선택한 이유와 채택하지 않은 대안:

- **버전 올리기(채택).** 사용자 채널과 같은 방식이며 이전 읽기 구현은 버전 번호만으로 파일을 건드리지 않고 거부합니다. 이 종류를 쓰지 않는 문서는 정본 버전 21(사용자 채널이 있으면 22)을 유지하므로
  Unity 0.2.0에서 열 수 있는 범위는 바뀌지 않습니다.
- **정본 버전 21을 유지하며 종류 64·65 허용.** 버전 번호가 어긋나면 양쪽 구현 모두 상대 문서를 잘못 읽습니다(정본 버전 22 절과 같은 이유).
  0.4.x까지의 Unity 브리지가 나중에 64 이후를 다른 의미로 사용하면 같은 정본 버전 21 파일의 의미가 나뉩니다.
- **기존 종류(EdgeWear·Dirt)의 「덧씌울 노이즈」 확장.** 같은 종류의 픽셀이 0.4.x까지의 Unity 브리지와 달라지고 C# 정답과의 전체 바이트 일치(338개 사례)가 깨집니다.
- **`.ylsmart` 형식 1에 포함.** 형식 1은 0.4.x까지의 Unity 브리지와 공유하므로 정본 버전 23 조각이 들어 있는 .ylp를 해당 Unity 브리지가 에셋까지 포함하여 열 수 없게 됩니다.
  사용자 채널과 마찬가지로 이 종류를 포함한 소재는 `SmartFile::from_core`가 이유와 함께 거부합니다(`REFUSAL_RUST_GENERATORS`).
  잃는 점: 노이즈·그런지를 쓰는 레이어를 「레이어에서 저장」으로 에셋에 넣을 수 없습니다(함께 제공하는 소재는 코드로 만든 core 소재를 에셋의 「내장」에 나열하므로 영향 없음).
  `.ylsmart` 형식 2를 정하면 포함할 수 있습니다.

이행: 정본 버전 1~22는 그대로 읽을 수 있습니다. 이 종류의 단계를 삭제하고 다시 저장하면 정본 버전 21(사용자 채널이 있으면 22)로 돌아갑니다.

보장 범위와 잃는 점:

- 세트 하나라도 정본 버전 23이면 Unity 0.2.0에서 해당 .ylp 전체를 열 수 없습니다. Unity에서 열어야 한다면 노이즈·그런지 단계를 삭제하거나 베이크한 파일을 저장합니다.
- 픽셀은 Rust 공식으로 생성되며 대응 C# 구현은 없습니다. 외부 정답 없이 `tests/procedural-index.txt`(구현을 고정하는 해시, 회귀 고정값)와 속성 테스트(결정성·이음새·취소·한도·검사)로 보호합니다.
  공식을 바꾸면 기존 문서의 외관이 달라지므로 변경 시 알고리즘 버전을 올리고 이전 공식을 남깁니다.
- 수치 일치는 Linux x86_64에서 확인한 범위입니다. Windows에서는 아직 측정하지 않았습니다.
- 보장 범위는 `Runtime/Core` 읽기 구현(`DocumentBinary`·`YlpFormat`) 결과까지입니다. Unity 창(EditorWindow) 조작 결과는 포함하지 않습니다.

## 정본 버전 25 그라데이션 맵의 색상 혼합

Unity 0.2.0은 정본 버전 25를 버전 22~24와 마찬가지로 버전 번호만으로 거부합니다(0.4.x까지의 Unity 브리지 `DocumentBinary.IsReadable`은 1~21만 읽으며

선택한 이유와 채택하지 않은 대안:

- **사용하는 문서만 버전 올리기(채택).** 색조 보정을 쓰지 않는 문서는 21~23, 색조 보정만 쓰면 24를 유지합니다. 이전 읽기 구현에서 열 수 있는 범위는 넓어지지 않습니다.
- **채우기 그라데이션 램프에도 색상 혼합 추가.** 해당 램프 구조는 0.4.x까지의 Unity 브리지와 공유하므로(정본 버전 21) 의미를 바꿀 수 없습니다.

- **정본 버전 24를 유지하며 색상 혼합 필드 추가.** 정본 버전 24의 그라데이션 맵을 기록하는 기존 구현과 버전 번호는 같지만 구조는 다른 파일이 생겨 양쪽 모두 상대 파일을 잘못 읽게 됩니다.

이행: 정본 버전 1~24는 그대로 읽을 수 있습니다. 색상 혼합을 해제하고 다시 저장하면 정본 버전 24(다른 기능이 없으면 21~23)로 돌아갑니다.

보장 범위와 잃는 점:

- 그라데이션 맵 하나라도 색상 혼합을 사용하면 Unity 0.2.0에서 해당 .ylp 전체를 열 수 없습니다.

## 정본 버전 29 포인트 그라데이션과 이미지 읽기

채우기 레이어의 채널별 포인트 그라데이션(모델 공간 또는 UV 공간의 점 색상을 거리 제곱의 역수 가중치로 혼합)과 채우기 이미지별 이방성 필터 켜기/끄기(기본값 켜짐,
끈 이미지만 `false`)를 추가한 버전입니다. 레이어 속성 플래그(1바이트)는 비트 6까지 모두 사용했으므로 비트 7을 「확장 속성 플래그 `attributes_ext`(int)가 이어짐」으로 지정하고
포인트 그라데이션은 확장 플래그의 비트 0에 둡니다. 확장 플래그는 잠금 바로 뒤에 기록하며 0이면 기록하지 않습니다.

선택한 이유와 채택하지 않은 대안:

- **확장 속성 플래그를 int로 추가(채택).** 속성 플래그의 빈자리는 비트 7뿐이며 포인트 그라데이션에 쓰면 다음 기능을 넣을 수 없습니다.
  int 확장 플래그에는 31개 비트가 남으며 사용하지 않는 레이어는 기존처럼 1바이트도 늘지 않습니다.
- **레이어 종류마다 같은 비트의 의미 변경.** 포인트 그라데이션은 채우기 레이어 전용이므로 다른 레이어 기능과 비트 6을 공유할 수 있습니다.
  그러나 경로 목록은 래스터와 채우기 레이어 모두에서 사용하므로 공유할 수 없고 읽기 검사도 종류별로 나뉘어 어긋나기 쉽습니다.
- **레이어마다 bool 추가.** 사용하지 않는 레이어까지 1바이트씩 늘어납니다.

이행: 정본 버전 1~28은 그대로 읽을 수 있습니다(정본 버전 29는 버전 27·28의 내용도 읽고 쓸 수 있음). 포인트 그라데이션을 삭제하고 이미지 이방성을 다시 켜서 저장하면 다른 기능에 따라 결정되는 버전으로 돌아갑니다.
정본 버전 32도 정본 버전 29의 내용을 읽고 쓸 수 있습니다.

보장 범위와 잃는 점:

- 세트 하나라도 포인트 그라데이션 또는 이방성을 끈 이미지를 사용하면 독립 실행형 0.4.x와 Unity 0.2.0에서 해당 .ylp 전체를 열 수 없습니다(버전 번호만으로 거부).
- `.ylsmart` 형식 1에는 포함하지 않습니다(`REFUSAL_POINT_GRADIENTS`).
- 정본 버전 29는 이미지마다 `anisotropic` bool을 기록합니다(켜진 상태의 이미지도 기록, 정본 버전 28까지는 기록하지 않음).

## 정본 버전 30 텍스트 레이어

텍스트 레이어를 추가한 버전입니다. 래스터 레이어에 텍스트 값(문자열·글꼴·크기·색상·줄 간격·자간·정렬·위치·회전·줄바꿈 너비)을 두고 레이어의 Color 픽셀은 해당 값으로 그린 결과를 다른 레이어와 같은 타일로 기록합니다.
값은 레이어 끝(경로 목록 뒤)의 `text` 블록에 두며 확장 속성 플래그(`attributes_ext`)의 비트 1로 이어짐을 표시합니다.

선택한 이유와 채택하지 않은 대안:

- **사용하는 문서만 버전 올리기(채택).** 정본 버전 22~25와 같은 방식이며 텍스트 레이어가 없는 문서는 이전 버전을 유지합니다. 정본 버전 25까지의 읽기 구현(독립 실행형 0.4.x)은
  「`.version の値 30 は未対応または範囲外です`」(분할 정본이면 「분할 정본 내부 버전 30은 지원하지 않습니다」)로,
  Unity 0.2.0은 버전 번호만으로 「Unsupported archive version; source retained unchanged.」라고 응답하며 파일을 건드리지 않고 거부합니다.
- **레이어 종류를 래스터(`kind` 0)로 유지하고 텍스트 값 추가(채택).** 경로 레이어(정본 버전 8·10)와 같은 방식으로 픽셀은 항상 타일에 있으므로
  텍스트를 모르는 처리(합성·내보내기·PSD)도 기존 레이어처럼 처리할 수 있습니다. 종류 값(4 등)을 추가하면 0.4.x까지의 Unity 브리지 레이어 종류와 같은 번호의 의미가 달라질 수 있으므로 번호를 비워 둘 수 있습니다.
  잃는 점: 종류 값만으로는 텍스트 레이어를 구분할 수 없습니다(확장 속성 플래그 비트 1 확인 필요).
- **글꼴 파일을 포함하지 않기(채택).** 글꼴 라이선스가 문서에 임베드하여 배포하는 것을 항상 허용하지는 않습니다. 문서는 이름(내장 글꼴) 또는
  경로·내용 SHA-256·패밀리 이름·PostScript 이름·굵기·기울임 여부(파일 글꼴)만 가집니다. 잃는 점: 글꼴이 없는 환경에서 열면 텍스트 값을 편집할 수 없습니다(픽셀은 그대로 보이며 내보내기도 달라지지 않음).
- **이름과 굵기도 저장(채택).** 경로와 SHA-256만으로는 글꼴 폴더가 다른 PC에서 같은 글꼴을 찾을 수 없습니다.
  PostScript 이름은 스타일 하나를 가리키며 이름이 없거나 중복되는 글꼴을 위해 패밀리 이름과 굵기·기울임 여부도 저장합니다. 스타일 이름(name의 17·2번)은 언어별로 달라 검색 단서로 쓰기 어려우므로 저장하지 않습니다.
- **픽셀도 저장(채택).** 열 때 다시 그리면 글꼴이 없는 환경에서 아무것도 보이지 않고 배치·렌더링 공식을 바꾸면 이전 문서의 외관도 바뀝니다. 잃는 점: 텍스트 레이어만큼 파일이 커집니다(문자가 덮는 영역의 타일만).
- **문자열 상한을 4096바이트로 설정.** 정본 문자열 상한(4096바이트)과 같게 정해 문자열 필드 읽기·쓰기를 그대로 유지했습니다.

이행: 정본 버전 1~29는 그대로 읽을 수 있습니다(정본 버전 30은 버전 27~29의 내용도 읽고 쓸 수 있음). 텍스트 레이어를 래스터화(값 제거)하거나 삭제한 뒤 저장하면 다른 기능에 따라 결정되는 버전으로 돌아갑니다.
정본 버전 32도 정본 버전 30의 내용을 읽고 쓸 수 있습니다(이음새 설정을 끈 문서의 텍스트 레이어는 정본 버전 32로 기록).

보장 범위와 잃는 점:

- 세트 하나라도 정본 버전 30이면 독립 실행형 0.4.x와 Unity 0.2.0에서 해당 .ylp 전체를 열 수 없습니다. 열어야 한다면 텍스트 레이어를 래스터화하여 저장합니다.
- 그린 픽셀은 이 앱의 배치·렌더링 공식으로 만든 것이며 다른 앱의 같은 글꼴·같은 크기 문자와 픽셀까지 일치한다고 주장하지 않습니다.
- `.ylsmart` 형식 1에는 포함하지 않습니다. 스마트 머티리얼로 만든 텍스트 레이어는 픽셀만 남습니다(알림 제공).
- PSD 내보내기는 텍스트 레이어를 픽셀 레이어로 기록합니다(PSD 텍스트 레이어는 기록하지 않음). PSD 가져오기의 텍스트 레이어는 기존처럼 픽셀로 읽습니다.

## 정본 버전 32 이음새 설정

문서 설정 「필터가 UV 이음새를 가로지름」(`filter_seams`)입니다. 켜져 있고 모델의 UV 토폴로지가 있는 문서에서는 레이어 필터의 이웃 영역 처리 단계(흐림·선명하게 등)가
아일랜드 바깥 띠를 이음새 반대편 아일랜드의 픽셀로 채운 뒤 평가하고 아일랜드 바깥은 단계 입력으로 되돌립니다. 합성 픽셀이 달라지므로 정본 헤더 필드로 정했습니다. 기본값은 켜짐이며 켜진 문서는 버전을 올리지 않습니다(정본 버전 21~25·27·28 유지).
설정을 끈 문서만 정본 버전 32가 됩니다.

선택한 이유와 채택하지 않은 대안:

- **설정을 끈 문서만 버전 올리기(채택).** 기본값인 켜짐은 필드를 쓰지 않고 표현할 수 있으므로 사용하지 않는 문서의 버전은 바뀌지 않습니다. 이전 읽기 구현(0.4.x·Unity 0.2.0)은 원래 이음새를 가로지르지 않으므로
  켜진 문서를 열어도 잘못 읽지는 않습니다(외관은 0.4.x 평가 결과).
- **상태 항목(`look.json` 같은 별도 항목)으로 저장.** 이전 읽기 구현에서 열 수는 있지만 합성 픽셀을 바꾸는 설정을 0.4.x까지의 Unity 브리지가 저장 시 버리는 곳에 두게 됩니다.
  해당 항목이 없어지면 꺼진 문서가 알림 없이 켜짐으로 돌아가 외관이 달라집니다.
- **레이어별로 저장(필터 단계 필드).** 모델 이음새는 문서당 하나이므로 레이어마다 다르게 설정하면 같은 가장자리에서도 레이어에 따라 이음새가 나타납니다. 단계 필드를 늘리면 사용하지 않는 문서의 필터 구조도 바뀝니다.

이행: 정본 버전 1~28은 그대로 읽으며 이음새 설정은 켜짐입니다. 설정을 다시 켜고 저장하면 다른 기능으로 결정되는 버전(21~25·27·28)으로 돌아갑니다.
정본 버전 32의 내용은 버전 28(0.5.0 효과)의 구조를 포함하므로 버전 28 단계가 있는 문서는 이음새 설정을 끄는 것만으로 28에서 32로 올라갑니다.

보장 범위와 잃는 점:

- 세트 하나라도 설정을 꺼 두면 0.4.x 독립 실행형과 Unity 0.2.0에서 해당 .ylp 전체를 열 수 없습니다(버전 번호만으로 파일을 건드리지 않고 거부).
- 필드에는 설정만 기록하며 띠의 복사본(모델·해상도별로 재생성 가능)은 기록하지 않습니다. 모델이 없는 문서는 켜져 있어도 2D 평가를 유지합니다.

## 정본 버전 33 베이킹 우선순위

겹치는 UV(같은 텍셀을 삼각형 2개 이상이 덮음)에서 어느 삼각형이 텍셀을 베이크할지 결정하는 방식(`bake_priority`)입니다.
텍스처 세트별 문서 설정이며 결정 방식에 따라 베이크 값이 바뀌고 수동으로 선택한 아일랜드(삼각형 번호)는 모델 형상과 연결되므로 정본 헤더 필드로 정했습니다.
기본값(번호가 작은 삼각형·제외 없음·수동 선택 아일랜드 없음)은 필드 없이 표현할 수 있어 기본 문서는 버전을 올리지 않습니다(정본 버전 21~25·27~30·32 유지). 변경한 문서만 정본 버전 33이 됩니다.

선택한 이유와 채택하지 않은 대안:

- **변경한 문서만 버전 올리기(채택).** 0.4.x와 Unity 0.2.0의 읽기 구현은 원래 번호가 작은 삼각형으로 베이크하므로 기본 문서는 이전 읽기 구현에서 열어도 의미가 같습니다.
- **상태 항목(`look.json` 같은 별도 항목)으로 저장.** 이전 읽기 구현에서 열 수는 있지만 베이크 값을 바꾸는 설정을 0.4.x까지의 Unity 브리지가 저장 시 버리는 곳에 두게 되어
  항목이 없어지면 결정 방식이 알림 없이 기본값으로 돌아갑니다(다시 베이크하면 값이 바뀜).
- **베이크된 메시 맵의 출처 키만으로 표현.** 키에는 결정 방식의 SHA-256만 들어가며(`;owner=…;outside=skip;islands=<SHA-256>`, 기본값이면 아무것도 추가하지 않음)
  수동 선택 아일랜드 번호는 복원할 수 없습니다. 맵을 삭제하면 설정도 사라집니다.
- **아일랜드를 UV 좌표로 기억.** UV가 정확히 겹친 미러 양쪽은 UV 좌표로 구별할 수 없습니다. 삼각형 번호와 모델 지문(`MeshBakeInput` 토폴로지의 SHA-256)으로 기억하고
  지문이 다른 모델은 베이킹 전에 거부합니다(알림 없이 다른 아일랜드를 제외하지 않음).

이행: 정본 버전 1~32는 그대로 읽으며 베이킹 우선순위는 기본값입니다. 기본값으로 되돌려 저장하면 다른 기능으로 결정되는 버전(21~25·27~30·32)으로 돌아갑니다. 정본 버전 33은 버전 27~32의 내용도 읽고 쓸 수 있습니다.

보장 범위와 잃는 점:

- 세트 하나라도 결정 방식을 바꾸면 0.4.x 독립 실행형과 Unity 0.2.0에서 해당 .ylp 전체를 열 수 없습니다(버전 번호만으로 파일을 건드리지 않고 거부).
- 수동 선택 아일랜드는 삼각형 수·UV·슬롯·렌더러가 같은 모델에서만 사용할 수 있습니다. 모델을 다시 만들었다면 목록을 지우고 다시 선택합니다.
- 베이크 맵의 값 계산(노멀·AO 등)은 바꾸지 않습니다. 달라지는 것은 겹치는 텍셀에 어느 삼각형의 값을 사용할지와 베이크하지 않는 아일랜드의 텍셀이 비게 되는 것뿐입니다.

<a id="正本のバージョン-34-パスのブラシのアンチエイリアス"></a>

## 정본 버전 34 경로 브러시 안티앨리어싱

경로 브러시(2D·3D 경로의 `brush` 블록) 가장자리의 안티앨리어싱 단계입니다(`anti_alias` byte, 0 없음·1 약·2 중·3 강).
경로는 저장한 설정으로 다시 그리므로 단계에 따라 픽셀이 달라지는 설정을 정본 경로에 저장했습니다. 없음(현재 공식)은 필드 없이 표현할 수 있으므로 없음 경로만 있는 문서는 버전을 올리지 않습니다(다른 기능으로 결정되는 버전 유지).
없음이 아닌 경로가 하나라도 있는 문서만 정본 버전 34가 됩니다.

이행: 정본 버전 1~33은 그대로 읽으며 경로 브러시는 없음입니다. 정본 버전 34는 버전 27~33의 내용도 읽고 쓸 수 있습니다.

보장 범위와 잃는 점:

- 세트 하나라도 없음이 아닌 경로가 있으면 0.5.x까지의 독립 실행형에서 해당 .ylp 전체를 열 수 없습니다(버전 번호만으로 파일을 건드리지 않고 거부).
  0.4.x까지의 Unity 브리지도 버전 번호로 거부합니다(0.5.0부터의 Unity 브리지는 .ylp를 열지 않음). 열려면 해당 경로를 없음으로 되돌리고 다시 저장합니다.
- 새 경로는 현재 브러시의 단계를 사용합니다(앱 기본 브러시는 중). 따라서 이 앱에서 새 경로를 만든 문서는 대개 정본 버전 34가 됩니다.
- 단계 공식(띠 너비·작은 dab의 농도)은 이 앱의 브러시 공식입니다([BRUSH.md](BRUSH.md)의 「안티앨리어싱」).

<a id="正本のバージョン-35-定規"></a>

## 정본 버전 35 자

자는 그릴 때 맞출 대상(직선자·평행선·동심원·원근)과 대칭(대칭자)이며 레이어(그룹 포함)에 붙여 정본에 저장했습니다.
(레이어 확장 속성 플래그의 비트 2, 레이어 끝의 `ruler_count`·`rulers[i]`.) 경로의 2D 대칭에도 각도가 있는 선대칭(`canvas_symmetry`의 `mode` 5·`angle`)을 추가했습니다.
자가 있는 레이어 또는 선대칭 2D 경로가 있는 문서만 정본 버전 35가 되며 나머지는 이전 버전을 유지합니다(자를 모두 삭제하고 다시 저장하면 자가 없을 때와 같은 바이트열로 돌아감).

선택한 이유와 채택하지 않은 대안:

- **레이어에 붙여 정본에 저장(채택).** 자는 레이어와 함께 실행 취소·복제·병합·삭제되는 본체 값이며 그릴 레이어에서 보이는 자가 스냅 대상과 대칭을 결정합니다.
- **자를 상태 항목(예: `sets/<ID>/rulers.json`)으로 분리하고 정본 버전 유지.** 이전 읽기 구현이 알 수 없는 항목을 바이트열로 보존하므로 열 수 있고 자도 남습니다.
  채택하지 않은 이유: (1) 이전 읽기 구현에서 레이어를 삭제하고 저장하면 남은 항목이 없는 레이어를 참조합니다(다시 열 때 조용히 버리거나 다른 곳에 붙일 수밖에 없음).
  (2) 상태 항목은 「읽지 못하면 기본값으로 복원」하는 종류여서 작업 일부(대칭으로 그릴 준비)를 알림 없이 잃을 수 있습니다.
  (3) 레이어 복제·병합의 실행 취소와 두 위치의 기록을 일치시키는 작업이 늘어납니다.
- **2D는 문서 픽셀, 3D는 모델 공간에 배치.** 2D는 2D 경로와 같은 공간이며 크기 변경 시 함께 이동합니다. 3D는 투영 상자·데칼과 같은 공간이며 모델 삼각형에 연결하지 않습니다.
  (3D 경로와 달리 표면상의 점이 아니며 다른 모델로 바꿔도 좌표 그대로 남음.) 채택하지 않은 대안: 3D 자를 위치·오일러 각·크기로 보관하기(모양 기즈모에는 맞지만
  직선자·원근의 두 점을 표현하기에 적합하지 않고 2D와의 대응도 끊어짐).
- **경로 대칭은 자를 참조하지 않고 경로 안에 자체 저장.** 경로 픽셀은 저장된 설정으로 다시 그리는 값이므로 자를 움직이면 경로 픽셀까지 바뀌게 됩니다. 선대칭에는 각도가 필요하므로 `mode` 5를 추가했습니다.
  채택하지 않은 대안: 경로 대칭을 없애고 자를 따르게 하기.

이행: 정본 버전 1~34는 그대로 읽으며 자는 없고 경로 대칭은 1~4를 유지합니다. 정본 버전 35는 버전 27~34의 내용도 읽고 쓸 수 있습니다.
이전 버전 파일에는 자와 대칭이 저장되어 있지 않으므로 옮길 항목은 없습니다.

보장 범위와 잃는 점:

- 자가 하나라도 있는 .ylp는 0.5.x까지의 독립 실행형에서 열 수 없습니다(버전 번호만으로 파일을 건드리지 않고 거부). 자만 버리고 여는 방식은 제공하지 않습니다.
  0.4.x까지의 Unity 브리지도 버전 번호로 거부합니다(0.5.0부터의 Unity 브리지는 .ylp를 열지 않음). 열려면 자를 모두 삭제하고 선대칭 경로를 세로·가로·양쪽·방사형으로 되돌린 뒤 저장합니다.
- 3D 자는 포즈가 적용된 모델에서 본을 따라 움직이지 않습니다(현재 3D 대칭과 같은 공간).
- 스마트 머티리얼(`.ylsmart`)은 자를 포함하지 않습니다. 레이어를 복사하여 저장하면 자를 제거하고 이를 알립니다.
- 병합은 제거할 레이어의 자를 모두 결과 레이어로 옮깁니다. 결과가 64개를 넘을 때만 아무것도 바꾸지 않고 거부합니다.

## 정본 버전 36 레이어 세트

레이어 세트는 텍스처 세트 내부의 이름 있는 레이어 묶음이며 출력 할당(채널별 최종 결과를 가져올 레이어 세트)과 함께 정본 헤더에 두고
레이어에는 소속 레이어 세트 ID를 둡니다(레이어 끝의 `set`). 레이어 세트가 하나이고 이름이 비어 있으며 모든 채널이 그곳에 할당된 문서는
필드 없이 표현할 수 있으므로 이전 버전으로 기록합니다(기존 문서는 모두 이 형태이므로 이전 앱에서 열 수 있음).

선택한 이유와 채택하지 않은 대안:

- **레이어 목록은 하나로 유지하고 레이어에 소속 정보 추가(채택).** 순서 변경·부모 자식·기록·병합에 같은 레이어 세트 내부라는 조건만 더하면 되며
  레이어 필드도 ID 하나만 늘어납니다.
- **레이어 트리를 레이어 세트별로 분리(`layers`를 `layer_sets[i].layers`로 변경).** 순서 변경·기록·병합을 모두 수정해야 하며 이전 버전과 같은 구조로 기록하는 경로도 이중화됩니다.
- **채널을 레이어 세트 하나에 배분(레이어 세트가 채널 집합을 가짐).** 출력 할당을 한 가지로 고정한 특수한 경우이며
  같은 채널의 서로 다른 안을 두 레이어 세트에 두고 비교할 수 없습니다.
- **모든 채널의 할당 기록.** 빠진 채널을 조용히 기본값으로 처리하지 않고 열기를 거부할 수 있도록 했습니다.

이행: 정본 버전 1~35는 그대로 읽으며 이름이 빈 레이어 세트 하나에 모든 레이어와 채널이 들어갑니다. 정본 버전 36은 버전 27~35의 내용도 읽고 쓸 수 있습니다.

보장 범위와 잃는 점:

- 레이어 세트가 2개 이상인 .ylp(이름을 붙이거나 할당을 바꾼 경우 포함)는 0.6.x까지의 독립 실행형에서 열 수 없습니다(버전 번호만으로 파일을 건드리지 않고 거부).
  열려면 레이어 세트를 하나로 만들고 이름을 비우며 모든 채널을 그 세트에 할당한 뒤 다시 저장합니다.
- 이전 버전으로 기록하는 형태의 레이어 세트 ID는 저장하지 않습니다(열 때마다 새 ID 생성).
- 효과는 해당 레이어의 레이어 세트 안에서만 읽습니다. 다른 레이어 세트의 Anchor를 읽는 참조는 사라진 Anchor와 마찬가지로 입력을 통과시킵니다.

## 내용 형식 9 여러 머티리얼의 세트

하나의 텍스처 세트가 머티리얼 2개 이상을 가질 수 있도록 했습니다(같은 텍스처에 여러 머티리얼의 면을 그림). 머티리얼이 2개 이상인
세트만 `project.json`의 `sets[].materials`(키 목록)로 기록하고 `material`은 쓰지 않습니다. 머티리얼이 하나인 세트는 기존 `material`을 유지합니다.

선택한 이유와 채택하지 않은 대안:

- **사용하는 파일만 내용 형식 9로 변경(채택).** 내용 형식 8(이름을 붙여 저장한 선택 영역)과 같은 방식입니다. 모든 세트가 머티리얼 하나만 가진
  파일은 기존과 같은 7·8로 기록하므로 0.6.x까지의 앱에서도 열 수 있습니다. 2개 이상을 사용하는 파일은 내용 형식 8까지의 읽기 구현이 작성한 앱을
  함께 표시하고 파일을 건드리지 않은 채 거부합니다.
- **항상 내용 형식 9로 기록.** 여러 머티리얼을 사용하지 않는 파일도 0.6.x까지의 앱에서 열 수 없게 됩니다.
- **`material`을 남기고 추가 머티리얼을 `extraMaterials` 같은 별도 키에 기록(내용 형식 유지).** 이전 읽기 구현은 알 수 없는 키를 건너뛰므로
  첫 머티리얼만 있는 세트로 조용히 열고 다시 저장하면 나머지 머티리얼 연결이 사라집니다.
- **키가 없는 세트(머티리얼 없음)를 빈 `materials` 목록으로 기록.** 연결하지 않는 세트는 기존에도 모델 슬롯 수 이후의 `slot`으로 기록하며
  0.6.x까지의 앱에서 열 수 있습니다. 빈 목록만을 위해 형식을 올리지 않습니다. `unassigned`는 「모델에서 머티리얼이 없는 모든 슬롯」을 뜻하는 키이므로
  머티리얼 없음이라는 의미로 사용할 수 없습니다.

보장 범위와 잃는 점:

- 머티리얼 하나는 세트 하나만 소유한다는 규칙은 바꾸지 않습니다(배타적 키는 `materials` 내부 항목까지 파일 전체에서 한 번만 등장).
- `materials` 요소의 알 수 없는 키는 유지하지 않습니다(기록할 때마다 현재 키만으로 재생성). 세트의 알 수 없는 키와 단일 `material`의 알 수 없는 키는 유지합니다.
- 키가 매우 많으면 `project.json` 한도(64 KiB)를 초과하여 저장을 거부합니다.

## 수동 ID 색상 기록

블록 구조는 0.4.x까지의 Unity 브리지 `DocumentBinary`(`WriteIdColors`·`ReadIdColors`)가 정한 것이며
이 앱의 쓰기 구현은 C# 쓰기 구현이 만든 예제(`native-rich-v21.utpaint`)를 읽고 다시 쓰면 같은 바이트열을 만듭니다.

선택한 이유와 채택하지 않은 대안:

- **색상이 있을 때만 블록을 기록하고 버전 유지(채택).** 블록은 정본 버전 19부터 넣을 수 있으며 쓰기 구현 버전(21 이상)은 모두 19 이상이므로 색상을 위해 버전을 추가할 필요가 없습니다.
  색상만 있는 문서는 정본 버전 21을 유지하여 0.4.x까지의 Unity 브리지에서 읽을 수 있습니다. 모두 제거하면 블록도 사라져 색상이 없을 때와 같은 바이트열로 돌아갑니다.
- **새 버전 번호 사용.** 색상을 쓴다는 이유만으로 0.4.x까지의 Unity 브리지에서 문서 전체를 열 수 없게 됩니다. 블록 구조와 정본 버전 19는 사양에 있고 해당 Unity 브리지가 읽고 쓸 수 있으므로 추가할 필요가 없습니다.
- **지문이 현재 모델과 맞지 않는 색상을 읽을 때 버리거나 읽기 거부.** 모델을 아직 불러오지 않은 동안에는 대조할 수 없으며 다른 모델을 열고 다시 저장했을 뿐인데 색상이 사라집니다.
  읽기 구현은 기록된 그대로 문서에 복원하고 사용하는 쪽에서 대조합니다(맞지 않으면 색상 편집과 ID 맵 베이킹을 거부).
- **색상을 정본 외부 항목에 저장.** 색상은 문서 일부(Undo 대상이며 ID 맵 베이킹 조건)이고 `document.utpaint` 버전 19에 정해진 위치가 있습니다. 별도 항목으로 만들면 0.4.x까지의 Unity 브리지가 저장할 때 버립니다.

보장 범위와 잃는 점:

- 색상은 부분 번호(연결된 메시 부분의 일련번호)로 연결됩니다. 모델 부분 수나 순서가 바뀌면 지문이 달라져 다른 모델의 것으로 취급합니다(번호를 이용해 다른 부분에 색상을 적용하지 않음).
- 색상은 최대 4096개, 부분 번호는 0~3999999, 색상은 0xRRGGBB입니다. 범위 밖 값은 쓰기 구현에 도달하기 전에 문서가 거부하며 읽기 구현도 거부합니다.
