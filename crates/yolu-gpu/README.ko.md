# 타일 합성과 브러시 GPU 미리 보기

`GpuPainter`는 wgpu 30의 compute로 `yolu-core`의 평면 레이어 문서를 타일별로 합성합니다. 26가지 합성 모드, 레이어 불투명도, 표시 여부, 채널, 클리핑을 처리합니다. RGB 색 공간을 변환하지 않고 straight RGBA8을 레이어마다 반올림합니다. 원본 CPU 타일은 읽기만 합니다. 저장·Undo의 기준 데이터에는 항상 `yolu-core`를 사용하세요.

```rust
use yolu_core::{Channel, Document, TileCoord};
use yolu_gpu::{Compositor, Options};
let doc = Document::new(128, 128).unwrap();
let mut compositor = Compositor::new(Options::default());
let result = compositor.composite_tiles(&doc, Channel::Color, &[TileCoord::new(0, 0)]).unwrap();
assert!(result.is_current(&doc));
// GPU が使えなければ CPU の結果と fallback_reason() の理由が得られる。
```

`Document::changed_tiles(channel, serial)` 목록을 `composite_tiles`에 전달하면 해당 타일만 합성합니다. 비워진 타일도 투명한 결과를 반환합니다. 가장자리의 부분 타일은 `TileResult::rect`의 너비와 높이로 잘라냅니다. 행은 왼쪽 아래부터 위로 나열됩니다. 캐시는 호출자가 소유하며 문서·채널을 전환할 때 폐기하세요. 같은 ID를 가진 문서를 다시 읽었을 때도 폐기합니다. `is_current`는 동일한 문서를 계속 편집하는 동안의 ID·revision 대조입니다.

`brush_dabs`는 스트로크 시작 전 사각형과 보간된 `Dab` 목록을 받아 원형 브러시 끝의 smoothstep, 경도, 필압, 유량, 불투명도 상한, 지우개를 계산합니다. 좌표는 전달한 사각형의 왼쪽 아래 기준 픽셀 좌표입니다. 같은 스트로크의 찍기를 모아서 전달하세요. 여러 호출에 걸친 커버리지 누적이나 입력 점 보간은 하지 않습니다. 취소하면 결과를 버리고 기준 데이터의 그리기·Undo는 core 스트로크로 처리합니다. 받는 것은 단순 원형 브러시(`BrushSettings`와 필압으로 크기·불투명도·유량을 바꿀지 선택하는 `PressureSwitches`)뿐이며, 영향 입력의 기울기·속도·무작위나 듀얼 브러시·산포 효과·색 변화·수채 경계·삐져나감 방지 같은 브러시 확장은 이 경로에 넣지 않습니다. 브러시 안티앨리어싱(`BrushSettings::anti_alias`)이 “없음” 이외인 설정은 이 경로로 그릴 수 없어 이유와 함께 거부합니다(가장자리 띠와 작은 찍기의 농도는 core 스트로크에만 구현됨). 브러시 색 혼합(두껍게 칠하기)은 이 경로에 넣지 않습니다. 혼합은 찍기마다 아래 픽셀을 읽어 붓의 물감 적재량(브러시가 가진 색)을 갱신하므로, 원형 브러시 끝 커버리지와 색만 반환하는 이 경로에서 계산하면 core 결과와 달라집니다([브러시](../../docs/ko/BRUSH.md#色の混ぜ厚塗り)). 투명 픽셀의 RGB는 입력 복사와 그리지 않은 경우 유지하며, 지우개로 알파가 0이 되면 core와 마찬가지로 RGBA를 0으로 합니다.

## 상주 캐시와 표시 텍스처

`ResidentCompositor`는 입력 레이어 타일을 GPU에 상주시켜 합성 결과를 표시용 `Rgba8Unorm` 텍스처에 유지합니다. `update`는 `Document::changed_tiles`의 세대를 추적하여 영향을 받는 좌표만 다시 합성합니다. 해당 좌표의 각 레이어를 대조용 CPU 복사본과 완전히 비교하여 실제로 바뀐 레이어 타일만 전송합니다. 전송할 타일·명령 배열·조정 테이블·묶음별 상수를 하나의 배열에 담아 GPU 측 임시 버퍼에 `write_buffer` 한 번으로 쓰고 GPU 내부에서 목적지로 복사합니다(쓰기 호출이 무거운 디바이스에서 타일별 쓰기가 누적되는 것을 피하기 위함). 쓰기 횟수는 `UpdateStats::transfers`이며 보통 1입니다. 한 번에 모으는 양은 남은 예산의 1/3(최대 64 MiB)이 상한이며, 초과하기 전과 아직 제출하지 않은 묶음이 읽을 타일을 퇴거시키기 전에 그때까지의 내용을 제출합니다(`ResidentOptions::transfer_limit_bytes`로 테스트에서 엄격한 상한을 둘 수 있음). 불투명도·합성 모드처럼 픽셀을 바꾸지 않는 변경은 입력을 다시 전송할 필요가 없습니다. 해시 충돌에 의존하지 않는 대신 입력과 같은 양의 CPU 복사본을 유지합니다.

```rust
use yolu_core::{Channel, Document};
use yolu_gpu::{ResidentCompositor, ResidentOptions};
let doc = Document::new(256, 256).unwrap();
let mut gpu = ResidentCompositor::new(ResidentOptions::default())?;
let stats = gpu.update(&doc, Channel::Color)?;
let display = gpu.display()?;
// display.texture / display.view を表示に使う。行は左下から。保存は core の正本から行う。
assert_eq!(display.revision, doc.revision());
// 必要なときだけ任意の矩形を読み戻す。
let request = gpu.request_readback(doc.bounds())?;
let pixels = gpu.finish_readback(request)?;
# Ok::<(), yolu_gpu::GpuError>(())
```

표시 텍스처는 빌려서 반환합니다. 다음 갱신에서 내용이 바뀌므로 이전 세대의 스냅샷으로 보관하지 마세요. 문서 ID·크기·채널이 바뀌면 상주 복사본을 폐기합니다. 같은 ID의 문서를 다시 로드할 때는 `reset()`을 명시적으로 호출하세요. 레이어 추가·삭제·순서 변경·중첩·마스크·채우기 값, 취소·Undo·Redo도 변경 기록의 타일을 통해 반영합니다(최초 또는 문서·채널이 바뀔 때만 전체 합성). `GpuPainter`의 기존 읽어오기 API와 브러시는 계속 사용할 수 있습니다.

### 합성 가능한 문서와 거부하는 문서

합성할 레이어 배열은 `plan.rs` 한 곳에서 만들며 `GpuPainter::composite_tiles`와 `ResidentCompositor`가 같은 것을 사용합니다. `yolu-core`의 CPU 계획과 같은 규칙(형제별 클리핑 묶음, 보이지 않는 바탕은 묶음 전체 제외, 그룹은 내부 내용의 계획)에 따라 해당 채널의 불투명도와 합성 모드(`ChannelBlend`)를 사용합니다. 계획은 평면 명령 배열이며 셰이더가 픽셀별로 처음부터 한 번만 실행합니다(재귀하지 않음). 결과와 클리핑 묶음 값의 레지스터에는 중첩 그룹이 임시 보관하는 작은 스택(결과와 묶음 값 각 1워드)을 둡니다. 작업 텍스처나 그룹별 추가 합성 단계가 없어 예산에 추가하는 것은 명령 배열과 조정 테이블뿐입니다.

- 합성 가능한 것: 래스터 레이어, 채우기 레이어(채널별 값), 래스터 마스크(활성화·반전·농도), 26가지 합성 모드, 채널별 합성, 클리핑, 그룹(통과이고 불투명도가 1이며 마스크가 적용되지 않으면 내용을 아래에 그대로 겹치는 것과 같아 평탄화합니다. 그 외에 통과이고 불투명도가 1이 아니거나 마스크가 적용되면 아래와 페이드하며, 통과가 아닌 것·클리핑되는 것·클리핑 바탕이 되는 것[클리핑된 레이어가 숨김·불투명도 0·내용 없음으로 그려지지 않아도 Photoshop과 동일]은 내용을 투명 상태부터 합성하여 겹칩니다), 조정 레이어(반전·레벨·색상/채도·그라데이션 맵·톤 곡선·색상 균형·밝기/대비·이진화·포스터화. 클리핑된 조정과 그룹 내부 조정도 포함), 노멀 유형 채널(단위 벡터 겹치기·클리핑·페이드. Overlay는 RNM, 다른 모드는 교체), 효과(활성화된 필터·생성기·채우기의 그라데이션과 투영·마스크 필터)가 있는 문서.
- 레이어 세트가 있는 문서: 채널 출력 할당(`Document::channel_output`)이 가리키는 레이어 세트의 레이어만 겹칩니다(다른 레이어 세트의 레이어는 배열에 넣지 않고 클리핑 묶음도 같은 레이어 세트 안에서 결정). 할당되지 않은 채널은 면이 없는 불투명 채우기 명령을 해당 채널 기본값 색으로 하나만 배치하여 CPU 최종 결과(기본값으로 채운 픽셀)와 맞춥니다(Color·Roughness·노멀 채널에서 CPU와 최대 차이 1 이내임을 테스트했습니다. 알파가 0이고 RGB가 0이 아닌 기본값은 테스트하지 않았으며 일치를 보장하지 않음).
- 거부하는 것(`supports`와 `update`가 `Unsupported` 이유를 반환): 문서에 없는 채널, 셰이더 스택에 들어가지 않는 깊이의 그룹 중첩(독립 합성 그룹은 32단계, 통과 그룹은 64단계. 문서의 중첩 상한은 64단계). 알리지 않고 다른 그림을 만들지 않으며 호출자가 CPU 합성을 사용합니다. `update`는 거부해도 GPU를 실패로 처리하지 않습니다(문서가 합성 가능한 구조로 돌아오면 계속 사용 가능). `Compositor`는 거부한 호출만 CPU로 합성하고 GPU를 버리지 않습니다.

조정 중 성분별로 결정되는 수식(레벨·톤 곡선·밝기/대비)은 CPU의 `apply_in`에 회색 픽셀을 통과시킨 결과로 항목 256개의 테이블을 만들어 업로드하며(성분이 독립적이어서 회색 한 줄로 R·G·B 테이블을 모두 구할 수 있음. CPU와 바이트까지 같음), 그라데이션 맵은 CPU와 같은 수식으로 만든 휘도 → 색 테이블을 업로드합니다. 반전·이진화·포스터화는 셰이더의 정수 수식으로 CPU와 바이트까지 같습니다. 색상/채도와 색상 균형만 셰이더의 f32 수식이며, f32와 f64의 반올림 경계에서 1바이트 차이가 날 수 있습니다(색상·채도·색·휘도 또는 나누기처럼 위 색의 채도나 작은 값에 따라 결과가 크게 달라지는 모드로 겹치면 그 차이가 커짐).

효과 계산 자체는 CPU(`yolu-core` 평가)에 그대로 둡니다. 평가한 출력은 `Document::layer_output_into`·`mask_output_into`(문서 평가 캐시. CPU 합성과 같은 평가 경로)에서 묶음의 타일을 포함하는 사각형을 한꺼번에 읽어 타일로 상주 업로드합니다(타일마다 요청하면 평가가 블록을 하나씩 직렬로 평가하기 때문). 출력이 모두 0인 타일은 상주시키지 않습니다. 변경 기록(흐림 반지름 범위, 전체 통계를 쓰는 단계·Anchor 리더 포함)은 core가 관리하므로 갱신 시 변경된 타일만 평가하여 다시 업로드합니다.

셰이더는 해당 기능을 사용하지 않는 문서에 스택·조정 수식·노멀 수식이 들어가지 않는 형태(`plan.rs`의 `Variant`)로 기능별로 처음 필요할 때 만듭니다. 픽셀별 전용 스택과 조정 수식이 들어 있으면 그룹도 조정도 없는 문서 합성까지 느려지기 때문입니다(소프트웨어 GPU 측정에서 3배).

레이어 픽셀이 없는 곳(없는 타일)은 상주시키지 않고 작업 영역을 0으로 채웁니다. 보이지 않는 레이어(숨김·불투명도 0·채널 비활성)는 배열에 넣지 않고 픽셀도 업로드하지 않습니다. 희소 문서에서 전체 타일만큼의 GPU 버퍼를 만들지 않기 위한 처리입니다.

### 전체 상주 가능 여부 추산

`resident_requirements(doc, channel, options, limits)`는 그려진 타일(레이어와 마스크의 존재하지 않는 타일 제외. 평가 출력을 갖는 레이어는 전체 평가 전까지 그려진 타일 수가 결정되지 않으므로 가질 수 있는 개수의 상한 사용: 채우기·생성기·이미지 투영은 캔버스 전체, 흐림은 원본 타일을 반지름만큼 넓힌 범위)을 모두 상주시키는 데 필요한 양을 GPU에 접근하지 않고 추산합니다. 표시 텍스처·작업 영역·전송 여유(`fixed_bytes`)와 타일의 GPU 복사본 및 같은 양의 CPU 복사본(`tile_bytes`)으로 계산하며, `update`가 세는 `UpdateStats::resident_bytes`와 같은 수식입니다(모든 타일이 상주하면 일치. 평가 출력을 갖는 레이어는 실제 상주량이 추산값 이하). 합계가 예산을 넘는 문서도 타일을 퇴거시키면서 합성할 수 있지만 레이어 불투명도나 합성 모드처럼 전체 영역에 영향을 주는 변경마다 모든 타일을 다시 업로드하므로 느려집니다(4096²·전체를 덮는 4레이어는 컨테이너의 실제 GPU에서 CPU의 약 3배, 소프트웨어 GPU에서 약 4.5배 시간). 호출자는 이 추산으로 CPU 합성을 선택할 수 있습니다. 디바이스 상한을 넘는 크기·GPU가 처리할 수 없는 문서는 Err입니다.

### 앱의 디바이스에서 실행하기·미리 곱한 알파로 표시

`GpuPainter::from_device(info, device, queue, options)`는 호출자가 가진 wgpu 디바이스와 큐로 생성합니다. egui 렌더링과 같은 디바이스를 전달하면 `Display::texture`를 읽어오지 않고 네이티브 텍스처로 표시할 수 있습니다. compute나 storage 상한이 부족한 디바이스(WebGL2 수준 상한 등)는 파이프라인 생성 단계에서 이유가 있는 오류를 반환합니다. 디바이스 상한(`max_texture_dimension_2d`, 스토리지 버퍼 바인딩 크기)에 들어가지 않는 문서도 이유와 함께 거부합니다.
`device_can_composite(&Limits)`는 해당 디바이스 상한으로 합성할 수 있는지(합성과 찍기 묶음용 스토리지 버퍼 7개·스토리지 텍스처 1개·크기 64의 워크그룹[compute 실행 단위])를 문서를 보기 전에 답합니다. egui-wgpu는 OpenGL일 때 WebGL2 수준 상한으로 디바이스를 만들므로, 그것으로 부족하면 호출자가 합성을 시도하지 않고 CPU를 선택할 수 있습니다.

`ResidentOptions::premultiplied_display`를 켜면 표시 텍스처를 미리 곱한 알파로 씁니다. 수식은 egui의 `Color32::from_rgba_unmultiplied`와 같은 정수식(알파 0은 모두 0, 255는 그대로, 그 외는 `p = v × a + 128; (p + (p >> 8)) >> 8`)이며, straight 표시를 CPU로 변환한 값과 바이트까지 일치합니다. 읽어오는 값도 미리 곱한 값이 됩니다.

동일한 대조(마스크·채우기·채널별 합성·클리핑·통과 그룹·취소·순서 변경·삭제)는 `cargo run --release -p yolu-gpu --example canvas_check`로 메인 스레드에서 사용 가능한 어댑터를 대상으로 실행할 수 있습니다(Mesa의 d3d12 경유 OpenGL처럼 테스트의 자식 스레드에서 디바이스를 생성하면 종료되는 환경을 위함). 어댑터 이름도 함께 기록하세요.

<a id="表示の許しgpu-と-cpu-の差"></a>

### 표시 허용 오차(GPU와 CPU의 차이)

레이어별로 반올림하여 RGBA8로 만드는 수식은 CPU와 같으며 둘 다 f32로 계산하지만, 셰이더 연산의 반올림(곱셈과 덧셈을 결합하는 것 등)이 CPU 수식(곱셈과 덧셈을 결합하지 않음)과 같다고 보장할 수 없어 단계마다 최대 1의 차이가 날 수 있습니다. 겹친 레이어의 차이는 다음 단계의 수식에서 증폭되며(Overlay·HardLight는 최대 2배, ColorDodge·ColorBurn·VividLight·Divide는 그 이상), 마스크·채우기·그룹·채널별 합성을 겹친 테스트 문서(`tests/canvas.rs`)에서는 2 이내였습니다. 임의의 레이어 수·모드에서 상한을 보장하지 않습니다. 이 차이는 표시에만 해당하며 저장·내보내기·3D 값은 항상 CPU 기준 데이터로 만듭니다.

<a id="常駐予算と読み戻しの寿命"></a>

### 상주 예산과 읽어오기 수명

기본 상주 예산은 768 MiB입니다. 표시 텍스처, 입력 GPU 복사본과 같은 양의 CPU 복사본, 작업 버퍼, 묶음별 전송 여유를 셉니다. 삭제된 레이어뿐 아니라 숨긴 레이어·불투명도 0·비활성화한 마스크 등 합성 계획에서 빠진 면의 타일도 상주에서 해제하고, 되돌리면 변경 기록의 타일을 다시 업로드합니다. 상한에 도달하면 마지막 사용 시각이 가장 오래된 레이어 타일부터 퇴거시킵니다. 표시와 최소 한 묶음조차 들어가지 않는 예산은 이유와 함께 거부합니다. `UpdateStats`로 갱신 수·전송 수/바이트·캐시 적중 수·퇴거 수·유지 예약량을 확인할 수 있습니다. CPU 컨테이너 관리 영역, 셰이더, 드라이버 내부 풀, 호출자가 가진 CPU 읽어오기 결과는 대상에서 제외됩니다.

갱신은 최대 16타일(설정 가능, 1~64)씩 처리합니다. 상주 입력에서 작업 영역으로 GPU 내부 복사를 수행하고 입력과 별도의 표시 텍스처에 씁니다. 픽셀 읽어오기는 없지만 전송 메모리의 수명을 구분하기 위해 묶음마다 GPU 처리가 완료될 때까지 기다립니다. 여러 프레임에 걸쳐 표시 갱신을 비동기로 중첩하는 구현은 아닙니다.

읽어오기에는 별도의 기본 64 MiB 예산이 있습니다. 256바이트로 정렬한 행 너비로 아직 완료되지 않았거나 수령하지 않은 요청 버퍼를 합산합니다. `request_readback`은 복사와 매핑을 시작하고 `finish_readback`은 완료를 기다려 연속된 RGBA8을 반환합니다. 요청은 버퍼와 디바이스를 소유하므로 표시 인스턴스를 폐기해도 `Readback::wait_ready`로 완료를 처리할 수 있습니다. 요청을 도중에 버려도 GPU 복사 완료까지 예산 예약을 유지합니다. 갱신이 없는 프레임에서도 `poll`을 호출하여 완료 알림을 처리할 수 있습니다.

표시 세대가 달라진 요청이나 다른 표시 인스턴스의 요청은 채택하지 않습니다. `reset`은 이전 텍스처를 참조하는 복사가 끝날 때까지 기다린 뒤 자원을 해제하여 이전 자원 몫을 다음 세대 예산으로 중복 사용하지 않도록 합니다. GPU 할당·실행 실패 시 이전 표시를 무효화하고 이유를 반환합니다. 호출자는 기존 CPU 합성 경로로 돌아가세요. 저장용 CPU 데이터와 표시용 GPU 데이터는 분리해 관리하세요.

<a id="常駐後の計測"></a>

### 상주 후 측정

Windows에서도 같은 example을 사용할 수 있습니다. 출력되는 어댑터 이름·백엔드와 함께 기록하세요.

```
cargo run --release -p yolu-gpu --example resident_measure -- 4096 3
```

인수는 캔버스 한 변(128의 배수)과 측정 횟수입니다. 4레이어와 16레이어를 측정하며 최초 상주와 각 사례의 워밍업 1회를 제외합니다. 국소 변경은 한 레이어의 한 타일을, 전체 변경은 모든 레이어의 모든 타일을 실제로 변경합니다. GPU 시간은 입력 대조, 필요한 전송, 합성과 완료 대기를 포함합니다. 읽어오기가 있는 경우 갱신 범위(국소 128², 전체 4096²)를 가져옵니다. CPU는 같은 범위의 합성만 측정하며 표시로의 전송은 포함하지 않습니다. 입력 변경 처리와 픽셀 일치 확인은 측정에서 제외합니다.

<a id="キャンバスの表示の更新の計測"></a>

### 캔버스 표시 갱신 측정

```
cargo run --release -p yolu-gpu --example canvas_measure -- 4096 5
```

CPU 표시(변경된 타일을 `composite_into` → 미리 곱한 값으로 변환 → `write_texture` → 제출과 완료 대기)와 GPU 상주 표시(`update`)를 같은 디바이스·같은 변경으로 비교합니다. 캔버스 한 변과 반복 수를 인수로 받고 환경 변수 `LAYERS`(기본값 `4,16,32`)로 레이어 수를 선택합니다. 모든 레이어가 전체를 덮는 문서와 바탕만 전체를 덮고 나머지는 4타일인 문서를 대상으로 1타일·16타일(4×4)·한 레이어 불투명도 변경을 측정하며, 표시 픽셀의 일치(허용 2)도 매번 확인합니다. 출력되는 어댑터 이름과 백엔드를 함께 기록하세요. 소프트웨어 GPU(llvmpipe), WSL 컨테이너 GPU(Mesa의 d3d12 경유 OpenGL), Windows의 D3D11/D3D12/Vulkan 결과를 혼동하지 마세요.

4096², 바탕만 전체를 덮고 다른 레이어는 4타일인 문서(그려진 타일이 예산에 들어가 앱이 GPU로 합성하는 쪽의 문서)의 중앙값(밀리초, CPU / GPU)입니다. CPU는 32스레드 PC에서도 타일을 하나씩 순서대로 합성하므로 같은 수식입니다.
다른 작업이 실행 중인 PC(평균 부하 5~12)에서 측정하여 값이 흔들리며, 실제 GPU는 두 번 측정한 범위를 적었습니다. 모든 레이어가 전체를 덮는 문서 등 다른 조건에서 측정한 값과 섞지 마세요.

| 변경 | 레이어 | llvmpipe(소프트웨어. 1회) | 실제 GPU(RTX 4080 SUPER, WSL의 d3d12를 Mesa OpenGL로 사용. 2회 범위) |
|---|---|---|---|
| 1타일 | 4 | 0.18 / 1.20 | 0.95~1.34 / 1.25~2.23 |
| 1타일 | 16 | 0.46 / 2.04 | 1.62~1.70 / 1.81~1.94 |
| 16타일(4×4) | 4 | 0.95 / 4.77 | 2.55~3.13 / 2.78~3.76 |
| 16타일(4×4) | 16 | 1.17 / 9.14 | 3.13~3.39 / 3.70~4.35 |
| 한 레이어 불투명도(해당 레이어의 19타일) | 4 | 1.29 / 6.84 | 2.85~4.35 / 3.30~7.42 |
| 한 레이어 불투명도(해당 레이어의 19타일) | 16 | 2.32 / 12.71 | 4.84~5.28 / 4.79~5.37 |
| 최초 표시 | 4 | 96 / 284 | 75~84 / 328~376 |
| 최초 표시 | 16 | 47 / 260 | 480~635 / 349~1934 |

소프트웨어 GPU에서는 계산도 CPU가 하므로 GPU 경로는 이 표의 갱신에서 CPU보다 4.4~7.8배, 최초 표시에서 3.0~5.5배 느려 앱의 `Auto`에서는 사용하지 않습니다. 실제 GPU(OpenGL 변환 레이어를 거친 값)에서는 이 조건의 갱신(1타일·16타일·불투명도 변경)이 GPU와 CPU에서 비슷하며 GPU/CPU는 0.8~1.7배 사이로 흔들립니다. 최초 표시에서는 4레이어에서 GPU가 약 4배 느려집니다. 측정한 범위에서 GPU가 CPU보다 뚜렷하게 빠른 조건은 없었습니다. Windows 네이티브 D3D12·Vulkan 값이 아니므로 실제 기기의 `canvas_measure` 결과로 `Auto` 선택 방식을 결정하세요. 현재 `Auto`는 소프트웨어 어댑터가 아니면 GPU를 선택합니다. 느리게 느껴지는 PC에서는 환경 변수 `YOLUPAINTER_CANVAS=cpu` 또는 설정의 “표시 합성”에서 CPU로 돌아갈 수 있습니다. 4096²에서 전체를 그린 레이어가 4장 이상인 문서는 모든 타일을 상주시킬 수 없어(예산 512 MiB), 레이어 불투명도가 바뀔 때마다 모든 타일을 다시 업로드하므로(전체를 덮는 4레이어와 16레이어에서 실제 GPU는 CPU의 2.3~3.5배, 소프트웨어 GPU는 약 4.5배 시간이 걸림) 앱은 CPU로 합성합니다.

<a id="メッシュマップの-gpu-ベイク"></a>

## 메시 맵 GPU 베이크

`BakeGpu`는 `yolu-core::mesh_maps`의 메시 맵(월드 노멀·위치·AO·곡률·두께·접선 공간 노멀·높이·ID·벤트 노멀·불투명도)을 wgpu compute로 베이크합니다. 수식의 기준은 CPU의 `bake`입니다. 준비(대상 선택·BVH·곡률·하이 폴리 투영·접선 공간·ID·광선 방향열)와 후처리(여백·기록·출처)는 core의 `MeshBakePlan`을 그대로 사용하고, 행별 계산(UV 소유자 판정·투영·각 맵의 값·광선)만 WGSL로 수행합니다. GPU 측에 별도 수식을 두지 않습니다.

```rust
use yolu_core::mesh_maps::MeshBakeBudget;
use yolu_gpu::{bake_mesh_maps, BakeBackend, GpuBakeSlot};
# fn demo(input: &yolu_core::mesh_maps::MeshBakeInput, settings: &yolu_core::mesh_maps::MeshBakeSettings) {
let slot = GpuBakeSlot::default(); // デバイスとシェーダーを使い回す（別のスレッドから共有できる）
let (result, run) = bake_mesh_maps(
    BakeBackend::Auto, &slot, input, settings, &MeshBakeBudget::default(), None, None, |_, _| true,
).unwrap();
// run.gpu: 使ったアダプターと計測。CPU で焼いたときは run.fallback_kind / run.fallback_reason が理由。
# let _ = (result, run); }
```

- **실행 위치 선택**: `Auto`는 사용 가능한 하드웨어 GPU가 있으면 GPU, 없으면 CPU입니다. 소프트웨어 렌더링(llvmpipe·WARP 등)은 CPU 멀티스레드보다 느리므로 자동으로는 사용하지 않습니다. `Gpu`는 소프트웨어 렌더링도 허용하며 사용할 수 없으면 이유와 함께 CPU로 돌아갑니다. `Cpu`는 core의 `bake`입니다.
- **광선을 쏘는 맵**(AO·두께·벤트 노멀·하이 폴리 투영): BVH(core의 `MeshRayBvh`를 평탄화한 배열)를 compute로 탐색합니다. 모든 GPU에서 동작합니다. wgpu의 실험 기능 ray query(하드웨어 레이 트레이싱. RT 코어)를 사용할 수 있는 어댑터에서는 가속 구조(BLAS/TLAS)를 만들어 ray query로 탐색하는 경로를 **기본으로 사용합니다**(`GpuBakeOptions::ray_query`. 환경 변수 `YOLUPAINTER_BAKE_RAY_QUERY`가 `0`·`false`·`off`·`no`이면 기본값이 꺼지며, 앱에서는 설정의 “베이크에서 RT 코어 사용”으로 전환합니다. `GpuBakeSlot::set_ray_query`로 나중에 바꾸면 다음 확인·베이크 때 디바이스를 다시 만듦). ray query 경로는 같은 광선 4096개를 compute와 ray query 양쪽 경로로 쏘아 충돌 여부·거리·삼각형·무게중심 좌표를 비교하는 자체 검증을 통과할 때만 사용하고, 통과하지 못하면 compute로 돌아갑니다. 어댑터 미지원·ray query를 켠 디바이스 생성 불가·셰이더나 가속 구조 생성 불가·자체 검증 실패 중 어디에서 돌아갔는지와 이유는 `GpuBakeStats::ray_query_note`에 남습니다(사용한 경로는 `GpuBakeStats::method`). 뒷면을 건너뛰는 설정에서는 뒷면을 건너뛰는 레이도 비교하고, 하드웨어의 앞뒷면 규약이 compute와 반대이면 정점 순서를 바꿔 다시 확인합니다. **실행하여 확인한 환경은 RTX 3050 Laptop의 Vulkan과 Apple M4의 Metal입니다**(CPU 결과와의 차이는 테스트 허용 범위 안이며 compute 경로보다 작음). 소프트웨어 Vulkan(llvmpipe)은 ray query가 없어 compute만 동작합니다. DX12는 DXC(새 셰이더 컴파일러)를 사용할 때만 ray query가 제공됩니다. Windows x86_64 msvc 빌드는 DXC를 실행 파일에 포함합니다(아래의 “D3D12 셰이더 컴파일러”). 어댑터 선택은 여전히 Vulkan을 우선합니다. 실험 기능의 드라이버가 멈추거나 응답 없음(TDR)이 되면 자체 검증도 같은 경로 안에서 수행하므로 compute로 돌아갈 수 없습니다. 그런 PC에서는 꺼 주세요. ray query 경로로 베이크하는 도중 실패하면(디바이스 유실·완료 대기 시간 초과 제외) ray query를 중지하고 compute로 한 번 다시 시도하며, 켜짐·꺼짐이 바뀔 때까지 compute로 베이크합니다(`RayQueryWhy::RunFailed`). 취소·시간 초과·진행 중단은 가속 구조 구축과 자체 검증 중에도 확인합니다. 사용하지 않은 이유의 종류는 `GpuBakeStats::ray_query_why`, 자세한 설명(자체 검증 수치 포함)은 `ray_query_note`에 있습니다. 광선이 필요 없는 맵은 UV 공간에서 텍셀별로 계산합니다.
- **자원 규칙**: 입력 배열은 읽기 전용이며 출력은 별도 버퍼입니다(같은 버퍼를 읽으면서 쓰지 않음). 입력·출력·읽어오기 합계를 기본 768 MiB 예산 안으로 제한하며, 출력이 들어가지 않는 크기는 행 띠로 나누어 베이크합니다(입력 배열이 들어가지 않거나 한 행도 들어가지 않으면 이유를 반환). dispatch 한 번의 크기는 시간에 맞춰 조정하여(기본 목표 50 ms) Windows GPU의 응답 없음(TDR)을 피합니다. 읽어오기는 띠마다 완료를 기다린 뒤 전달합니다. 취소·시간 초과·진행 중단은 dispatch 사이에 확인하고 CPU와 같은 빈 결과를 반환합니다(기존 맵을 바꾸지 않음).
- **CPU로 돌아가는 조건**: GPU 없음·디바이스 생성 실패·셰이더 생성 불가(`FallbackKind::Unavailable`), 예산 또는 디바이스 상한 초과(`Budget`), 실행 중 실패(디바이스 유실·대기 시간 초과·검증 오류·양자화 전에 센 NaN·무한대·범위 밖 값. `Failed`). NaN·무한대는 GPU가 만든 경우에 세므로 GPU의 f32에서는 오버플로가 발생하지만 CPU의 f64로는 베이크할 수 있는 입력(매우 큰 좌표 등)은 이유와 함께 CPU로 돌아갑니다. 실패한 디바이스는 계속 사용하지 않고 다음 베이크에서 다시 만듭니다. 설정·UV·예산·수동 ID 색 등 CPU도 거부하는 입력은 CPU로 돌아가지 않고 그대로 오류를 반환합니다.
- **결과의 성격**: 베이크 결과는 저장해도 되는 파생 데이터입니다. 원본 모델·머티리얼·텍스처는 변경하지 않습니다.

<a id="cpu-との差"></a>

### CPU와의 차이

모든 바이트가 일치할 필요는 없습니다. 차이의 원인은 3가지입니다. f32와 f64의 반올림, UV 커버리지 경계(텍셀 중심이 삼각형 변 바로 위에 있는 경우)의 판정, 광선 충돌 여부(f32와 f64에서 교차 판정이 달라지는 광선이 드물게 있으며, 그 광선 하나로 텍셀 값이 1/광선 수만큼 바뀜)입니다. AO·두께·벤트 노멀의 광선 회전은 GPU sin/cos 정확도에 의존하지 않고 다항식으로 계산하며 난수열은 core가 만든 방향열을 그대로 사용하므로 CPU와 같은 광선을 쏩니다. UV 커버리지는 삼각형 원점을 정수와 소수 부분으로 나눈 로컬 좌표로 계산하고 허용 오차는 1e-6입니다(core는 1e-9). 여백(padding)은 띠를 가로지르는 인접 정보가 필요하므로 GPU로 옮기지 않고 core 후처리(CPU)로 수행합니다.

`cargo test -p yolu-gpu --test bake -- --nocapture`는 정육면체·요철이 있는 정육면체(정점 노멀·AA 2)·하이 폴리 투영·이름 대응·ID 원본 4종과 수동 색·여러 슬롯과 홀수 크기(AA 4)에서 맵별로 CPU와의 차이를 측정하고 허용 범위와 비교합니다. 값은 16 bit(0~65535)의 차이입니다.

| 맵(하이 폴리 투영 없음) | 허용 범위(테스트 판정) | 측정한 최댓값(llvmpipe) | 근거 |
|---|---|---|---|
| 월드 노멀·위치·곡률·높이·접선 공간 노멀 | 최대 차이 8 | 1 | 광선을 쏘지 않으므로 f32 반올림만 발생 |
| 불투명도·ID | 일치(최대 차이 0) | 0 | 정수와 0/1 값 |
| AO·두께·벤트 노멀 | 최대 차이 6%(3932), 0.5%를 넘는 텍셀은 0.2% 이하, 5%를 넘는 텍셀은 0.05% 이하 | 최대 2.8%(1856), 0.5% 초과 0.012%, 5% 초과 0 | 광선 32개 중 하나의 충돌 여부가 약 3%. 차이는 충돌 여부가 달라지는 광선이 있는 드문 텍셀에서만 발생 |
| UV 커버리지(어느 텍셀을 베이크할지) | 불일치는 덮이는 텍셀의 0.1% 이하 | 0(모든 사례) | 변 위의 텍셀만 판정이 달라질 수 있음 |

하이 폴리 투영이 있으면 투영 광선의 충돌 여부가 f32와 f64에서 달라지는 텍셀이 드물게 발생합니다. 해당 텍셀은 다른 면(또는 빗나감)의 값이 되므로 차이가 0과 1 또는 다른 부품의 색만큼 커집니다(69312면 하이 폴리·2048²·AA 1의 전체 10종에서 약 400만 텍셀 중 불투명도·ID·높이의 5텍셀. AO는 0.0047%, 곡률은 0.0001%의 텍셀이 0.5%를 넘었으며 최대 차이는 AO 32%·곡률 23%·높이 50%·불투명도와 ID 100%). 투영이 있는 테스트는 차이의 크기를 제한하지 않고 0.5%를 넘는 텍셀의 비율을 0.2% 이하, 평균 차이를 2 이하로 제한합니다.

텍셀 중심이 삼각형이 공유하는 변(사각형 대각선) 위에 놓이는 입력에서는 어느 삼각형의 면 노멀을 쓰느냐에 따라 AO 광선이 바뀝니다. 이 변동은 CPU끼리도 UV를 몇 ulp만 이동하면 발생하므로 테스트에서는 “GPU와 CPU의 불일치가 CPU 자체 변동의 2배＋8텍셀 이내”인지 확인합니다(6144텍셀 중 CPU끼리는 61·GPU와 CPU는 86). 광선을 줄이면(개수 16 이하) 광선 하나의 가중치가 커져 최대 차이도 그만큼 커집니다(16개에서 6.1% 관측). 허용 범위는 광선 32개 테스트의 값입니다.

<a id="ベイクの計測"></a>

### 베이크 측정

```
cargo run --release -p yolu-gpu --example bake_measure
cargo run --release -p yolu-gpu --example bake_measure -- --triangles 70000 --size 2048 --samples 64 --runs 3
```

기본값은 7만 삼각형·2048²·광선 64개이며, 광선이 필요 없는 맵 7종, 광선 맵 3종, 하이 폴리 투영(로우 폴리 192면 ← 하이 폴리)의 전체 10종을 CPU·GPU compute·지원 어댑터의 ray query 순서로 측정하고 사용한 경로와 CPU 차이도 출력합니다. 인수는 `--triangles`·`--size`·`--samples`·`--aa`·`--runs`·`--software`(소프트웨어 렌더링 어댑터도 사용)·`--no-cpu`입니다. GPU 첫 실행은 별도로 출력합니다(파이프라인 준비 포함). 어댑터 이름·백엔드·CPU 스레드 수와 함께 기록하세요.

Linux에서 어댑터가 llvmpipe(Vulkan, CPU에서 실행되는 소프트웨어 렌더링)뿐인 환경의 측정 예입니다(`--runs 2 --software`. CPU는 32스레드이며 다른 부하가 있는 PC에서 측정해 시간이 흔들림). **소프트웨어 렌더링이므로 GPU 속도 비교가 되지 않습니다**. 정확성(CPU와의 차이)과 dispatch 분할·띠 수를 확인하기 위한 값입니다. 하드웨어 GPU가 CPU보다 빠른지, ray query 경로를 사용할 수 있는지는 아직 측정하지 않았습니다. 실제 기기(RTX 등)에서 `bake_measure`를 실행하여 “사용한 경로”에 ray query가 나오는지와 CPU 차이·시간을 확인하세요(자동 기본값, 즉 사용 가능한 하드웨어 GPU가 있으면 GPU를 선택하는 것은 아직 하드웨어 측정 없이 정한 값입니다. 느린 PC에서는 베이크 위치로 “CPU”를 선택하세요).

| 조건(69312삼각형·2048²·AA 1·광선 64개) | CPU(중앙값) | GPU compute(llvmpipe, 중앙값) | dispatch·띠 |
|---|---|---|---|
| 광선이 필요 없는 맵 7종 | 9.8초 | 25.3초 | 660회·2띠 |
| 광선 맵 3종(AO·두께·벤트 노멀, 4.8억 개) | 8.7초 | 44.1초 | 1077회·1띠 |
| 하이 폴리 투영(로우 폴리 192면 ← 하이 폴리 69312면), 전체 10종 | 5.7초 | 27.9초 | 735회·3띠 |

가장 긴 dispatch는 76~205 ms입니다(목표 50 ms는 최초 한 번을 가볍게 실행한 뒤 시간으로 조정하므로 느린 어댑터에서는 초과할 수 있음). 출력이 예산(768 MiB)에 들어가지 않는 2048²의 전체 맵은 2~3개 띠로 나누어 베이크합니다.

<a id="d3d12-のシェーダーのコンパイラー"></a>

## D3D12 셰이더 컴파일러

Windows D3D12에서는 wgpu의 기본 컴파일러(FXC)가 오래되고 느리므로 x86_64 msvc 빌드에 DXC를 정적으로 포함합니다(`Cargo.toml`의 `static-dxc`. DXC DLL을 별도로 배포하지 않음). `yolu_gpu::dx12_compiler()`가 프로세스에서 한 번만 컴파일러를 결정하고 `instance_descriptor()`가 `wgpu::Instance` 설정을 그에 맞춰 만듭니다.
`GpuPainter`·`BakeGpu`·앱 렌더링 설정·테스트 예제는 이 설정으로 디바이스를 만듭니다.

- 환경 변수 `WGPU_DX12_COMPILER`가 있으면 확인 없이 해당 지정을 따릅니다.
- 없으면 내장 DXC로 D3D12 instance를 만들어 어댑터가 보이는지 확인한 뒤 DXC를 사용하고, 보이지 않으면 FXC로 돌아가 이유를 표준 오류에 한 줄 출력합니다. `Dx12Compiler::Auto`를 사용하지 않는 이유는 내장 DXC를 생성할 수 없으면 FXC로 돌아가지 않고 D3D12 전체를 사용할 수 없게 되기 때문입니다.
- 다른 OS와 빌드(Linux·macOS·x86_64-pc-windows-gnu)는 wgpu 기본값을 유지합니다.

이 선택 규칙은 OS와 관계없이 단위 테스트로 확인합니다.

<a id="gpupainter-の同期-api-の予算と失敗"></a>

## GpuPainter 동기 API의 예산과 실패

읽기 입력과 출력은 별도 버퍼입니다. 한 번의 읽어오기가 완료된 뒤 다음 묶음을 제출합니다. 기본 64 MiB GPU 작업 예산에는 입력, 메타데이터(명령 배열과 조정 테이블), 타일별 픽셀 유무 표시와 명령 번호 배열, 출력, 읽어오기 및 이들과 같은 양의 전송 여유를 포함합니다. 한 묶음의 타일 수는 실행 시 세는 이 양이 예산에 들어가는 최댓값이며, 명령 번호 배열은 모든 레이어가 그려진 타일의 최대 길이로 셉니다. 드라이버 내부 영역, 셰이더, 호출자가 보관하는 CPU 결과는 이 예산에 포함하지 않습니다. 한 묶음은 최대 64타일이며 디바이스의 버퍼·dispatch 상한도 적용합니다. 브러시는 한 번에 100만 찍기 이내이면서 예산 이내여야 합니다.

읽어오기는 최대 30초 기다립니다. 실패한 인스턴스는 다음 제출을 거부하며 다시 생성해야 합니다. `Compositor`는 GPU 초기화 또는 실행 실패 시 이유와 함께 CPU로 전환합니다. `GpuPainter`를 직접 사용하거나 브러시를 사용하는 경우 `Result` 오류를 받아 core로 돌아가세요.

<a id="検証と計測"></a>

## 검증과 측정

```
cargo test -p yolu-gpu -- --nocapture
cargo run -p yolu-gpu --example measure
```

어댑터 또는 디바이스를 얻을 수 없으면 GPU 테스트는 이유를 표준 오류로 출력하고 종료합니다(Rust 집계에서는 passed로 표시되므로 `--nocapture` 출력을 확인하세요). 환경 변수 `YOLUPAINTER_REQUIRE_GPU`를 설정하면 어댑터가 없어 건너뛰는 테스트(이 크레이트의 테스트와 단위 테스트, yolu-app의 `common::canvas_device`와 GPU로 베이크한 메시 맵의 저장·복원 테스트)를 건너뛰지 않고 실패로 처리하므로 어댑터가 있는 환경에서 테스트가 실행되었는지 확인할 수 있습니다. 셰이더 결함은 건너뛰지 않고 실패합니다. `WGPU_BACKEND` 등 wgpu 환경 변수로 백엔드를 선택할 수 있습니다.

GPU를 사용하는 테스트는 디바이스(wgpu의 Instance·Device)를 만들기 전에 `tests/support/gpu_lease.rs`의 `lease()`를 호출합니다. 같은 실행 파일 안의 테스트가 디바이스 생성·사용·폐기를 하나씩 수행하도록 하기 위함입니다(Vulkan의 lavapipe에서는 서로 다른 스레드에서 디바이스를 동시에 생성하면 프로세스 전체가 SIGSEGV로 종료될 수 있음). 대여는 스레드가 끝날 때(테스트가 끝날 때) 해제되며 같은 테스트가 디바이스를 몇 개 만들어도 기다리지 않습니다.

GPU와 CPU의 부동소수점 연산 및 반올림 차이로 합성 결과가 달라질 수 있습니다. 비선형 모드의 여러 단계 합성에서는 앞 단계의 반올림 차이가 증폭되므로 임의의 레이어 수에 대해 최대 차이 1을 보장하지 않습니다. 저장에는 CPU 기준 데이터를 사용하세요.

동기 API용 `measure`는 4096²·4레이어에서 워밍업 후 측정하며 전송과 읽어오기를 포함하여 CPU와 비교합니다. 성능은 어댑터·백엔드·드라이버에 따라 달라지므로 출력되는 환경 정보와 함께 평가하세요.

의존성인 wgpu, pollster, bytemuck은 MIT 또는 Apache-2.0을 선택할 수 있는 라이선스입니다.
