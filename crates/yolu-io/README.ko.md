# yolu-io

`.ylp` 형식 1〜9 (1〜7은 0.4.x까지의 Unity 브리지가 작성한 형식. 8은 이름을 지정해 저장한 선택 영역을 사용하는 파일만, 9는 머티리얼을 2개 이상 가진 세트가 있는 파일만. 아래 참고), `document.utpaint` 버전 1〜30·32〜36 (31은 결번), 외부 `YLP-1`〜`4` (`YLP-4`는 기존 상한에 들어가지 않는 큰 .ylp. 아래 참고)를 읽고 씁니다. 버전 1〜21은 0.4.x까지의 Unity 브리지가 작성한 버전이며, 22 이후는 Rust 구현에서 추가한 버전입니다. 22 사용자 채널·23 절차적 Generator·24 색상 보정·25 그라데이션 맵 색상 혼합·26 분할 정본·27 경로 목록·28 0.5.0 효과·29 포인트 그라데이션·30 텍스트 레이어·32 이음새 설정·33 베이크 우선순위·34 경로 브러시 앤티앨리어싱·35 자와 경로 선대칭·36 레이어 세트 (아래). 형식 명세 (엔트리·JSON 구조·정본 필드·버전)는 [docs/YLP_FORMAT.md](../../docs/ko/YLP_FORMAT.md)에 있습니다. 파일 전체나 정본 전체를 메모리에 만들지 않고 스트리밍으로 읽고 씁니다. 레이어 (래스터·채우기·보정·그룹, 마스크, 클리핑, 채널별 합성) 문서는 `yolu-core::Document`와 상호 변환할 수 있습니다.

```rust,no_run
use yolu_io::{NativeValue, SaveTarget};

let (project, mut target) = SaveTarget::open("sample.ylp")?;
// 正本は骨組みだけを持ち、画素は要るときに流して読む。小さな文書は `with_value` などでメモリの正本にして書き換えられる
let set = &project.sets()[0];
let document = set.document.with_value(
    "layers[0].name",
    NativeValue::Text("背景".into()),
)?;
let changed = project.with_document(&set.id, &document)?;
target.save(&changed)?;
# Ok::<(), yolu_io::Error>(())
```

## 읽기와 쓰기

- `Project::read` (메모리 바이트열)·`Project::open(path, limits)` (파일 스트리밍)은 ZIP CRC·manifest SHA-256·길이·이름·상한 (`Limits`, 설정 예산에서 결정. 아래 “큰 문서”)을 검증하고 텍스처 세트·정본·선택 영역·리소스를 읽습니다. 파일에서 연 엔트리는 작은 것 (최대 1 MiB)만 메모리에 두고 나머지는 파일 내부 위치 (`Blob`)로 보유하며 필요할 때 해당 위치에서 스트리밍으로 읽습니다 (읽을 때마다 길이·SHA-256·CRC 재검증. 열린 파일 핸들에서 읽으므로 외부에서 이름 변경·이동·삭제·다른 파일로 교체해도 열었을 당시 내용을 읽음. 아래 “저장”). `Blob::hold_in(dir, keep)`는 내용을 다른 폴더에 다시 배치합니다 (내용 파일은 하드 링크, 불가능하면 검증하며 스트리밍 복사. `keep`을 해제하면 폴더 전체 정리. 앱은 복구 세대에서 연 프로젝트에 사용해 해당 세대가 나중에 정리·폐기되어도 저장할 수 있게 함).
- `TextureSet::document`는 `SetDocument`입니다 (정본 골격: `Bytes` 값 (색상·픽셀)을 보유하지 않는 항목, 그리고 원본: 저장된 정본·메모리 정본·core 문서). `to_core_within(budget)`는 레이어별로 스트리밍해 core 문서로 만들고 (레이어 1장만 보유하며 예산 초과 시 중단), `to_native` / `to_bytes`는 작은 문서용으로 메모리 정본을 만듭니다 (최대 512 MiB. 초과하는 정본은 내용을 읽지 않고 `Error::Budget`로 거부).
- `NativeDocument::fields()`는 디스크 순서의 타입 지정 항목을 반환합니다. 예: `layers[0].opacity`, `layers[0].channels[0].tiles[0].rgba`. 정수·불리언·배정밀도 수·GUID·UTF-8 문자열·픽셀 바이트열을 구분합니다. GUID 바이트열은 C# `Guid.ToByteArray()` 순서입니다.
- 정본은 채널과 타일, 마스크, 보정, 필터, Generator, 채우기 이미지·투영·데칼·그라데이션, 2D/3D 경로, Anchor, 수동 ID 색상을 보존합니다. `to_bytes`는 각 값을 원래 순서로 다시 인코딩하며 부동소수점 연산이나 픽셀 변환을 하지 않습니다.
- `with_value`는 기존 항목을 교체한 뒤 정본 전체를 다시 검증합니다. `with_values`는 여러 항목을 함께 교체하고 재검증은 1회만 합니다 (같은 항목을 2회 교체하지 않음). 버전이나 개수만 변경해 불일치가 생기면 거부합니다. 레이어·타일 편집에는 지원 범위를 검사한 후 core API를 사용할 수 있습니다.
- `Project::to_bytes`는 원래 형식을 유지하고 엔트리 내용과 manifest를 바이트가 일치하도록 다시 저장합니다. ZIP 시각·압축 결과·추가 필드는 일치 대상이 아닙니다.
- `migrated_entries`는 형식 7 배열로 메모리에서 마이그레이션한 엔트리입니다. `ylp.json`은 제외하며 원래 형식과 작성 앱은 `info()`로 가져옵니다.
- `upgraded(writer)`는 명시적으로 형식 7로 업그레이드합니다. 정본 버전은 바꾸지 않습니다. 알 수 없는 엔트리·JSON 키도 보존합니다. 알 수 없는 엔트리는 `unknown_entries()`와 `notes()`로 알립니다.
- 형식 7의 `TextureSet::materials`는 `MaterialRef` (이름과 선택적인 에셋 GUID/부호 있는 64 bit `fileId`, 미할당, 이전 슬롯 참조) 배열입니다 (1개 이상). 1개는 `material`, 2개 이상은 형식 9의 `materials`에 기록하며, 2개 이상을 가진 세트가 있는 파일만 형식 9가 됩니다. 이름만 있으면 다른 세트와 중복할 수 있지만 에셋·미할당·슬롯은 파일 전체에서 배타적입니다. 이전 `materialSlot`은 메모리에서 `material: {"slot": …}`로 마이그레이션합니다. `with_materials`는 형식 7 이상 참조 배열을 검증해 변경합니다.
- `Project::create(writer, sets, current)`는 형식 7의 새 프로젝트를 만듭니다 (각 세트는 `SetSpec`: ID·이름·`MaterialRef` 배열·정본 (`DocumentSource`: 메모리 정본 또는 core 문서 사본. core 문서는 전체 정본을 메모리에 만들지 않고 기록할 때 레이어별 스트리밍으로 생성)·사용 중인 채널별 합성 PNG). `with_sets(writer, sets, current)`는 형식 7의 세트 배열·이름·머티리얼 참조·현재 세트를 교체하고 정본과 합성을 바꿉니다. 원래 세트는 모두 배열에 있어야 합니다 (삭제는 `with_sets_dropping(writer, sets, current, dropped)`. 호출자가 확인한 삭제 세트 ID를 전달하면 배열에서 제외하고 `sets/<ID>/` 아래 정본·선택 영역·합성·메시 맵·원본 PSD를 모두 삭제. 어느 쪽에도 없는 세트·양쪽에 있는 세트·파일에 없는 ID는 거부). 정본이 `None`인 세트는 엔트리를 바이트열 그대로 유지하고, 정본을 바꾼 세트의 `composite/`는 삭제한 뒤 전달받은 PNG (`composite_pngs` 출력. 표준 채널만, 같은 채널은 1회)를 기록합니다. 각 세트와 루트의 알 수 없는 JSON 키, 선택 영역·메시 맵·원본 PSD·루트의 다른 엔트리는 유지하고 `savedBy`를 작성자로 설정합니다. 둘 다 기록한 내용을 다시 읽어 검증합니다. 썸네일 (`thumbnail.png`)은 다시 만들지 않습니다.
- `Project::view_model()` / `with_view_model(path)`는 독립 실행형 앱이 view.json (상태 엔트리)에 남기는 모델 파일 (FBX) 참조 `standaloneModel.path` (.ylp 기준 상대 또는 절대 경로 문자열. 1〜1024자, 제어 문자 없음)를 읽고 씁니다. view.json에 선택 항목을 추가할 뿐이므로 형식과 정본 버전은 바꾸지 않습니다. view.json이 없으면 0.4.x까지의 Unity 브리지 리더가 허용하는 최소 구조 (`modelAssetGuid`는 빈 값, `selectedChannel`은 0)로 만들고, 있으면 0.4.x까지의 Unity 브리지가 기록한 모델 GUID·표시 상태를 포함해 알 수 없는 키를 보존합니다. 읽을 수 없는 view.json은 참조를 기록할 때만 최소 구조로 다시 만들며, 참조를 제거하기만 할 때는 변경하지 않습니다.
- `Project::look(set_id)` / `with_look(set_id, look)`는 독립 실행형 세트의 외관 설정 (`sets/<ID>/look.json`, 아래 “외관 설정”)을 읽고 씁니다. `None`이면 엔트리를 삭제합니다 (표준 외관. Unity에서 받은 값이 있으면 엔트리를 유지하고 본체만 기본값으로 설정). 형식 7에만 기록할 수 있습니다. 읽을 수 없는 항목 (손상되었거나 새로운 형식)은 오류를 반환하고 엔트리는 바이트열 그대로 유지합니다. `received_look(set_id)` / `with_received_look(set_id, received)`는 같은 엔트리에서 Live Link로 Unity에서 받은 값 (`received`)만 읽고 씁니다 (본체와 알 수 없는 키는 유지. 읽을 수 없는 엔트리에는 기록하지 않고 거부).
- 선택 영역 (`selection.bin`)은 `Selection`으로 읽고 쓰며 `Selection::from_core` / `to_core`로 core의 `SelectionMask`와 상호 변환합니다. 기록 바이트열은 C# `SelectionBinary.Write`와 같습니다 (값이 있는 타일만 (y, x) 순으로 배열). `Project::with_selection(set_id, Some(&selection))`은 세트의 선택 영역만 교체하며 `None`은 선택 없음입니다 (엔트리 삭제). 정본과 크기가 다른 선택 영역은 재검증에서 거부하고 다른 엔트리는 변경하지 않습니다. 불러온 직후 문서에는 `Document::restore_selection`으로 복원합니다 (Undo 단계 증가 없음).
- 이름을 지정해 저장한 선택 영역 (`sets/<ID>/selections.json`과 `selection-<中身の印>.bin`, 형식 8)은 `Project::saved_selections(set_id)` (읽은 항목 `items`, 건너뛴 항목과 이유 `skipped`. 손상 항목만 건너뛰고 건너뛴 엔트리는 바이트열 그대로 유지)와 `with_saved_selections(set_id, &items)` (세트 인덱스와 내용을 모두 교체. 규칙에 맞지 않는 배열은 거부)로 읽고 씁니다. 선택 영역은 현재 선택 영역 (`selection.bin`)과 같은 `YLSL` 버전 1이며, 내용 식별자는 SHA-256의 앞 128 bit입니다 (엔트리 이름이 `sets/<ID>/`를 포함해 최대 96자이기 때문). 1세트당 최대 32개이며 이름은 앞뒤 공백 없이 1〜256자·제어 문자 없음·중복 없음입니다. 사용하는 문서만 `ylp.json` 형식을 8로 올리고 (외부 `YOLUPAINTER-YLP-3`는 유지), 모두 없어지면 7로 되돌립니다 (다시 쓸 때마다 정리). 형식 7까지의 리더는 형식 8을 작성한 앱과 함께 거부합니다 (`Error::UnsupportedFormat`, 지원 상한은 `MAX_FORMAT`). 배포용 사본에서는 `Removal::SavedSelections`로 제외할 수 있습니다.
- 모델의 현재 포즈 (루트 `pose.json`, 상태 엔트리이므로 형식은 올리지 않음)는 `Project::pose()` (읽을 수 없으면 오류, 엔트리는 바이트열 그대로 유지)와 `with_pose(Some(&pose))` (`None`이면 엔트리 삭제)로 읽고 씁니다. `yolu_io::pose::StoredPose`는 휴지 포즈와의 차이 (본은 이름 경로, BlendShape는 메시 이름과 이름의 조합)이며 범위 초과·숫자가 아닌 값·단위 회전이 아님·중복·상한 초과 (본 4096·BlendShape 4096)가 있으면 엔트리 전체를 거부합니다. 독립 실행형 0.3.x는 알 수 없는 엔트리로 바이트열 그대로 유지하고, 0.4.x까지의 Unity 브리지는 알린 뒤 저장 시 제외합니다 (포즈만 손실). 배포용 사본에서는 `Removal::ModelReference`와 함께 제외합니다.
- `Project::mesh_map(set_id, kind, max_bytes)`는 세트의 메시 맵 (`meshmap-<種類>.bin`, 버전 1〜3)을 예산 제한과 함께 읽습니다. 형식 1·2는 루트 엔트리, 형식 3 이후는 세트 아래에 있습니다. `with_mesh_map(set_id, map)`은 파생 데이터만 교체해 버전 3으로 기록하고 문서와 알 수 없는 엔트리는 보존합니다. 형식 7에만 쓸 수 있으므로 이전 형식은 먼저 `upgraded`로 마이그레이션합니다 (형식 5·6의 메시 맵은 마이그레이션 시 버전 2·슬롯 1개를 유지하며 교체된 항목부터 버전 3이 됨).
- `GenerationStore`는 복구 세대 저장소입니다 (0.4.x까지의 Unity 브리지 `GenerationStore`와 같은 디스크 구조: `current`·`previous`·`generations/<世代>/manifest.sha256`·`contents/<SHA-256>.bin`, 헤더 `DOTPAINT-MANIFEST-1|2`. 0.4.x까지의 Unity 브리지가 작성한 세대는 이 저장소에서 읽을 수 있음. 반대로 `sets/<ID>/` 아래의 중첩 이름 (열었던 `.ylp`의 합성 PNG 등)을 포함한 세대는 0.4.x까지의 Unity 브리지가 읽지 못함). `commit`은 세대를 만들고 기록 내용을 다시 읽어 확인한 뒤 세대 이름으로 이름을 바꾸고, `previous`를 교체한 다음 마지막으로 `current`를 교체합니다 (도중 충돌해도 `current`는 이전 세대로 읽을 수 있음. 확정하지 않은 작성 중 데이터는 실패 시 정리). 바뀌지 않은 엔트리는 내용 식별자로 세대 사이에 공유하며, `keep`을 전달하면 확정 후 `current`·`previous`를 보호하며 초과한 오래된 세대만 삭제합니다 (정리 실패는 확정된 저장을 취소하지 않음). `expected`에 식별자를 전달하면 외부 작성자가 `current`를 변경한 경우 거부합니다 (`Changed`). 배타성은 OS 잠금으로 처리합니다 (다른 작성자가 보유하면 기다리지 않고 `Busy`). `list`는 세대 목록 (최신순. manifest와 각 엔트리의 존재·길이만 확인하며 손상 세대에는 이유 표시), `load_generation`은 이름으로 선택한 세대를 모든 엔트리의 해시까지 검증해 읽으며, `remove_generation`은 세대 1개를 폐기합니다 (`current`·`previous`를 남은 세대 중 가장 최신으로 다시 연결한 뒤 삭제하고 사용되지 않는 공유 내용도 삭제). `Project::from_entries`는 세대에서 읽은 엔트리를 그대로 `Project`로 만듭니다 (작은 엔트리만 메모리에 두고 나머지는 저장소 내용 파일을 참조). 기록과 검증 모두 스트리밍이며 (엔트리 전체를 메모리로 읽지 않음), 양의 상한은 `with_limits`로 지정합니다 (아래 “큰 문서”). `RecoveryInfo`는 세대에 첨부하는 목록용 `recovery.json`입니다.
- `Archive`는 메모리 ZIP의 외부 구조만 검증하는 저수준 API입니다 (`.ylsmart`·`.ylbrush`·에셋과 기존 구조 (`YLP-1`〜`3`)의 .ylp. `YLP-4`는 읽지 않음). `Package`는 .ylp 외부 구조를 스트리밍으로 읽고 씁니다 (`YLP-1`〜`4`). 각 정본이나 리소스까지 검증해야 하면 `Project`를 사용합니다.

## core 변환과 합성 PNG

`NativeDocument::to_core()`는 C# `DocumentBinary.Read`와 같은 의미로 정본을 core 문서로 만듭니다.

| 정본 | core |
|---|---|
| 레이어 종류 (래스터·채우기·보정·그룹), 중첩, 통과·분리 (혼합 모드) | 레이어 배열과 부모. ID·이름·표시·불투명도·26개 혼합 모드·클리핑 |
| 래스터 마스크 (활성화·반전·밀도·픽셀) | 마스크 |
| 레이어 잠금 (버전 12. 속성 플래그 비트 1과 직후 int. 투명 영역 1·픽셀 2·위치 4·전체 8) | `LayerLocks`. 불러오기 마지막에 `set_locks_for_load`로 설정. 잠금 없는 레이어는 기록하지 않으며 잠금 없는 문서는 버전 11까지와 같은 배열 |
| 채널별 표면 (Color〜Emission과 사용자 채널), 활성 플래그, 비활성 채널의 픽셀 | 레이어 채널의 표면과 활성 상태 |
| 채널별 혼합 모드·불투명도 (버전 14) | `ChannelBlend` |
| 채우기의 채널별 값과 활성 상태 | 채우기 값과 활성 상태 |
| 보정 (반전·레벨 보정·색조/채도/명도. 버전 24부터 그라데이션 맵·톤 곡선·색상 균형·밝기/대비·2진화·포스터화 포함)과 대상 채널 | 보정 설정과 대상 |
| Normal 출력 설정 (버전 7) | `NormalSettings` |
| 사용자 채널 목록 (버전 22) | 문서 채널 목록 (번호·이름·종류·색 공간·기본값) |
| 레이어·그룹의 자 (버전 35. 1개 레이어당 최대 64개) | 레이어의 자 (`Ruler`) |
| 레이어 세트 목록 (ID·이름), 채널별 출력 할당 (머리 부분), 레이어 소속 (레이어 끝의 `set`) (버전 36) | 레이어 세트와 출력 할당, 레이어 소속. 불러오기 마지막에 `set_layer_sets_for_load`로 설정. 수·ID·할당 배열·참조 ID·그룹 하위 항목 소속이 맞지 않으면 열기 거부 |

문서·레이어 ID와 투명 픽셀의 RGB를 보존하며 불러오기를 Undo 기록에 남기지 않습니다. 불러오기 예산은 core 픽셀 예산 (256 MiB)이며 초과하면 레이어·타일을 첨부해 거부합니다.

`core_issues()`는 변환을 거부하는 항목을 레이어 기능마다 1개 (`layers[2].adjustment.gamma（調整の種類が使わない値が既定ではない）` 형식) 반환합니다. 대상은 core에 없는 항목, 타일 외곽의 0이 아닌 패딩, core 예산 초과, **보정 종류에서 사용하지 않는 값이 기본값이 아닌 정본**입니다. 마지막 항목은 C# 리더가 종류별 생성 방식으로 알림 없이 기본값으로 되돌리므로 core에 넘기면 저장 시 값이 바뀌기 때문에 거부합니다. 숨긴 레이어·비활성 마스크 내부도 거부하며 조용히 버리지 않습니다. 정본 읽기·쓰기는 계속 가능하고 거부된 문서는 원래 바이트열 그대로 저장됩니다.

`NativeDocument::from_core(&document)`는 C# `DocumentBinary.Write`와 같은 배열로 정본을 만듭니다. 사용하는 기능에 필요한 최소 버전으로 기록합니다. 레이어 세트가 2개 이상이거나, 이름 있는 레이어 세트가 있거나, 모든 채널을 1개의 레이어 세트에 할당하는 형태가 아닌 출력 할당이 있으면 **버전 36** (그렇지 않으면 필드를 기록하지 않아 레이어 세트가 없을 때와 같은 바이트열), 자가 있는 레이어 (그룹) 또는 선대칭 2D 경로가 있으면 **버전 35**, 경로 브러시 앤티앨리어싱이 “없음”이 아닌 경로가 있으면 **버전 34**, 베이크 우선순위를 기본값에서 바꿨으면 **버전 33**, 이음새 설정을 껐으면 **버전 32**, 텍스트 레이어가 있으면 **버전 30**, 포인트 그라데이션 또는 비등방성을 끈 채우기 이미지가 있으면 **버전 29**, 0.5.0 필터 (종류 70〜79) 또는 생성기 (종류 66〜70)가 있으면 **버전 28**, 경로 목록 형식으로 기록하는 경로가 있으면 **버전 27**, 색상 혼합 (일반 이외의 혼합 모드 또는 구간 혼합률 곡선)을 사용하는 그라데이션 맵이 있으면 **버전 25**, Rust 전용 색상 보정 6종의 보정 레이어나 필터 단계가 있으면 **버전 24**, Rust 전용 Generator 종류 (노이즈·그런지) 단계가 있으면 **버전 23**, 둘 다 없고 사용자 채널도 없으면 **버전 21** (Unity 0.2.0에서 읽을 수 있음), 사용자 채널이 있으면 **버전 22**입니다. 수동 ID 색상 (`Document::id_colors`)은 비어 있지 않으면 레이어 뒤 블록 (버전 19. `tag` `YLID`·개수·지문·번호 오름차순 색상)에 기록하며 버전은 바꾸지 않습니다 (비어 있으면 블록을 기록하지 않음). 읽을 때는 지문이 현재 모델과 일치하는지 보지 않고 기록된 그대로 `Document::restore_id_colors`로 복원합니다 (대조는 사용하는 쪽 담당). 치수는 8192 이하, 타일 치수는 8〜512의 2의 거듭제곱, 레이어는 최대 2048개, 그룹 중첩은 최대 64단계입니다 (`yolu_core::MAX_GROUP_DEPTH`. 리더도 같은 상한이며 초과 파일은 손상이 아닌 상한 초과로 거부). 문자열은 UTF-8로 최대 4096바이트입니다. 그리는 중인 스트로크는 저장을 거부합니다. 값 없는 채우기 채널과 그룹 활성 플래그는 합성에 영향을 주지 않고 C# 작성기도 기록하지 않으므로 기록하지 않습니다 (C# 정본을 읽고 다시 쓰면 바이트가 일치). 이전 버전이나 빈 타일의 디스크 배치까지 재현하는 API는 아닙니다. 원본 버전·항목·순서를 바이트까지 일치하게 복원하려면 원래 `NativeDocument::to_bytes()`를 사용합니다.

```rust,no_run
use yolu_io::{NativeDocument, Project};
let project = Project::read(&std::fs::read("sample.ylp")?)?;
let set = project.sets().iter().find(|s| s.id == project.current_set()).unwrap();
let mut core = set.document.to_core()?; // 対応外の項目があれば、編集を始める前に断る。
core.add_group("グループ", None)?;
let native = NativeDocument::from_core(&core)?;
let changed = project.with_document(&set.id, &native)?; // 他セット・リソース・未知エントリを保持。
# Ok::<(), yolu_io::Error>(())
```

### 큰 문서 (정본 버전 26)와 큰 .ylp (`YLP-4`) 읽기·쓰기

구조 (분할 정본·`YLP-4` 상한과 zip64·이전 리더의 거부)는 [docs/YLP_FORMAT.md](../../docs/ko/YLP_FORMAT.md)에 있습니다. 기존 상한에 들어가는 프로젝트는 1바이트도 변경하지 않습니다 (테스트는 형식 1〜6의 실제 픽스처를 읽고 다시 기록해 기존 작성기 (`Archive::to_bytes`)와 바이트까지 일치하는지 확인).
사용량 상한은 `Limits`입니다 (설정의 “레이어 메모리” 예산 `load_source_bytes`에서 결정). 초과하면 어떤 예산인지 알리고 (`Error::Budget`. 문구는 `OVER_LAYER_PIXELS_DOCUMENT`·`OVER_LAYER_PIXELS_TOTAL`이며 수치·세트 ID·상한 산출 방식은 포함하지 않음. 영어 UI는 이 문구로 구분해 번역) 압축 해제 전에 거부합니다. 기록한 내용을 다시 읽어 검증할 때는 예산으로 거부하지 않습니다 (`Limits::unbounded`). `Limits::check`는 저장한 문서를 현재 예산으로 다시 열 수 있는지 리더와 같은 계산 방식으로 추정합니다 (앱은 저장 알림에 표시). 열 때의 픽셀 상한은 core에 넣는 도중 같은 예산으로 확인합니다 (`to_core_within`).

**작성기 최적화** (`YLP-4` 전용. 기존 구조는 기존 작성기와 바이트까지 일치시키기 위해 항상 스레드 1개로 다시 압축): 같은 내용 (길이와 SHA-256)의 압축된
바이트열이 파일에 있으면 (변하지 않은 엔트리·이전 저장에서 내용이 같은 부분) 그대로 복사합니다. 4 MiB 이상 엔트리는 처음 1 MiB를 시험 압축하고 97% 미만으로
줄지 않으면 압축하지 않습니다. 줄어드는 내용은 1 MiB 블록을 별도 스레드 (최대 8개)에서 압축해 1개의 Deflate 스트림으로 이어 붙입니다 (pigz와 같은 구조: 이전 블록의
마지막 32 KiB를 사전으로 사용하고 마지막이 아닌 블록은 Sync flush로 바이트 경계에 맞춤. 출력은 스레드 수와 무관). 복사한 내용도 기록 후 다시 읽으며
길이·CRC·SHA-256을 검증합니다.

**메모리와 흐름**: 저장·열기·복구 기록에서 core 문서 (및 사본) 외에 보유하는 것은 레이어 1장분 배열과 작은 작업 영역뿐입니다 (파일 전체·zip 전체·정본
전체를 메모리에 만들지 않음).

- 저장 (`SaveTarget::save_with`)은 2회로 나눕니다. 1회차에 모든 엔트리의 길이와 SHA-256을 계산해 manifest를 만듭니다 (core 문서에서 생성하는 정본은 레이어별로 만들면서
  계산하고 리더로도 다시 읽음). 2회차에 임시 파일로 스트리밍 기록합니다. 임시 파일을 스트리밍으로 다시 읽어 검증하고 (manifest가 기록하려던 것과 같음), 교체 후의
  파일을 가리키는 프로젝트를 `SaveReport::project`로 반환합니다 (다음 저장·복구 기록은 바뀌지 않은 엔트리를 해당 파일에서 복사. 저장에 사용한 core 문서 사본은
  해제. 외부 구조·마이그레이션 후 엔트리·세트 정본은 참조를 바꾼 뒤에도 같은 엔트리를 보유하므로 다음 재구성에서 변경되지 않은 정본 골격을 다시 읽지 않음). 파일 식별자
  (SHA-256)와 백업 사본도 스트리밍으로 계산합니다.
- 열기: 모든 엔트리를 1회 스트리밍해 길이·CRC·SHA-256을 확인하고 (분할하지 않은 정본은 이때 골격도 읽음. 버전 26은 헤더와 부분 길이만), `to_core_within`에서
  다시 1회 스트리밍해 레이어별로 core 문서에 넣습니다.
- 복구 세대 (`GenerationStore`)도 스트리밍으로 기록·검증합니다. 내용 SHA-256이 같은 엔트리 (변하지 않은 세트·변하지 않은 레이어 부분)는 이전 세대와 공유하고 기록하지 않습니다.
  공유 내용은 이 도구가 스트리밍 검증한 뒤 길이와 수정 시각이 바뀌지 않았다면 다음 확정 시 해시를 다시 계산하지 않습니다 (보장 범위: 수정 시각을 바꾸지 않고 같은 길이로
  변경하는 외부 작성자는 확정 시 발견하지 못함. 열기 (`load`)에서는 항상 전체를 계산). 사용량 상한은 `with_limits(Limits)`입니다 (위와 같은 계산 방식).

**테스트 진입점**: `Thresholds::scoped` (현재 스레드 범위에서만 기존 구조 상한·zip64 임계값·정본 분할 임계값·부분 크기·작은 레이어 묶음 크기·메모리에 유지하는
크기를 줄임)로 작은 문서 상태에서 큰 형식의 모든 경로를 통과시킵니다. 리더 상한 (`Limits`)은 바꾸지 않습니다.

**측정** (`cargo test -p yolu-io --test projects bigdoc::measure -- --ignored --nocapture`, 4096²·레이어 60개 (채색 40·선화 15·노이즈 5)·레이어 픽셀 2110 MiB, 개발 빌드 (이 크레이트는
opt-level 1), Linux 컨테이너·32코어): 새 저장 13 s (파일 460 MiB. 병렬 압축 전에는 53 s), 레이어 1개 변경 후 덮어쓰기 저장 6.8 s, 열기 3.4 s + core 변환
6.5 s, 복구 기록 1회차 5〜11 s (2110 MiB 기록)·2회차 2.2 s (기록량 44 MiB). 저장·복구 기록의 최대 RSS 증가량은 60 MiB 이하입니다 (열기는 core 문서만큼
증가).

현재 세트의 Color 합성을 PNG로 만드는 예입니다 (출력 위치는 새 파일).

```sh
cargo run -p yolu-io --example composite_png -- sample.ylp output.png
```

`composite_png(&core)`는 아래쪽 원점 RGBA를 PNG의 위쪽부터 시작하는 행으로 배열하고, 0.4.x까지의 Unity 브리지 `RgbaPng`와 같은 적응형 필터·청크 배치로 출력합니다. `composite_pngs(&core)`는 어느 레이어에서든 활성화한 표준 채널별로 같은 형식의 PNG를 반환합니다 (Height → Normal 생성 설정에서 Height를 사용하면 Normal도 포함. Normal은 Unity용 OpenGL 출력). Color는 사용하는 레이어가 없어도 포함합니다. 0.4.x까지의 Unity 브리지 임포터는 `composite/<チャンネル>.png` 배열에서 세트 채널을 구성하므로 `SetSpec`에 이를 전달합니다. flate2의 zlib 백엔드 (libz-sys)를 사용합니다. 압축 결과는 deflate 구현 버전에도 의존하므로 모든 런타임·이미지에서 일치를 보장하지 않습니다.
압축 흐름은 2가지입니다. `composite_pngs`와 에셋 이미지 (.ylp 내부 PNG)는 1개 스트림이며 바이트는 이전 버전과 같습니다. `composite_png`와 텍스처 내보내기 (`export`)는 필터링한 행 스트림이 1 MiB를 초과하면 1 MiB 블록으로 나눠 병렬 압축한 뒤 1개의 zlib 스트림으로 연결합니다 (블록은 이전 32 KiB를 사전으로 사용하며 마지막이 아니면 Sync flush로 종료. Adler-32는 블록별로 계산해 결합). 픽셀은 같고 일반 PNG로 읽을 수 있으며 바이트는 스레드 수와 무관하지만 1개 스트림보다 조금 큽니다. 1 MiB 이하 이미지는 2가지 방식이 바이트까지 같습니다.

## PSD・PSB

`psd`는 0.4.x까지의 Unity 브리지와 같은 RGB8 PSD 코덱입니다. `psd::Document`·`Layer`·`Mask`·`Adjustment`는 core 문서에 의존하지 않는 데이터 타입이며 레이어와 RGBA 행은 위에서 아래 순서입니다. 이름, 양수의 고유 PSD 레이어 ID, 캔버스 밖 픽셀, 투명 픽셀 RGB를 보존합니다.

```rust,no_run
use yolu_io::psd::{self, CompatibilityMode, Limits};
let limits = Limits::default();
let origin = psd::read(&std::fs::read("sample.psd")?, &limits)?;
for note in origin.diagnostics() {
    eprintln!("{}: {}", note.code, note.message);
}
if origin.mode() == CompatibilityMode::EditableRaster {
    let mut document = origin.to_core()?; // 変換対象外の情報があれば理由を添えて拒否。
    document.add_layer("新しいレイヤー")?;
    let edited = psd::Document::from_core(&document)?;
    let bytes = psd::write_edited(&origin, &edited, &limits)?;
    // bytesを新規出力または外部改変検知・一時ファイル置換を備えた保存処理へ渡す。
}
# Ok::<(), yolu_io::Error>(())
```

| 요소 | 읽기·내보내기 |
|---|---|
| PSD v1 RGB8, raw / PackBits RLE | 읽기 가능. 내보내기는 raw. 통합 이미지는 흰 배경의 RGB와 원래 투명도를 저장 |
| 래스터, 26개 혼합 모드, 클리핑, 표시·불투명도, Unicode 이름·ID | 읽기·쓰기. 누락·잘못됨·중복 ID를 이름으로 복구하지 않음 |
| 래스터 마스크 | 사각형·기본값 0/255·활성/비활성·밀도·픽셀 보존 |
| 그룹 | 중첩, 통과·분리, 마스크, 그룹과 구분자 ID 보존. core 그룹으로 변환 (중첩은 PSD 예산의 최대 32단계) |
| 보정 | 반전, RGB 일괄 레벨 보정, 마스터 색조/채도. PSD 정수 간격으로 보존. 채널별 보정·Colorize 등은 보호. 색상 보정 6종은 `grdm` (그라데이션 맵)·`curv` (톤 곡선)·`blnc` (색상 균형)·`brit`＋`CgEd` (밝기/대비)·`thrs` (2진화)·`post` (포스터화). 간격 사이 값은 반올림하지 않고 거부하며, 그라데이션 맵의 색상 혼합 (혼합 모드·혼합률 곡선)과 값 곡선은 엄격한 내보내기에서는 거부하고 베이크 내보내기에서는 정지점 배열로 펼침 (근사치. 차이는 기록 전 확인 창에 표시). 표현할 수 없는 내용 (노이즈형 그라데이션·점이 16개 초과 또는 양 끝이 0과 255가 아니거나 인접 간격이 6 미만인 곡선·이전 방식 밝기/대비 등)은 `PreserveOnly`로 원본 보존 |
| 단색 채우기 `SoCo` | RGB 색상 보존. 8bit 미만 소수 부분은 반올림해 알림. 픽셀 캐시를 사용하지 않는다는 점도 알림 |
| 레이어 잠금 `lspf` | 투명·픽셀·위치·전체 보존. 지원하지 않는 비트는 알림 |
| 렌더링과 관계없는 알려진 메타데이터, sRGB IEC61966-2.1, 1:1 픽셀 비율 | 편집 가능으로 수용하고 내보내기에 포함되지 않는 정보는 `NotCarriedIntoExport`로 알림 |
| PSB, RGB8 이외, ZIP 압축, 알 수 없는 태그·보정, 효과, 텍스트, 스마트 오브젝트, 벡터 마스크 | `PreserveOnly`와 이유를 반환하고 원본 전체만 보존. PSB 디코딩·새로 생성은 하지 않음 |
| 구조 손상·예산 초과 | `Rejected`. 원본 보존 상한 이내라면 원본 바이트는 유지 |

`psd::read` / `read_stream`은 `ReadResult`를 반환합니다. 편집 가능한 경우에만 `document()`에 값이 있습니다. `original_bytes()` / `copy_original_bytes()`는 원래 파일 전체이며 원본 보존 예산을 초과했을 때만 보유하지 않습니다. 알 수 없는 정보를 편집 후 파일에 부분적으로 덧붙이는 방식이 아닙니다. **가져온 원본을 편집해 저장하려면 `write_edited`를 사용합니다**. `PreserveOnly`·`Rejected`는 여기서 거부합니다. `write`는 새로 만든 PSD 스냅샷용입니다.

원본 복사는 백업·보존용이며 외부에서 변경된 파일을 덮어쓸 권한을 부여하지 않습니다. PSD API는 파일시스템을 조작하지 않습니다. 저장 대상의 외부 변경 감지·백업·마지막 한 번의 교체는 호출자의 책임이며, .ylp용 `SaveTarget`은 PSD에 사용할 수 없습니다.

`ReadResult::to_core`와 `psd::Document::to_core/from_core`는 Color 사본을 변환합니다. 대상은 래스터·그룹 (중첩, 통과·분리)·단색 채우기·보정 (반전·레벨 보정·색조/채도·색상 보정 6종)·클리핑·래스터 마스크 (활성/비활성·밀도)·레이어 잠금·26개 혼합 모드·표시·불투명도입니다. 불러오기 시 Undo 기록을 남기지 않으며 PSD 레이어 ID와 그룹 구분자 ID는 core의 영구 ID에 넣어 다시 출력합니다. 이름이 같은 레이어도 ID로 구분합니다. 배열은 0.4.x까지의 Unity 브리지 가져오기와 같습니다 (아래에서 위, 그룹 내용은 그룹 바로 아래).

- `from_core` (core에서 PSD로): 위 내용을 PSD 형식으로 기록합니다. 잠금은 `lspf`에 투명 영역·픽셀·위치·전체 (`0x80000000`만 기록) 그대로 기록하며 투명 영역 잠금은 레이어 레코드 플래그의 비트 0에도 기록합니다. 마스크는 캔버스와 다른 부분의 경계 사각형 및 사각형이 더 작아지는 쪽의 기본값 (255 또는 0)으로 기록합니다. 레이어 혼합 모드와 불투명도는 Color에서의 실효 값 (채널별 설정이 있으면 그것)으로 기록합니다. PSD가 보유할 수 없는 내용은 병합하거나 조용히 버리지 않고 레이어 이름과 기능별 이유로 거부합니다. 반전된 마스크 (PSD에 비파괴 반전 없음), 클리핑된 그룹, 반투명 채우기, PSD 간격 (0〜255 정수·감마는 1/100·1도·1%. 색상 보정은 위치 1/4096·중간점 1%·불투명도와 곡선 점 1/255·정수 슬라이더) 사이의 보정 및 PSD 범위 밖 레벨 보정, 레이어가 적용되는 다른 채널의 실효 합성이 Color와 다른 경우 (PSD 레이어는 1조만 보유 가능. 적용 채널은 명시 설정이 있는 채널과, 보정이면 활성 채널, 그룹이면 표준 채널. Color만 레이어 값과 다른 보정·그룹도 거부), Color 이외 채널의 픽셀·활성 플래그·채우기 값, 비활성 Color (보정은 Color에서 비활성인 것), 필터·Generator 단계 (비활성·작동하지 않는 단계도 포함. 효과를 적용한 합성은 통합 이미지에만 들어가 레이어 픽셀과 달라지기 때문), Anchor, 경로입니다. 보정 대상 채널은 PSD가 보유할 수 없어 기록하지 않으며, 다시 불러오면 지원하는 모든 표준 채널에 적용되는 보정이 됩니다 (0.4.x까지의 Unity 브리지 가져오기와 동일). `psd::export_blockers(&document)`는 거부할 레이어와 이유 (`Refusal`) 전체를 반환해 UI가 표시 언어에 맞춰 설명할 수 있게 합니다 (`from_core`는 일본어 진단으로 첫 1개를 반환).
- `to_core` (PSD에서 core로): 위 내용을 core 레이어로 만듭니다. 캔버스 밖 픽셀·캔버스 밖의 기본값과 다른 마스크 값은 잘라내지 않고 거부합니다 (`core_issues()`). 레이어 잠금 (lspf 비트 0·1·2·31)은 core 레이어 잠금에 넣습니다 (`set_locks_for_load`. 불러오기 마지막에 설정하며 기록을 남기지 않음. `from_core`의 역변환이며 전체는 개별 비트를 더하지 않음). `.ylp`에도 기록할 수 있으므로 (버전 12 배열) 가져오기에서 잠금을 제거하거나 거부하지 않습니다.

core 출력 사각형은 타일 범위가 되며 불투명도는 가장 가까운 1/255로 반올림합니다. 원본의 압축이나 사각형까지 바이트를 일치시켜 복원하는 API는 아닙니다.

기본 `Limits`는 원본·출력 각각 128 MiB, 치수 8192, 캔버스 16,777,216픽셀, 레이어 레코드 256개 (구분자 포함), 디코딩 256 MiB, 메타데이터 4 MiB, 이름 4096 UTF-16 단위, 진단 128건, 그룹 32단계입니다. `write` (엄격한 내보내기의 무압축 작성기)는 할당 전에 구조·픽셀·출력 길이를 검증합니다. `read`는 전체를 메모리에서 처리하므로 스트리밍 방식의 대규모 문서용이 아니며, 이러한 제한은 프로세스 전체 메모리 사용량을 보장하지 않습니다. 실제 규모 내보내기 (아래) 상한은 `Limits::for_export(budget)`가 호출자 예산 (앱에서는 설정의 “레이어 메모리”)으로 결정합니다.

`read`는 통합 이미지를 참조 합성과 비교합니다. 일반 합성만으로 차이가 크면 편집을 중단하며, 혼합 모드·마스크·그룹·보정 등이 있으면 `CompositeDiffers`로 외관 차이를 알립니다. 참조 합성은 YoluPainter 수식이며 Photoshop/CSP의 외관 재현을 보장하지 않습니다. 색상 보정 6종의 참조 합성도 core 수식을 그대로 사용하므로 이 비교는 PSD 기록과 읽기 사이의 불일치를 확인하는 것이며 Photoshop 또는 CLIP STUDIO 수식과의 독립 대조가 아닙니다 (내보낸 통합 이미지는 이 도구 수식의 결과이며 Photoshop이 보정 레이어를 재평가하면 외관이 달라질 수 있음). 재생성·검증 조건은 [PSD 픽스처](tests/fixtures/psd/README.ko.md)를 참고하세요.

### 실제 규모 내보내기 (`ExportPlan::write_psd`·`psd::verify_stream`)

베이크 내보내기 (`plan_export` → `ExportPlan`)에는 모든 레이어를 메모리에 만드는 `build` 외에 레이어를 1장씩 스트리밍 기록하는 `write_psd(&document, &ctl, &mut out, compression)`이 있습니다. `out`은 `Write + Seek`입니다 (쓰기 시작 위치는 맨 앞). 먼저 헤더와 모든 레이어 레코드 (사각형·채널 길이는 임시 값)를 기록하고, 레이어 픽셀을 PSD 레코드 순서로 1장씩 평가·압축·기록한 뒤 즉시 버립니다. 모든 레이어 기록 후 통합 이미지를 만들어 기록하고 마지막에 맨 앞으로 돌아가 확정된 레코드를 다시 씁니다. 메모리에는 레이어 1장분과 레코드 표만 보유하며 전체 레이어 픽셀 합계에는 상한이 없습니다 (Normal 베이크와 평면 1장은 각각 기록한 레이어에서 통합 이미지를 생성하거나 레이어 1장 자체이므로 모든 레이어를 메모리에 구성하고 합계를 예산으로 제한). `ExportControl`은 취소 플래그, `source_budget` (설정의 “레이어 메모리”. 레이어 레코드는 예산 1 MiB당 1건으로 256〜32767건, 캔버스는 예산 내 범위, 변 길이는 30000, `None`이면 C#과 대응하는 고정 상한), `max_file_bytes` (기본값과 상한은 PSD의 2 GiB. 압축 후 크기를 기록하면서 확인. 모든 레이어를 메모리에 만드는 경로도 동일)를 보유합니다. 예산·형식 상한 때문에 기록할 수 없으면 `ExportError::Overrun(Overrun)` (캔버스 픽셀 수·변 상한·레이어 레코드 수와 상한·레이어 이름을 포함한 예산 초과·2 GiB)으로 반환하며 UI가 유형별로 언어에 맞는 문장을 만듭니다. `Written`은 기록 바이트 수·레이어 수, 기록 바이트열 대조용 `Checksum` (선두 재기록 전후를 고려해 앞부분과 뒷부분을 별도로 계산한 CRC-32와 길이. `Checksum::matches(&mut reader, cancel)`로 다시 읽은 파일이 기록한 그대로인지 확인)을 보유합니다. 작성 중 파일의 삭제는 호출자가 담당합니다.

압축은 `Compression::Raw` (0.4.x까지의 Unity 브리지와 바이트 일치. `write`·엄격한 내보내기는 이것을 사용) 또는 `Compression::Rle` (PackBits. 레이어와 마스크는 채널 1개씩 압축하며 작아지지 않으면 무압축. 통합 이미지는 전체가 1개)입니다. 메모리 문서는 `write_with(&document, &limits, compression)`로 기록할 수 있습니다.

`psd::verify_stream(&mut reader, cancel)`는 기록한 PSD를 끝까지 스트리밍으로 다시 읽어 검증합니다. `import_copy`와 같은 리더 (레이어 레코드·채널 디코딩·통합 이미지 읽기)를 거치지만 core 문서를 만들지 않으므로 베이크한 픽셀이 문서 예산을 초과해도 검증은 중단되지 않습니다. 메모리는 압축 채널 1개분과 통합 이미지 1장입니다 (레이어·마스크 채널은 픽셀을 보유하지 않고 행을 풀어 검증. ZIP 채널만 표면 1장). 헤더 치수는 PSD 상한 30000까지이며, 통합 이미지 공간은 남은 파일이 해당 압축의 최소 길이를 만족할 때만 할당합니다 (손상된 치수대로 먼저 할당하지 않음). 모든 레이어·마스크·통합 이미지의 모든 행 디코딩 (행은 병렬로 풀고 통합 이미지는 표면 1장분 압축 데이터를 한 번에 읽음), 레코드 길이와 데이터 길이 일치, 파일 끝과 통합 이미지 끝 일치, 가져오기 시 제외·변경되는 내용이 없음을 확인합니다 (기록 픽셀과 문서 픽셀의 일치는 검사하지 않음. 기록 바이트열과의 일치는 `Checksum::matches`). 다시 읽기와 대조를 1회 읽기로 수행하려면 리더를 `Checksum::recount(reader)` (`Recount`)로 감싸 `verify_stream`에 전달하고, 이후 `Recount::finish(cancel)`로 대조합니다 (검증이 읽은 바이트를 즉시 계산하고 건너뛴 구간과 나머지만 추가로 읽음. `psd::check_written`은 이 방식).

### 사본으로 가져오기 (`psd::import_copy`)

원본 보존 읽기 (`read`)는 PSD 정보를 알림 없이 버리지 않기 위해 편집할 수 없는 내용이 1개라도 있으면 원본 보존만 수행합니다. 원래 PSD에 다시 기록하지 않는 용도 (앱의 불러오기)에는 별도 진입점 `import_copy(&mut reader, &CopyOptions { source_budget, cancel })`가 있습니다. `Read + Seek`에서 스트리밍으로 읽고 원본 바이트열은 보유하지 않습니다 (추가 정보는 레이어별·태그별로 읽고 버리며, 레이어 픽셀은 1장씩 디코딩해 core에 넣은 뒤 즉시 버림). 원본 보존 상한 (128 MiB)은 적용되지 않으며, 레이어 수·캔버스·레이어 픽셀·레이어 1장의 추가 정보 상한은 호출자가 전달하는 `source_budget` (앱에서는 설정의 “레이어 메모리”)에서 결정됩니다 (레이어 수는 예산 1 MiB당 1장으로 256〜32767장). 문서 레이어 수 (그룹은 세고 구분자 레코드와 제외할 레이어는 제외)가 `.ylp` 상한 2048장을 초과하는 PSD는 예산에 관계없이 `LayerCountOverLimit`로 거부합니다. 결과는 `CopyOutcome`이며, 가져올 수 없는 이유 (`CopyRefusal`: PSB·RGB8 이외·예산 초과·손상·레이어 없음) 또는 core 문서와 알림 (`ImportNote`)입니다.

알림은 기능 (`ImportFeature`)과 처리 (`ImportAction`)마다 1건이며 해당 레이어 이름 (처음 8장)과 개수가 붙습니다. **무시** (외관과 내용에 영향 없는 정보), **제외** (레이어 픽셀은 유지하지만 해당 기능 설정·원래 데이터는 보유하지 않음. 픽셀 없는 미지원 보정은 레이어 전체), **변경** (평가할 수 없는 효과 등 합성이 PSD 통합 이미지와 달라질 수 있는 항목. 레이어 픽셀 그대로 가져옴)으로 분류하며 표는 [docs/PSD.md](../../docs/ko/PSD.md)에 있습니다. 레이어 ID는 누락·중복·잘못된 레이어에만 이름으로 보정하지 않고 새 ID를 부여합니다 (유효하고 고유한 ID는 순서와 관계없이 유지). 가져온 문서 합성을 행 띠마다 PSD 통합 이미지와 대조해 최대 차이와 차이가 있는 픽셀 수를 알립니다. `read`처럼 일반 합성의 큰 차이로 가져오기를 중단하지 않고 차이만 알립니다 (캔버스가 예산에 비해 크거나 통합 이미지가 없거나 읽을 수 없으면 대조하지 않고 그 사실을 알림). 읽는 압축은 raw·PackBits RLE·ZIP·예측 ZIP입니다. 이름 상한 (4096 UTF-16 단위)을 초과한 레이어 이름은 상한까지 잘라 가져오며 제외 항목으로 `LayerNameTruncated`를 알립니다 (원본 보존 `read`는 원본 이름을 변경해 다시 기록할 수 없으므로 거부). 캔버스 밖으로 나가는 래스터 레이어는 캔버스 내부 범위의 크기만큼 메모리를 잡고 예산도 그 크기로 확인합니다 (채널을 행 1개씩 풀어 범위 안 열만 복사. 범위 밖은 알파에 0이 아닌 값이 있는지만 확인하고 버림). 마스크는 기존처럼 전체를 보유합니다.

## 브러시 형식 가져오기

`brushes`는 다른 앱의 브러시 파일을 core 브러시 (`yolu_core::Brush`)로 변환합니다. 앱 진입점은 1개이며 메모리 바이트열은 `import_bytes`를 사용합니다.

```rust,no_run
use yolu_io::brushes::{import, Unrepresented};

let set = import(std::path::Path::new("chalk.abr"))?;
for brush in &set.brushes {
    // brush.brush は core のブラシ。筆先・質感の画像は Arc で共有する（同じ筆先を使うプリセットは同じ画像を指す）。
    for note in &brush.unrepresented {
        println!("{}", note); // 表せなかった設定（note.english() は英語）
    }
}
# Ok::<(), yolu_io::brushes::BrushImportError>(())
```

**표현할 수 없는 설정을 버리지 않습니다.** 원래 앱에는 있지만 core 브러시로 표현할 수 없는 설정 (최소 지름, 노이즈, 젖은 가장자리, 브러시 자국별 텍스처, 개수 지터, 1축만의 분산, 필압 이외 일부 제어, 이중 브러시 뒤집기, 컬러 브러시 색 등), 근사한 설정 (호스 셀 선택 방식, 스파이크 모양, 회색 변환), 읽지 못한 설정은 `Unrepresented`에 타입으로 기록합니다. 브러시 설정은 `ImportedBrush::unrepresented`, 파일 전체 항목 (읽지 못한 설정·패턴 섹션, 건너뛴 섹션, `.pat`의 사용할 수 없는 패턴)은 `ImportedSet::notes`에 1회만 기록하며 브러시마다 복제하지 않습니다 (브러시 수에 비례해 늘어나는 것을 방지하고 UI에서 관계없는 브러시에 다른 패턴의 실패가 나열되지 않게 함). 문장은 종류와 값으로 UI가 언어별로 생성합니다 (`Display`는 일본어, `english()`는 영어). 프리셋 구조가 손상되어 가져오지 못한 항목은 `ImportedSet::skipped`에 이유와 함께 기록합니다 (ABR C# 구현은 조용히 건너뛰었음). core 확장 (팁 뒤집기·펜 축 회전·텍스처 혼합 방식 8종)은 C# 구현이 “미지원”으로 처리했던 것도 복사합니다. 배경색은 브러시에 포함되지 않으므로 가져오기에서는 색상 변화의 `secondary`를 변경하지 않습니다.

**신뢰할 수 없는 파일.** 다운로드한 브러시를 읽는 상황을 전제로 패닉을 일으키지 않고, 개수나 길이 선언만으로 미리 할당하지 않습니다. 파일은 최대 256 MiB (`.sut`는 128 MiB, VBR은 64 KiB, 읽기 전 거부), 풀어낼 팁·패턴 픽셀 합계는 최대 256 MiB입니다 (PackBits는 2바이트를 128픽셀로 풀 수 있으므로 작은 파일이 거대한 이미지가 되는 구조를 예산으로 거부. 텍스처 “반전”으로 새로 만드는 이미지도 패턴마다 1개를 공유하며 예산에서 차감). 팁·패턴 개수는 최대 1만 개입니다 (ABR 버전 6 이후의 팁·패턴 섹션 포함. 픽셀 1개인 팁은 픽셀 예산으로 막히지 않음). 디스크립터는 깊이 32·값 100만 개까지입니다. 파일 전체 알림에 나열하는 알 수 없는 섹션 종류는 최대 64개입니다 (나머지는 섹션 수를 1개 알림으로 표시). 유한하지 않은 수 (NaN·무한대)가 있는 설정 섹션은 읽을 수 없는 것으로 처리하고 팁만 알림과 함께 가져옵니다. 이름은 제어 문자를 제거하고 최대 128자로 제한하며, 섹션 키·타입 이름 같은 형식 식별자의 제어 문자는 `?`로 바꿔 UI 문장에 제어 문자가 들어가지 않게 합니다. UI 문장에는 오프셋 등의 내부 수치를 표시하지 않습니다 (`Fault` 값에는 유지). 손상 사례는 모든 바이트 변경·모든 길이에서 자르기·극단값·삽입과 삭제·쓰레기 입력으로 테스트합니다 (`tests/brushes/brush_import_hostile.rs`, 약 25만 가지에 `.sut` 약 32만 가지 추가). `.sut`는 SQLite를 메모리상 읽기 전용·방어 모드로 열고 길이·명령 수·시간 상한을 적용합니다 (확장 로드 함수를 활성화하지 않아 SQL의 `load_extension()`은 거부됨). 정해진 표와 읽을 열만 조회합니다 (`src/brushes/sut/db.rs`). 소재 C2F는 SQLite 본체를 거치지 않고 직접 읽습니다 (`src/brushes/sut/c2f.rs`. 블록 수·행 크기·트리 깊이·이미지 크기에 상한을 두며, 만드는 행 크기 (256 MiB)와 풀어낼 픽셀 (256 Mi 픽셀)은 1개의 `.sut` 가져오기 전체 합계로 제한. 표준 압축 해제기로 열지 못한 첫 블록은 읽지 않음). 손상되었거나 합계를 소진한 뒤에는 소재 이미지가 없는 것으로 처리합니다 (손상 시험은 `tests/brushes/brush_import_sut_layer.rs`의 약 3400가지와 상한·거부 이유별 테스트).

**0.4.x까지의 Unity 브리지 (C#)와 대조.** `tests/brushes/brush_golden.rs`는 수작업 88개 사례, 동봉된 Krita GIMP 형식의 실제 파일 37개, 수작업 사례를 손상시킨 약 1.1만 입력을 C# 리더 (`Runtime/Core/Brushes` (Unity 브리지 태그 0.4.0, 0.5.0에서 제거))에 통과시킨 결과와 비교합니다 (`tests/fixtures/brushes/`. 0.4.x까지의 Unity 브리지 출력을 이어받았으며 재생성 시 Rust 출력 사용). 가져오기 성공/거부 여부와 가져온 설정 (수치는 모든 비트, 팁·텍스처·이중 브러시 픽셀은 지문)이 같아야 합니다. C#이 검증 예외로 종료되는 입력 (NaN 브러시 크기 등)과 유한하지 않은 수가 있는 설정 섹션은 비교하지 않습니다. PNG 팁은 Unity 엔진 (`Texture2D.LoadImage`)을 거쳐 Core 밖에 있으므로, 동봉 PNG 39개의 커버리지를 다른 디코더 (Pillow)로 같은 식에 통과시킨 지문과 비교합니다 (`tests/brushes/brush_bundled.rs`). Unity 엔진 자체와는 대조하지 않았습니다.

**동봉 브러시 팁.** `brushes::bundled::krita4()`는 Krita 4 기본 팁 76개 (CC0 1.0. 원본 바이트열·출처·SHA-256은 리프 크레이트 `yolu-brush-sets`)를 가져오기와 같은 리더로 브러시로 만듭니다 (반경을 4〜40으로 제한하고 필압으로 불투명도를 바꾸지 않음). 원본 그대로 `include_bytes!`로 보유합니다. 11.5 MB이며 실행 파일에서는 사용하지 않으면 읽지 않고, 설치 프로그램 압축 후 배포 크기 증가는 약 4 MB입니다. 별도 크레이트로 분리한 이유는 `yolu-io`를 다시 빌드할 때마다 데이터를 다시 읽거나 `yolu-io`의 rlib에 섞지 않기 위해서입니다.

## 리소스와 지원하지 않는 내용

이미지는 RGBA8 PNG를 디코딩해 치수와 아래 행부터의 픽셀 해시를 검증합니다. 스마트 머티리얼·스마트 마스크·머티리얼·브러시는 내장 파일 전체를 보존합니다. 내부 manifest, 정본, 종류, 채널, 이미지, 브러시 schema·이미지 참조도 검증합니다.

브러시 설정의 렌더링 의미, .ylp 내부 원본 PSD·합성 PNG·메시 맵·화면 설정의 자동 디코딩은 미구현입니다 (효과 실행은 core의 `Document`가 담당하고 메시 맵과 이미지는 `Document::set_effect_inputs`로 전달. 이미지 리소스 입력은 `Project::image_inputs`). 독립 PSD는 위 API로 읽고 쓸 수 있습니다. 이러한 데이터는 건너뛰어 폐기하지 않고 원본 엔트리로 유지합니다. `notes()`를 호출자 UI에 표시할 수 있습니다. 이미지 리소스 이외의 모든 PNG를 디코딩하는 API는 아닙니다.

형식 10 이후, 정본 버전 37 이후와 결번 31, 알 수 없는 열거 값·알고리즘 버전은 이유와 함께 거부합니다. 암호화·분할 ZIP, RGBA8 이외의 리소스 PNG는 처리하지 않습니다. ZIP64는 `YLP-4`만 지원합니다. 기존 구조 (`YLP-3`까지)는 엔트리 1개 512 MiB·압축 해제 총량 768 MiB·엔트리 1000개이며 `YLP-4` 상한은 아래 “큰 문서”를 참고합니다. 디코딩 리소스는 최대 768 MiB입니다. 전체를 메모리에 올려 읽는 정본 (`NativeDocument::read`·`from_core`)은 최대 512 MiB입니다. 이는 데이터 양의 상한이며 프로세스 최대 메모리 사용량을 보장하지 않습니다.

## 저장

`SaveTarget::open` (기본 예산)·`open_within(path, limits)`은 파일을 스트리밍으로 열고 SHA-256·길이·수정 시각을 기록합니다 (읽는 중 길이나 수정 시각이 바뀌면 거부). 외부 변경은 내용 (SHA-256과 길이)으로 구분하며 수정 시각만 바뀐 경우 (동기화 도구 등)는 변경으로 취급하지 않습니다. `create`는 새 저장 전용입니다. 저장은 디스크에 쓰기 전에 모든 엔트리를 계산·검증하고 (1회차), 대상과 같은 폴더의 임시 파일로 스트리밍 기록한 뒤 `sync_all`, 다시 읽기 검증, 외부 변경 재확인을 거쳐 `rename`으로 한 번만 확정합니다. 교체에 실패해도 삭제 후 이동하는 방식으로 바꾸지 않습니다. 변하지 않은 엔트리는 열린 파일에서 스트리밍 복사합니다. 이를 위해 열린 .ylp 핸들을 유지하고 (큰 엔트리만. 모두 작으면 연 뒤 닫음), 경로로 다시 열지 않고 핸들에서 위치를 지정해 읽습니다 (Unix는 `read_at`, Windows는 `seek_read`. 파일 커서를 사용하지 않아 여러 개를 읽어도 서로 위치를 움직이지 않음). 표준 방식으로 열어 유지하므로 (Windows에서도 Rust 표준 라이브러리 기본값은 읽기·쓰기·삭제 공유), 열린 .ylp를 외부에서 이름 변경·이동·삭제하거나 POSIX 교체 (다른 파일을 같은 이름으로 `rename`), OneDrive 등으로 교체해도 핸들은 열었을 당시 내용을 계속 읽습니다. 따라서 다른 이름으로 저장은 외부에서 어떤 작업을 했든 처음 연 내용으로 기록할 수 있습니다 (외부 파일은 변경하지 않음). Linux에서는 테스트로 확인했습니다. Windows (NTFS)도 표준 라이브러리 공유 기본값과 `fs::rename` 동작으로 그렇게 작동한다고 가정해 설계했지만 실제 Windows에서는 확인하지 않았습니다. 같은 이름으로 덮어쓰기는 대상이 삭제되었거나 내용이 바뀌면 거부합니다 (외부 변경을 조용히 덮어쓰지 않음). 외부에서 같은 파일을 같은 위치에 직접 덮어쓴 경우 (덮어쓰기 복사 등)에는 읽을 때마다 길이·SHA-256·CRC를 확인해 손상 엔트리로 거부합니다. 저장 검증에서 연 임시 파일 핸들은 교체 후 그대로 저장 후의 원본 위치가 됩니다 (교체 후 경로로 다시 열지 않아 검증한 파일 자체를 계속 읽으며, 교체와 다시 열기 사이에 바꿔치기되는 경쟁도 없음. `SaveReport::project`).

이 프로세스가 직접 연 핸들 때문에 교체가 실패할 수 있습니다. 교체 규칙이 POSIX가 아닌 파일시스템 (FAT·exFAT·일부 네트워크 공유)이 해당합니다. NTFS에서는 외부 도구 (백신·동기화)가 점유한 것이 일반적인 원인이며 자체 핸들은 교체를 막지 않는다고 가정합니다 (실제 Windows에서는 미확인). 교체가 공유 위반·접근 거부가 되면 우선 자체 핸들을 놓지 않고 0.3초 동안 기다리며 재시도합니다. 그동안 성공하면 저장 전 프로젝트 사본은 계속 읽을 수 있습니다. 성공하지 않을 때만 이 프로세스가 연 대상 핸들을 해제하고 남은 대기 동안 재시도하며, 교체하지 못하면 다시 획득합니다 (열었을 때와 길이가 같은 파일만. 내용은 읽을 때마다 검증). 교체에 성공하면 해제 상태로 둡니다. 저장 전 프로젝트 사본은 읽으려 하면 `SOURCE_RELEASED`로 거부합니다 (저장 후 프로젝트는 새 파일에서 읽을 수 있음). 원인이 외부 도구여도 0.3초 넘게 점유되면 마찬가지로 해제합니다 (원인 구분 불가). 앱은 열린 파일을 교체하는 저장 전에 복구 기록 완료를 기다리며, 배포용 저장 사본이 있는 동안에는 저장하지 않습니다 (해당 읽기가 저장 전 프로젝트 핸들을 사용하기 때문).

Windows 교체 (덮어쓰기·새 저장·백업 이동)는 공유 위반·잠금 위반·접근 거부일 때만 잠깐 재시도합니다. 동기화 도구·백신이 대상이나 임시 파일을 일시 점유해 생기는 실패이며 대부분 1초 이내에 해제됩니다. 대기는 10·20·40…ms로 두 배씩 늘려 300 ms에서 제한하고 총 1.5초 후 포기해 실제 실패로 반환합니다 (덮어쓰기는 처음 0.3초 동안 위의 자체 핸들을 놓지 않고 대기. 저장은 호출자 스레드에서 실행). 접근 거부는 실제 권한 부족으로도 발생하지만 그 경우 기다려도 통과하지 않아 같은 실패를 반환합니다. Unix는 열린 파일이 방해하지 않으므로 재시도하지 않습니다.

직전 버전은 `<ファイル名>-backups~/`에 `<名前>-<UTC の時刻（ミリ秒）>.ylp` 이름으로 보관합니다 (0.4.x까지의 Unity 브리지와 동일). 같은 시각 백업이 있거나 시계가 되돌아갔으면 밑줄을 추가해 이름순이 항상 최신순이 되도록 합니다. `backup_origin(path)`는 백업 폴더 안의 백업이면 원래 파일 위치를 반환합니다 (사용자가 이름을 바꿔 둔 파일이나 다른 파일의 백업은 `None`). 보관 수는 호출자가 `BackupKeep` (모두·N·0)으로 정하며 기본값은 모두 유지입니다 (`save`). `save_with`는 정리 결과를 `SaveReport`로 반환합니다. 0은 백업하지 않습니다 (기존 백업은 삭제하지 않음). 정리는 교체로 확정한 뒤에만 수행하며, 현재 백업을 포함해 N건이 되도록 해당 문서의 백업을 최신순으로 남기고 오래된 것을 삭제합니다. 사용자가 이름을 바꿔 둔 파일·다른 문서의 백업·폴더·링크는 계산하지도 삭제하지도 않습니다. 삭제하지 못해도 저장은 성공 상태이며 실패한 항목과 이유가 `prune_failures`에 기록됩니다. 이전 버전이 SHA-256 이름으로 보관한 것은 가장 오래된 백업으로 계산합니다 (그들끼리는 수정 시각순. 이름에 순서가 없으므로 동기화·복사로 수정 시각이 바뀌면 오래된 순서를 보장하지 않음). 백업은 마지막 검증 후·교체 직전에 만들며 교체까지 도달하지 못한 저장은 만든 백업 (및 만든 폴더)을 삭제합니다. 사본은 임시 이름 `.<ファイル名>.<pid>-<番号>.pending~` (백업 폴더 안)에 기록·동기화하고 내용을 확인한 뒤 최종 이름으로 덮어쓰지 않는 이동을 합니다 (강제 종료된 저장이 임시 사본을 남겨도 백업으로 계산하지 않아 보관 수를 차지하지 않음). 백업은 저장 대상과 독립된 바이트열 사본이며 하드 링크가 아닙니다. 이전 버전 저장 위치를 일반 파일이나 심볼릭 링크가 막고 있으면 대상을 변경하지 않고 `SaveConflict`로 거부합니다 (프로젝트 데이터 오류와 구별. 백업하지 않는 설정에서는 해당 위치를 건드리지 않음). 연 뒤 대상이 삭제되었다면 외부 변경으로 거부하고 사라진 파일 대신 새로 기록하지 않습니다.

새 저장 대상 (`create`)은 이름이 `.ylp` (대소문자 무관)로 끝나지 않으면 디스크를 건드리기 전에 거부합니다 (`SaveConflict`. 열린 파일 이름이 달라도 `open`으로 읽을 수 있지만 저장은 거부). 대상 폴더가 없으면 저장 시 만들고 저장이 확정되지 않았으면 직접 만든 빈 폴더만 삭제합니다 (기존 폴더와 다른 내용이 들어간 폴더는 삭제하지 않음). 마지막은 덮어쓰지 않는 이동으로 확정합니다. 확인 후 이동하는 것이 아니라 이동 작업 자체가 기존 대상이 있으면 거부합니다. Linux (glibc)는 `renameat2`의 `RENAME_NOREPLACE`, 이를 사용할 수 없는 위치와 다른 Unix는 `hard_link` 후 원래 이름을 삭제하며 (삭제하지 못해도 저장은 확정되어 성공으로 처리하고 남은 임시 파일은 후처리에서 다시 삭제), Windows는 교체 플래그 없이 `MoveFileExW`를 호출합니다. 모두 사용할 수 없는 파일시스템 (FAT 계열·일부 네트워크 공유 등)은 잠금을 사용할 수 없는 위치와 마찬가지로 거부하지 않고 다시 확인한 후 교체 이동으로 확정합니다 (그 사이 외부에서 생성되는 경쟁은 막지 못함). 외부에서 먼저 만든 파일은 덮어쓰지 않고 그대로 남깁니다. 덮어쓰기 저장은 교체 이동을 유지하며 직전까지의 식별자 검증이 보호합니다.

저장은 대상마다 1개씩이며 `.<ファイル名>.save.lock~`를 열어 OS 배타 잠금을 유지합니다. 다른 저장이 보유하면 `SaveConflict` (진행 중)로 거부하고 해당 파일을 삭제하지 않습니다. 잠금 여부는 파일 존재가 아니라 실제 잠금 보유로 결정하므로 충돌 후 남은 파일은 다음 저장을 막지 않으며 완료하면 삭제됩니다. 잠금을 사용할 수 없는 파일시스템 (잠금 획득 자체가 실패하는 위치)에서는 C# (.NET의 FileShare.None)과 마찬가지로 배타성 없이 계속합니다 (거부하면 그 위치에 저장할 수 없게 되기 때문). 이 경우도 교체 전 식별자 검증은 동작하며 잠금 파일은 완료 시 삭제합니다. 교체 후 실패는 실패로 반환하지만 새 버전은 이미 확정되어 있고 (`stamp()`도 새 버전), 다음 저장은 그대로 통과합니다. 비협조 프로세스가 마지막 검사와 교체 사이에 기록하는 경쟁, 전원 차단 시 디렉터리의 영속성은 보장 범위 밖입니다.

저장 임시 파일 `.<ファイル名>.<pid>-<番号>.pending~`와 백업 임시 파일은 저장이 강제 종료되면 (`Drop` 미실행) 남습니다. 배타 잠금을 획득한 저장 (다른 저장자가 이 대상에 저장 중이지 않음)만 같은 폴더에 있는 이 대상 형식 (`.<ファイル名>.<数字>-<数字>.pending~`)의 파일을 자신의 임시 파일 생성 전에 삭제합니다. 백업 폴더의 잔여물은 백업을 만드는 저장 (대상에 이전 버전이 있고 백업하지 않는 설정이 아님)만, 해당 위치가 실제 폴더일 때 백업 생성 전에 삭제합니다. 다른 저장이 진행 중이거나 잠금을 사용할 수 없는 파일시스템 (저장자가 없음을 확인할 수 없음), 다른 대상의 임시 파일, 사용자 파일, 백업하지 않는 설정의 위치, 심볼릭 링크나 일반 파일로 막힌 위치는 변경하지 않습니다. 삭제하지 못해도 저장은 계속합니다 (다음 저장에서 재시도). 파일 이름이 200바이트보다 길면 임시 파일 이름 (OS 상한 255바이트를 넘지 않도록)과 식별에 사용하는 `<ファイル名>`을 앞부분을 자르고 전체 FNV-1a (16자리)를 붙인 이름으로 만듭니다 (앞부분이 같은 다른 긴 이름의 임시 파일과 혼동 방지). 임시 파일과 잠금 파일은 Windows에서 숨김 속성으로 만듭니다 (앞의 `.`만으로는 숨겨지지 않음). 숨김 속성은 교체 직전에 제거합니다 (유지한 채 이동하면 저장한 .ylp가 숨김 파일이 됨).

## 내보내기 (템플릿과 패딩)

`export`는 내보내기 템플릿 (`yolu_core::export`: Unity Standard / URP Lit·HDRP Lit·lilToon) 이미지를 폴더에 PNG로 기록합니다. 파일 이름은 0.4.x까지의 Unity 브리지와 같은 `<名前>[_<セット名>]_<接尾辞>.png`입니다 (세트가 여러 개일 때만 `_<セット名>`, 사용할 수 없는 문자는 `_`).

```rust,no_run
use yolu_core::export::ExportTemplate;
use yolu_core::padding::Reach;
use yolu_io::export::{write_template, PaddingSpec, SetExport, WriteOptions};

# let (document, coverage): (yolu_core::Document, Vec<bool>) = unimplemented!();
let report = write_template(
    std::path::Path::new("out"),
    &ExportTemplate::unity_standard(),
    &SetExport {
        stem: "Texture",
        set_name: None,
        document: &document,
        occlusion: None,
        padding: Some(PaddingSpec { coverage: &coverage, reach: Reach::Fill }),
        max_working_bytes: 1 << 30,
    },
    &WriteOptions::default(),
)?;
for image in &report.written {
    // Unityの取り込み設定は書かない。ここで渡す。
    println!("{} srgb={} normal_map={}", image.file_name, image.srgb, image.normal_map);
}
# Ok::<(), yolu_io::export::ExportError>(())
```

- 읽을 데이터가 있는 이미지만 기록합니다 (`should_write`). 사용하지 않는 채널만 읽는 이미지는 기록하지 않고 `skipped`에 접미사를 반환합니다.
- 절차는 (1) 이름·크기·덮어쓰기 확인, (2) 이미지를 1장씩 만들어 숨김 임시 파일에 기록하고 `sync_all` 후 다시 읽어 RGBA 일치 확인, (3) 모두 완료한 뒤 1장씩 `rename`으로 교체입니다. (2)까지 실패·취소하면 원본 파일은 1개도 바뀌지 않고 임시 파일도 남지 않습니다. (3) 도중 실패한 경우만 `ExportError::Partial`로 완료분을 알립니다 (새로 만든 파일은 삭제).
- 기존 파일은 기본적으로 교체하지 않고 `WouldReplace`를 반환합니다 (아무것도 기록하지 않음). `existing_files`로 보여 주고 확인한 뒤 `Overwrite::Replace`를 사용합니다. 교체하지 않는 설정에서는 `hard_link`로 배치하므로 확인 후 다른 프로세스가 만든 파일도 덮어쓰지 않습니다. 폴더·링크는 교체하지 않습니다.
- 여러 텍스처 세트는 `plan_template`로 기록할 이미지와 이름을 구하고, `clashes`로 이름 중복을 확인하며, `write_images` (내용은 호출자 함수에서 1장씩 제공)로 전체를 1회 절차로 처리합니다.
- 이미지 내용은 1장씩만 보유합니다. 상한은 1변 8192입니다 (0.4.x까지의 Unity 브리지 `RgbaPng`와 동일). PNG는 `composite_png`와 같은 인코더입니다 (행별 적응형 필터, 1 MiB를 초과하는 행 스트림은 블록으로 나눠 병렬 압축. 압축 바이트는 deflate 구현 버전에 의존).
- Unity 가져오기 설정 (sRGB·노멀 맵·알파를 투명도로 사용)은 파일에 기록하지 않습니다. `WrittenImage`의 `srgb`·`normal_map`·`alpha_is_transparency`를 나중에 사용합니다.
- 취소는 `WriteOptions::cancel` 플래그로 처리합니다 (교체 시작 전까지). 색상 확장 중에도 플래그를 확인하며 어디서 멈추든 `ExportError::Cancelled`로 반환합니다.

## 기타 진입점

- `atomic`: 임시 파일에 기록하고 마지막 1회 교체로 확정하는 쓰기입니다 (설정·브러시·프리셋·소재·캐시·다운로드). 임시 파일은 대상과 같은 폴더의 `.{ファイル名}.{pid}-{通し番号}.pending~` (파일 이름이 200바이트를 초과하면 앞부분을 자르고 지문 추가)이며 기록 후 `sync_all`, 교체는 `rename`입니다. Windows 공유 위반·잠금 위반·접근 거부 동안 총 1.5초까지 재시도합니다. 실패하면 임시 파일을 삭제하고 대상은 이전 상태로 유지합니다.
- `psd::write_verified`: 검증 포함 PSD 내보내기입니다. 같은 폴더의 임시 파일에 스트리밍 기록·동기화하고 끝까지 스트리밍으로 다시 읽어 검증한 뒤 (`verify_stream`), 기록 바이트열과 CRC-32·길이를 대조해 확정합니다 (교체하는 `rename` 또는 “이미 있으면 실패”인 `hard_link`). 읽을 수 없거나 기록 내용과 다른 PSD는 확정하지 않습니다.
- `library`: 개인 라이브러리 (프로젝트를 넘어 사용하는 소재 폴더)의 읽기·쓰기입니다. PNG·`.ylsmart`·`.ylbrush`·`.ylmaterial`을 확장자로 구분하며 폴더 밖 파일은 목록·읽기·쓰기·삭제 대상에 포함하지 않습니다.
- `distribution`: 배포용 사본입니다. 열린 .ylp에서 가져온 원본 PSD·제외하도록 선택한 에셋 (ID로 1개씩 선택. 목록은 에셋별 ID·종류·이름·크기·사용 여부를 보유하며 기본 선택은 `Project::unused_resources`)·모델 위치 (`pose.json`·Live Link로 연 모델 기록 `livelink.json` 포함)·베이크한 메시 맵·Unity 머티리얼 값·알 수 없는 엔트리·에셋 원본 경로 (텍스트 레이어 글꼴 파일 위치는 파일 이름만) 등을 제외한 사본 (`Project::distribution_inventory`·`Project::for_distribution`·`Removal`, 에셋 이외는 종류별)을 만듭니다. 작업 파일은 변경하지 않습니다.
- `fonts`: OS에 설치된 글꼴 목록 (`fontdb`)과 텍스트 레이어 글꼴 검색 규칙입니다 (저장된 위치는 절대 경로일 때만 사용하고 파일 이름만 있거나 상대 경로이면 이름으로 검색. 구조는 [docs/YLP_FORMAT.md](../../docs/ko/YLP_FORMAT.md)의 “텍스트”).
- `livelink`: Live Link 상대 문서 (루트 `livelink.json`)를 검증합니다 (크기·JSON 오브젝트·`format`). 내용은 앱이 읽습니다.
